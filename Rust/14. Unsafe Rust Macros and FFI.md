# 14. Unsafe Rust Macros and FFI

> The advanced toolbox: `unsafe` for the rare moments the compiler can't verify what you know, FFI for talking to C, and macros for code that writes code. Most application developers *use* these features via libraries far more often than they write them — but you must understand what they mean.

## 14.1 What `unsafe` Actually Means

`unsafe` does **not** turn off the borrow checker or type system. It unlocks exactly **five superpowers**, nothing more:

1. Dereference raw pointers (`*const T`, `*mut T`)
2. Call `unsafe` functions (including all FFI)
3. Implement `unsafe` traits (`Send`, `Sync`, …)
4. Access/modify mutable `static`s
5. Access fields of `union`s

Everything else — ownership, moves, lifetimes on references, type checking — still applies inside an `unsafe` block. The keyword's real meaning: *"the compiler cannot verify this invariant; I, the programmer, am now responsible for it."*

```rust
let mut n = 5;
let p1 = &n as *const i32;        // creating raw pointers: safe
let p2 = &mut n as *mut i32;
unsafe {                          // dereferencing them: unsafe
    println!("{} {}", *p1, *p2);
}
```

Raw pointers may be null, may dangle, may alias mutably — the rules you're vouching for manually. Violating them is **undefined behavior** (UB), which can manifest anywhere, not just at the bad line.

### The encapsulation principle (the important part)

Good unsafe is a **small audited core wrapped in a safe API whose types make misuse impossible**. This is how the standard library itself works — `Vec`, `String`, `Mutex` are full of unsafe internally, yet impossible to misuse from safe code:

```rust
/// Safe wrapper: splits a slice into two disjoint MUTABLE halves.
fn split_at_mut(v: &mut [i32], mid: usize) -> (&mut [i32], &mut [i32]) {
    let len = v.len();
    let ptr = v.as_mut_ptr();
    assert!(mid <= len);                       // the invariant, CHECKED
    unsafe {
        (std::slice::from_raw_parts_mut(ptr, mid),
         std::slice::from_raw_parts_mut(ptr.add(mid), len - mid))
    }
}
```

The borrow checker can't prove the halves don't overlap; the `assert!` + pointer math does. Callers get a 100% safe function.

**Rules of engagement:** exhaust safe alternatives first · keep blocks minimal · write a `// SAFETY:` comment stating the invariant and why it holds (enforced by `clippy::undocumented_unsafe_blocks`) · test under `cargo miri test`, the UB-detecting interpreter · in app code, prefer crates that have already done this (e.g. `bytemuck`, `zerocopy`).

## 14.2 FFI — Calling C and Being Called

```rust
// Calling C from Rust
unsafe extern "C" {
    fn abs(input: i32) -> i32;                 // declaration matches the C prototype
    fn strlen(s: *const std::ffi::c_char) -> usize;
}

fn main() {
    println!("{}", unsafe { abs(-3) });        // every FFI call is unsafe: C makes no promises
}
```

```rust
// Exposing Rust to C
#[unsafe(no_mangle)]                            // keep the symbol name (Rust 2024 syntax)
pub extern "C" fn add(a: i32, b: i32) -> i32 { a + b }
```

Key pieces of the FFI toolkit:

- **Strings:** C strings are NUL-terminated; Rust's aren't. Bridge with `std::ffi::CString` (Rust→C, owned) and `CStr` (borrowed view of a C string). Never pass `&str` raw.
- **Layout:** `#[repr(C)]` on structs guarantees C-compatible field order/padding (Rust's default layout is unspecified!).
- **Bindgen/cbindgen:** generate declarations automatically from headers (and vice versa).
- **build.rs + cc crate:** compile bundled C sources as part of `cargo build`.
- **Panics must not cross FFI boundaries** (UB) — catch with `std::panic::catch_unwind` in exported functions.
- The `libc` crate provides C type aliases; `-sys` crates (e.g. `openssl-sys`) are the convention for raw bindings, with a safe wrapper crate on top.

## 14.3 Declarative Macros — `macro_rules!`

Pattern-matching on token trees; the workhorse behind `vec!`, `println!`, `assert_eq!`:

```rust
#[macro_export]
macro_rules! my_vec {
    () => { Vec::new() };
    ($($x:expr),+ $(,)?) => {{           // one-or-more exprs, optional trailing comma
        let mut v = Vec::new();
        $( v.push($x); )+                 // repeat for each captured $x
        v
    }};
}
let v = my_vec![1, 2, 3];
```

Fragment specifiers you'll actually meet: `expr`, `ident`, `ty`, `pat`, `literal`, `path`, `block`, `tt` (raw token tree — the escape hatch). Repetition syntax: `$(...),*` (zero+), `$(...),+` (one+), `$(...)?` (optional).

**When to write one:** eliminating true syntactic boilerplate that functions/generics can't express — variadic-like APIs, test-case generation, implementing a trait for many tuple arities. Macros are hygienic (their internal names can't collide with yours) and expand at compile time. Debug with `cargo expand`.

```rust
// A genuinely useful everyday example: table-driven tests
macro_rules! parse_tests {
    ($($name:ident: $input:expr => $want:expr),* $(,)?) => {
        $( #[test] fn $name() { assert_eq!(parse($input), $want); } )*
    };
}
parse_tests! {
    empty: "" => 0,
    single: "5" => 5,
    sum: "2+3" => 5,
}
```

## 14.4 Procedural Macros — Code That Runs at Compile Time

Proc macros are Rust functions (in a special `proc-macro = true` crate) that receive a `TokenStream` and return one. Three kinds:

| Kind | Syntax at use site | Examples in the wild |
|---|---|---|
| **Derive** | `#[derive(Serialize)]` | serde, thiserror, clap |
| **Attribute** | `#[tokio::main]`, `#[test_case(…)]` | tokio, axum route macros |
| **Function-like** | `sqlx::query!("SELECT …")` | sqlx (compile-time-checked SQL!) |

```rust
// The shape of a derive macro (using syn + quote, the universal pair):
#[proc_macro_derive(Hello)]
pub fn hello_derive(input: TokenStream) -> TokenStream {
    let ast: syn::DeriveInput = syn::parse(input).unwrap();
    let name = &ast.ident;
    quote::quote! {
        impl Hello for #name {
            fn hello() { println!("Hello from {}", stringify!(#name)); }
        }
    }.into()
}
```

You'll *consume* proc macros daily (`#[derive(Debug, Clone, Serialize)]` is the ecosystem's backbone) and write them rarely. Costs to know: proc-macro crates slow compilation, and heavy macro DSLs can obscure errors. `syn`/`quote` docs plus `cargo expand` are the learning path when you do need one.

## 14.5 A Taste of the Deep End (know these exist)

- **`union`** — C-style untagged unions; field access is unsafe. FFI and niche bit-tricks only.
- **`#[repr(transparent)]`** — newtype guaranteed to have the exact ABI of its single field; essential for FFI-safe wrappers.
- **`std::mem::transmute`** — reinterpret bits as another type. The most dangerous function in Rust; almost always a better way exists (`from_ne_bytes`, `bytemuck`).
- **`MaybeUninit<T>`** — correctly handle uninitialized memory (replacing the deprecated `mem::uninitialized`).
- **`PhantomData<T>`** — zero-sized marker giving a type "pretend" ownership/variance over `T`; appears in unsafe data structures and typestate APIs.
- **Miri** — `cargo +nightly miri test` interprets your code and catches UB (use-after-free, invalid aliasing, uninit reads) that tests silently "pass" through. Non-negotiable for crates with real unsafe.
- **`no_std`** — drop the standard library (keep `core`, optionally `alloc`) for embedded/wasm/kernels. Much of the ecosystem supports it via feature flags.

**Perspective:** the overwhelming majority of Rust code — including most production services — contains zero `unsafe` blocks. Its existence is what lets Rust replace C at the bottom of the stack while the rest of us stay in the safe subset.
