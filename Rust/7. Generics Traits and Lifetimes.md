# 7. Generics Traits and Lifetimes

> Rust's abstraction toolkit. Generics give you code reuse without runtime cost, traits define shared behavior (Rust's answer to interfaces — but more powerful), and lifetimes let you *name* how long borrows last so references can flow through APIs safely.

## 7.1 Generics

```rust
fn largest<T: PartialOrd>(list: &[T]) -> &T {
    let mut max = &list[0];
    for item in list {
        if item > max { max = item; }
    }
    max
}

struct Pair<T> { a: T, b: T }
struct Point<X, Y> { x: X, y: Y }

impl<T> Pair<T> {                       // methods for any T
    fn new(a: T, b: T) -> Self { Self { a, b } }
}
impl Pair<f64> {                        // methods ONLY for Pair<f64>
    fn midpoint(&self) -> f64 { (self.a + self.b) / 2.0 }
}

enum Option<T> { Some(T), None }        // the generics you've been using all along
```

### Monomorphization — why generics are free

The compiler stamps out a **separate, fully concrete copy** of generic code for every type it's used with (`largest::<i32>`, `largest::<String>`, …). Each copy is optimized independently — calls are static, inlinable, no boxing, no vtable. Cost: larger binaries and longer compile times. This is the same model as C++ templates, but type-checked *at definition* against the declared bounds, so errors appear in your generic code, not in a user's instantiation 12 layers deep.

## 7.2 Traits — Shared Behavior

```rust
trait Summary {
    fn summarize(&self) -> String;                    // required method
    fn preview(&self) -> String {                     // default method
        format!("{}…", &self.summarize()[..10.min(self.summarize().len())])
    }
}

struct Article { title: String, body: String }
impl Summary for Article {
    fn summarize(&self) -> String { format!("{}: {}", self.title, self.body) }
}
```

Like interfaces, plus:
- **Default methods** can call required ones (template-method pattern built in).
- **Retroactive implementation:** you can implement *your* trait for *someone else's* type (e.g. `impl Summary for Vec<u8>`), and std traits for your types.
- **Associated types, associated consts, generic methods** — traits are a full abstraction mechanism, not just method lists.

### The orphan rule (coherence)

`impl Trait for Type` is allowed only if **the trait or the type is local to your crate**. You cannot `impl Display for Vec<u8>` (both foreign) — otherwise two crates could give one type conflicting behavior. Workaround: the **newtype pattern** — `struct Bytes(Vec<u8>); impl Display for Bytes {…}`.

## 7.3 Trait Bounds — Constraining Generics

```rust
fn notify<T: Summary>(item: &T) { println!("{}", item.summarize()); }
fn notify(item: &impl Summary) { }                    // impl Trait sugar — same thing

fn process<T: Summary + Clone>(item: &T) { }          // multiple bounds

fn complex<T, U>(t: &T, u: &U) -> String              // where clause for readability
where
    T: Summary + Clone,
    U: Summary + std::fmt::Debug,
{ /* ... */ }

impl<T: PartialOrd> Pair<T> {                         // conditional methods:
    fn larger(&self) -> &T { if self.a > self.b { &self.a } else { &self.b } }
}   // Pair<T> always exists; .larger() only when T is comparable

// impl Trait in RETURN position: "some concrete type implementing Iterator; not telling which"
fn evens() -> impl Iterator<Item = u32> { (0..).step_by(2) }
```

Return-position `impl Trait` is essential for closures and iterator chains whose concrete types are unnameable. Limitation: all return paths must be the *same* concrete type (use `Box<dyn Trait>` when they differ).

## 7.4 Static vs Dynamic Dispatch (interview essential)

```rust
fn f_static<T: Summary>(x: &T) { x.summarize(); }   // monomorphized per T; call inlined
fn f_dyn(x: &dyn Summary)     { x.summarize(); }    // ONE compiled function; vtable call
let items: Vec<Box<dyn Summary>> = vec![Box::new(article), Box::new(tweet)];  // mixed types!
```

| | Generics `<T: Trait>` | Trait objects `dyn Trait` |
|---|---|---|
| Dispatch | static (compile time) | dynamic (vtable at runtime) |
| Speed | fastest; inlinable | one indirect call; no inlining |
| Binary size | grows per instantiation | one copy |
| Heterogeneous collections | ❌ one T per instantiation | ✅ `Vec<Box<dyn Trait>>` |
| Where | zero-cost abstraction default | plugin lists, GUI widgets, erased returns |

A `&dyn Trait` / `Box<dyn Trait>` is a **fat pointer**: (data pointer, vtable pointer). **Object safety (dyn-compatibility):** a trait can be a `dyn` object only if its methods don't return `Self`, take `self` by value, or have generic type parameters — the vtable must be fixed. `Clone` is the classic non-object-safe example (returns `Self`).

**Default choice:** generics. Reach for `dyn` when you need heterogeneous collections or want to cut compile time/binary size on cold paths.

## 7.5 The Standard Traits You Must Know

| Trait | Method / purpose | Notes |
|---|---|---|
| `Debug` | `{:?}` | derive everywhere |
| `Display` | `{}` | implement manually; implies `ToString` |
| `Clone` / `Copy` | duplication | ch. 3 |
| `PartialEq` / `Eq` | `==` | `Eq` = full equivalence relation |
| `PartialOrd` / `Ord` | `< > sort` | floats: only `PartialOrd` (NaN) |
| `Hash` | hashing | required for HashMap keys (with `Eq`) |
| `Default` | `T::default()` | pairs with struct-update syntax |
| `From` / `Into` | conversions | implement `From`; `Into` comes free; used by `?` |
| `TryFrom` / `TryInto` | fallible conversions | returns `Result` |
| `FromStr` | `"x".parse::<T>()` | string parsing |
| `Iterator` | `next()` | ch. 9 — the crown jewel |
| `Deref` / `DerefMut` | `*` and auto-deref | smart pointers, ch. 10 |
| `Drop` | destructor | ch. 10 |
| `Send` / `Sync` | thread-transfer / thread-share | auto traits; ch. 11 |
| `Sized` | size known at compile time | implicit bound on every generic; `?Sized` opts out |

```rust
// From/Into in practice — ergonomic APIs:
impl From<u32> for UserId { fn from(v: u32) -> Self { UserId(v) } }
fn lookup(id: impl Into<UserId>) { let id = id.into(); /* ... */ }
lookup(42u32);          // caller passes anything convertible
```

## 7.6 Associated Types vs Generic Traits

```rust
trait Iterator {              // associated type: ONE Item per implementing type
    type Item;
    fn next(&mut self) -> Option<Self::Item>;
}
trait From<T> { fn from(t: T) -> Self; }   // generic param: MANY impls per type (From<u32>, From<&str>, …)
```

Rule: if each type should have exactly **one** implementation, use an associated type (cleaner inference, no turbofish). If a type legitimately implements the trait for **many** parameter types, use a generic parameter.

## 7.7 Lifetimes — Naming How Long Borrows Live

Lifetimes are generic parameters over *scopes*. They add **no runtime behavior whatsoever** — they only give you vocabulary to tell the compiler how input and output references relate.

### The problem they solve

```rust
fn longest(x: &str, y: &str) -> &str { ... }   // ❌ won't compile
```

The compiler must verify at every call site that the returned reference doesn't outlive its source — but which source, `x` or `y`? You have to say:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str {
    if x.len() > y.len() { x } else { y }
}
```

Read: *"there exists a scope `'a`; both inputs live at least that long; the output is valid for `'a`."* Concretely, the output is only usable while **both** inputs are still alive:

```rust
let s1 = String::from("long string");
let result;
{
    let s2 = String::from("short");
    result = longest(&s1, &s2);
    println!("{result}");          // ✅ fine here
}
// println!("{result}");           // ❌ s2 is gone; 'a ended
```

**Lifetimes never extend how long anything lives.** They only *describe* relationships so the borrow checker can verify them across function boundaries.

### Elision — why you rarely write them

The compiler fills in lifetimes using three rules:
1. Each input reference gets its own lifetime parameter.
2. If there is exactly **one** input lifetime, outputs get it.
3. If there's `&self`/`&mut self`, outputs get `self`'s lifetime.

```rust
fn first_word(s: &str) -> &str          // elided: fn first_word<'a>(s: &'a str) -> &'a str
fn get(&self) -> &str                   // elided via rule 3
fn longest(x: &str, y: &str) -> &str    // ambiguous → rules fail → you must annotate
```

### Structs holding references

```rust
struct Excerpt<'a> {
    part: &'a str,        // Excerpt cannot outlive the string it points into
}

impl<'a> Excerpt<'a> {
    fn shout(&self) -> String { self.part.to_uppercase() }
}

let novel = String::from("Call me Ishmael. Some years ago…");
let first = Excerpt { part: novel.split('.').next().unwrap() };
// drop(novel);           // ❌ would invalidate first
```

Guideline: structs that *borrow* are great for short-lived views (parsers, iterators); structs that *own* (`String` instead of `&str`) are simpler for long-lived data. When fighting lifetime soup, owning is usually the pragmatic fix.

### 'static

`'static` = "valid for the entire program". String literals are `&'static str`. The bound `T: 'static` means "T contains no non-static borrows" (owned types qualify!) — required when data must outlive the current scope (spawned threads, tokio tasks). It does *not* mean "lives forever"; it means "*could* live forever if kept".

## 7.8 All Three Together

```rust
use std::fmt::Display;

fn longest_with_note<'a, T: Display>(x: &'a str, y: &'a str, note: T) -> &'a str {
    println!("note: {note}");
    if x.len() > y.len() { x } else { y }
}
```

Generic over a type `T` (bounded by `Display`) *and* a lifetime `'a` — one signature encoding behavior requirements and borrow relationships, all verified at compile time, all erased by runtime.
