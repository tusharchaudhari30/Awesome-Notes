# 16. Interview Quick Fire QA

> Rapid-revision answers, grouped by topic. Each answer is the 30-second version you'd give in an interview — chapters referenced for the deep dive.

## Ownership & Borrowing (ch. 3)

**Q: What are Rust's ownership rules?**
Every value has exactly one owner; when the owner goes out of scope the value is dropped; assignment/passing moves ownership unless the type is `Copy`.

**Q: Move vs Copy vs Clone?**
Move: shallow copy of the stack part + source invalidated (default for heap-owning types). `Copy`: implicit bitwise duplication, only for trivially-copyable types (ints, bool, `&T`). `Clone`: explicit, potentially expensive deep copy.

**Q: The borrowing rules?**
Any number of shared refs `&T` XOR exactly one mutable ref `&mut T`; references must never outlive their referent. Enforced at compile time (borrow checker), ending data races, iterator invalidation, and dangling pointers.

**Q: Why can't you mutate a Vec while iterating it?**
The iterator holds a shared borrow; `push` needs `&mut` and could reallocate the buffer, dangling the iterator. The aliasing-XOR-mutation rule rejects it at compile time — the same bug is a runtime `ConcurrentModificationException` in Java and UB in C++.

**Q: How does Rust free memory without a GC?**
The compiler inserts `drop` calls at the owner's scope exit — deterministic, zero runtime machinery. RAII applies to all resources (files, locks, sockets), not just memory.

**Q: What is NLL?**
Non-lexical lifetimes: a borrow ends at its last *use*, not the end of the block — so sequential shared-then-mutable borrows compile fine.

## Types & Traits (ch. 4, 7)

**Q: How does Rust handle null?**
It doesn't have null. Absence is `Option<T>` — a different type from `T`, so the compiler forces handling before use. `Option<&T>` compiles to a plain nullable pointer (niche optimization), so it's also free.

**Q: Trait vs interface?**
Traits add: default methods, retroactive implementation on foreign types (bounded by the orphan rule), associated types/consts, and static dispatch by default via monomorphization rather than vtables.

**Q: Static vs dynamic dispatch?**
`<T: Trait>` monomorphizes — one specialized copy per concrete type, inlinable, zero cost, bigger binary. `dyn Trait` uses a fat pointer (data + vtable) — one compiled copy, indirect calls, enables heterogeneous collections. Default to generics; `dyn` for mixed-type collections or compile-time/binary-size relief.

**Q: What is the orphan rule?**
`impl Trait for Type` requires the trait or the type to be local to your crate — prevents two crates giving one type conflicting impls. Workaround: newtype wrapper.

**Q: What are lifetimes, really?**
Generic parameters over borrow durations. They add zero runtime behavior — they only declare relationships ("output lives as long as input `'a`") so the borrow checker can verify calls across function boundaries. Mostly elided by three rules; `'static` means "contains no non-static borrows".

**Q: Associated type vs generic trait parameter?**
Associated type (`Iterator::Item`) when each type has exactly one sensible impl; generic parameter (`From<T>`) when many impls per type make sense.

## Error Handling (ch. 6)

**Q: Rust's error model in one breath?**
No exceptions. Recoverable errors are values: `Result<T, E>`, propagated with `?` (which also auto-converts via `From`). Unrecoverable bugs panic. Libraries expose typed errors (`thiserror`); applications aggregate with `anyhow` + context.

**Q: When is panicking appropriate?**
Broken invariants/bugs, not expected failures. `unwrap()` in tests/prototypes; `expect("why this can't fail")` when you can prove impossibility; `Result` everywhere a caller could react.

**Q: What does `?` desugar to?**
`match expr { Ok(v) => v, Err(e) => return Err(From::from(e)) }` — early return with error conversion. Also works on `Option`.

## Collections & Strings (ch. 5)

**Q: String vs &str?**
`String` = owned, growable heap buffer (Vec<u8> guaranteed UTF-8). `&str` = borrowed fat-pointer view. Take `&str` in APIs; deref coercion converts `&String` automatically.

**Q: Why can't you index a String?**
UTF-8 is variable-width; byte position ≠ character position, and O(1) "i-th char" is impossible. Use `.chars()`, `.bytes()`, or byte-range slicing on known boundaries. `.len()` is bytes, not chars.

**Q: HashMap upsert idiom?**
`*map.entry(key).or_insert(0) += 1;` — the entry API does one lookup instead of contains+insert.

## Smart Pointers & Concurrency (ch. 10, 11)

**Q: Box vs Rc vs Arc?**
`Box`: unique heap owner (recursion, trait objects, big moves). `Rc`: shared ownership via refcount, single-thread only. `Arc`: atomic refcount, thread-safe. None allow mutation through sharing by themselves.

**Q: What is interior mutability?**
Mutation through `&self`, moving rule-enforcement to runtime: `Cell` (copy in/out, zero-cost), `RefCell` (runtime borrow counting — panics on violation), `Mutex`/`RwLock` (blocks instead). Combos: `Rc<RefCell<T>>` single-threaded, `Arc<Mutex<T>>` multi-threaded.

**Q: What are Send and Sync?**
Auto marker traits: `Send` = ownership may cross threads; `Sync` = `&T` may be shared across threads. Derived structurally; `thread::spawn` requires `Send + 'static`, so sending an `Rc` is a compile error — that's the whole "fearless concurrency" mechanism.

**Q: Why Arc<Mutex<T>> and not either alone?**
`Mutex<T>` owns the data so access *requires* the lock (compile-enforced), but must be shared by all threads → `Arc` provides shared ownership. `Rc` won't compile (`!Send`); a bare `Mutex` can't be moved into multiple closures.

**Q: What concurrency bugs does Rust NOT prevent?**
Deadlocks, livelock, starvation, and application-level race conditions. It prevents *data* races, not *logic* races.

**Q: How do Rc cycles leak, and the fix?**
Two `Rc`s pointing at each other keep counts ≥ 1 forever (leaks are safe, just bad). Break back-edges with `Weak` — non-owning, must `upgrade() -> Option<Rc<T>>` to use.

## Async (ch. 12)

**Q: How do Rust futures differ from JS promises?**
Lazy — a future does nothing until polled/awaited; a promise runs on creation. Futures compile to stack-allocated state machines; the runtime (Tokio etc.) is a library, not built into the language.

**Q: tokio::spawn vs join!?**
`join!` runs futures concurrently within the same task (no `Send` needed, no parallelism). `spawn` creates an independent task on the thread pool (parallel, requires `Send + 'static`).

**Q: Top async pitfalls?**
Forgetting `.await`; blocking calls (`std::thread::sleep`, sync IO) starving the executor; CPU work without `spawn_blocking`; holding a std `MutexGuard` across `.await`; assuming tasks aren't cancelled at await points (`select!` drops losers).

## Tooling & Misc (ch. 1, 8, 13, 14)

**Q: What does `unsafe` unlock?**
Five things only: deref raw pointers, call unsafe fns/FFI, impl unsafe traits, touch mutable statics, access union fields. The borrow checker stays on. Idiom: tiny audited unsafe core, safe API on top, `// SAFETY:` comments, Miri in CI.

**Q: Integer overflow behavior?**
Panics in debug, wraps in release. Explicit control: `checked_*` (Option), `wrapping_*`, `saturating_*`, `overflowing_*`.

**Q: Why are Rust compile times long, and mitigations?**
Monomorphization, heavy inlining/optimization, proc macros. Mitigate: `cargo check` in the loop, workspace splitting, sccache, fewer generic instantiations at crate boundaries (`dyn` where cold).

**Q: What is Cargo.lock for, and do you commit it?**
Exact resolved versions of the full dependency graph → reproducible builds. Commit for applications (libraries traditionally don't, though it's now acceptable).

**Q: Unit vs integration tests?**
Unit: `#[cfg(test)] mod tests` beside the code, can test private items. Integration: `tests/` dir, each file its own crate, exercises only the public API. Doc tests: examples in `///` compiled and run by `cargo test`.

**Q: Name the zero-cost abstractions.**
Generics (monomorphized), iterators (compile to loops, often auto-vectorized better than manual indexing), `Option<&T>`/newtypes (layout-optimized away), lifetimes (compile-time only), async state machines (no allocation per await).

## Curveballs

**Q: Why does `let x = x;` sometimes break code later?** Shadowing creates a *new* binding; if the old one was borrowed, or the new one has a different type/mutability, later uses change meaning.

**Q: Can a struct contain a reference?** Yes, with a lifetime parameter (`struct View<'a> { s: &'a str }`) — the struct then can't outlive the referent. Prefer owned fields for long-lived data.

**Q: Why is `String` 3 words but `&str` 2?** `String` = (ptr, len, capacity) — it manages growth. `&str` = (ptr, len) — a view needs no capacity.

**Q: What happens on panic in a spawned thread?** That thread dies; `join()` returns `Err`. In the main thread, the process exits. A panic while a `Mutex` is held poisons it.

**Q: `impl Trait` argument vs return position?** Argument: sugar for a generic param. Return: an opaque concrete type ("some Iterator") — required for closures, but all return paths must be the same type.
