# 6. Error Handling

> Rust has no exceptions. Errors are **values**, encoded in return types, and the compiler forces callers to acknowledge them. The result: failure paths are visible in every signature, and "I forgot to handle that error" becomes a compile error instead of a 3 a.m. page.

## 6.1 The Two-Tier Model

| Tier | Mechanism | For | Recoverable? |
|---|---|---|---|
| **Expected failures** | `Result<T, E>` | file missing, bad input, network timeout — anything the caller might handle | Yes |
| **Bugs / broken invariants** | `panic!` | index out of bounds, violated precondition, "this can never happen" happened | No (by design) |

**Rule of thumb:** if the *caller* could sensibly react, return `Result`. If the *program itself* is wrong, panic. Libraries should almost never panic on bad input — return `Result` and let the application decide.

## 6.2 panic!

```rust
panic!("invariant violated: {details}");
let v = vec![1]; v[99];                  // panics: index out of bounds
let x: Option<i32> = None; x.unwrap();   // panics: called unwrap on None
unreachable!(); todo!(); unimplemented!(); // structured placeholder panics
assert!(cond); assert_eq!(a, b); debug_assert!(cond);  // assertion panics
```

- Default behavior: **unwind** — run `Drop` for everything on the stack, then exit the thread. `panic = "abort"` in Cargo.toml kills the process immediately (smaller binaries, common in embedded).
- `RUST_BACKTRACE=1 cargo run` prints a stack trace.
- A panic in a spawned thread kills that thread only; the main thread sees it via `JoinHandle::join` returning `Err`.
- `catch_unwind` exists but is for FFI boundaries and thread-pool isolation — **not** a try/catch substitute.

## 6.3 Result\<T, E\>

```rust
enum Result<T, E> { Ok(T), Err(E) }     // just an enum from chapter 4!
```

```rust
use std::fs::File;

match File::open("cfg.toml") {
    Ok(file) => read(file),
    Err(e) => eprintln!("open failed: {e}"),
}
```

`Result` is `#[must_use]` — silently ignoring one is a compiler warning. Handling options, bluntest to nicest:

```rust
let f = File::open("x").unwrap();                 // panic on Err — prototypes/tests
let f = File::open("x").expect("x must exist");   // panic with context — better
let f = File::open("x").unwrap_or_else(|_| create_default());
let ok = result.is_ok();
let opt: Option<T> = result.ok();                 // Result → Option, discarding the error
```

### Combinators (mirror Option's)

```rust
let n: Result<i32, _> = "42".parse::<i32>().map(|x| x * 2);        // transform Ok
let r = result.map_err(MyError::from);                             // transform Err
let r = parse(s).and_then(validate);                               // chain fallible steps
let v = result.unwrap_or_default();
```

## 6.4 The `?` Operator — Ergonomic Propagation

`expr?` means: *if `Ok(v)`, evaluate to `v`; if `Err(e)`, `return Err(e.into())` from the enclosing function.*

```rust
use std::fs; use std::io;

// Without ?
fn read_username_verbose() -> Result<String, io::Error> {
    let s = match fs::read_to_string("user.txt") {
        Ok(s) => s,
        Err(e) => return Err(e),
    };
    Ok(s.trim().to_string())
}

// With ? — same semantics
fn read_username() -> Result<String, io::Error> {
    let s = fs::read_to_string("user.txt")?;
    Ok(s.trim().to_string())
}
```

Three details that matter:

1. **Auto-conversion:** `?` calls `From::from` on the error — if `MyError: From<io::Error>`, then `io` failures propagate into `Result<_, MyError>` automatically. This is the hook `thiserror`'s `#[from]` uses.
2. **Works on Option** too (early-returns `None`), inside functions returning `Option`. You can't mix `Result` and `Option` with `?` in one function without converting: `opt.ok_or(Error::Missing)?` / `res.ok()?`.
3. **main can return Result:** `fn main() -> Result<(), Box<dyn std::error::Error>>` lets you use `?` at top level; an `Err` prints via `Debug` and exits with code 1.

```rust
// Chains beautifully:
let port: u16 = std::env::var("PORT")?.parse()?;
```

## 6.5 Designing Error Types

### The std::error::Error trait

```rust
pub trait Error: Debug + Display {
    fn source(&self) -> Option<&(dyn Error + 'static)> { None }  // the cause chain
}
```

Any good error type implements `Debug` (for logs), `Display` (for humans), and `Error` (for composition and cause chains).

### Level 1: String errors (prototyping only)

```rust
fn parse(s: &str) -> Result<Config, String> {
    Err(format!("bad line: {s}"))       // easy, but callers can't match on cases
}
```

### Level 2: Custom enum (the library standard)

```rust
use std::fmt;

#[derive(Debug)]
pub enum ConfigError {
    Io(std::io::Error),
    Parse { line: usize, msg: String },
    MissingKey(String),
}

impl fmt::Display for ConfigError {
    fn fmt(&self, f: &mut fmt::Formatter<'_>) -> fmt::Result {
        match self {
            Self::Io(e) => write!(f, "io error: {e}"),
            Self::Parse { line, msg } => write!(f, "parse error on line {line}: {msg}"),
            Self::MissingKey(k) => write!(f, "missing key `{k}`"),
        }
    }
}

impl std::error::Error for ConfigError {
    fn source(&self) -> Option<&(dyn std::error::Error + 'static)> {
        match self { Self::Io(e) => Some(e), _ => None }
    }
}

impl From<std::io::Error> for ConfigError {          // enables `?` conversion
    fn from(e: std::io::Error) -> Self { Self::Io(e) }
}
```

Callers can now `match` on variants and react differently to a missing file vs a syntax error.

### Level 3: `thiserror` — Level 2 without the boilerplate

```rust
use thiserror::Error;

#[derive(Debug, Error)]
pub enum ConfigError {
    #[error("io error: {0}")]
    Io(#[from] std::io::Error),          // Display + From + source(), all generated
    #[error("parse error on line {line}: {msg}")]
    Parse { line: usize, msg: String },
    #[error("missing key `{0}`")]
    MissingKey(String),
}
```

Identical expansion to the manual version — zero runtime difference.

### Level 4: `anyhow` — for applications

```rust
use anyhow::{anyhow, bail, Context, Result};   // Result<T> = Result<T, anyhow::Error>

fn run() -> Result<()> {
    let cfg = std::fs::read_to_string("app.toml")
        .context("failed to read app.toml")?;            // attach context as it bubbles
    let port: u16 = std::env::var("PORT")
        .context("PORT not set")?
        .parse()
        .with_context(|| format!("PORT must be a number"))?;
    if port < 1024 { bail!("refusing privileged port {port}"); }
    Ok(())
}
// Error output shows the whole chain:
//   refusing privileged port 80
//   caused by: ...
```

`anyhow::Error` is a type-erased, boxed error that accepts anything implementing `std::error::Error` — perfect when you only need to *report* errors, not match on them.

### The ecosystem consensus

| You are writing a… | Use | Because callers… |
|---|---|---|
| **Library** | `thiserror` enum (or manual) | need to match on specific failures |
| **Application** | `anyhow` + `.context()` | just log/display; context chains beat variant matching |
| Quick script | `Box<dyn Error>` | zero dependencies: `Result<(), Box<dyn Error>>` |

## 6.6 Panic-vs-Result Judgment Calls

- **Indexing:** `v[i]` (panic — "I know it's in bounds") vs `v.get(i)` (Result-ish — untrusted index). Both exist on purpose; pick per call site.
- **`unwrap()` in production** is acceptable when a `None`/`Err` is truly impossible and you can argue why — but prefer `expect("why it can't fail")` so the panic message carries the argument.
- **Constructors:** validate and return `Result` rather than panicking (`Config::parse(s) -> Result<Config, ConfigError>`), so "invalid config" is representable only as an error, never as a half-built struct.
- **Don't stringify too early:** keep structured errors as deep as possible; convert to a message only at the logging/display boundary.

## 6.7 Patterns Worth Knowing

```rust
// Collect Vec<Result<T,E>> → Result<Vec<T>, E>  (first error wins)
let nums: Result<Vec<i32>, _> = ["1", "2", "x"].iter().map(|s| s.parse::<i32>()).collect();

// Partition successes and failures
let (oks, errs): (Vec<_>, Vec<_>) = results.into_iter().partition(Result::is_ok);

// Option ↔ Result bridges
let r: Result<T, E> = opt.ok_or(E::Missing);
let r = opt.ok_or_else(|| E::Missing(name.clone()));   // lazy
let o: Option<T> = res.ok();

// Fallible main
fn main() -> anyhow::Result<()> { run() }
```

**Mental model:** `Result` is just an enum + `match` + one sugar operator (`?`) + one conversion trait (`From`). There is no hidden control flow — every error path is written in the code you can read.
