# 12. Async Programming

> Async Rust = massive IO concurrency without a thread per connection. It's also the part of Rust with the most sharp edges — this chapter covers the model, Tokio in practice, and the pitfalls that bite everyone once.

## 12.1 The Model: Futures Are Lazy State Machines

```rust
async fn fetch_user(id: u64) -> Result<User, Error> {
    let resp = http_get(&format!("/users/{id}")).await?;
    Ok(parse(resp)?)
}
```

- `async fn` returns `impl Future<Output = T>` immediately, **doing nothing**. Futures are inert values — no work happens until awaited/polled. (Opposite of JavaScript, where a Promise starts running when created.)
- The compiler transforms the function body into a **state machine**: one state per `.await` point, locals that live across an await become fields of the machine. Zero heap allocation, no callbacks.
- `.await` = "yield here if not ready". The task suspends, the thread moves on to other tasks, and a **waker** re-queues the task when the IO completes.

```rust
pub trait Future {
    type Output;
    fn poll(self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output>;
    // Poll::Ready(T) | Poll::Pending  (registers the waker before returning Pending)
}
```

**Rust has no built-in runtime.** The standard library defines the `Future` contract; an executor crate (Tokio, async-std, smol, embassy) supplies the event loop, timers, and IO. This split keeps async usable from servers to microcontrollers.

### Concurrency vs parallelism, one line

Async = *concurrency* (many tasks interleaved on few threads, ideal for waiting on IO). Threads/rayon = *parallelism* (many CPUs computing). Tokio's multi-thread runtime gives both, but CPU-heavy code still doesn't belong on async worker threads (see 12.6).

## 12.2 Tokio Essentials

```rust
#[tokio::main]                       // macro wraps main in a runtime
async fn main() -> anyhow::Result<()> {
    let body = reqwest::get("https://example.com").await?.text().await?;
    println!("{} bytes", body.len());
    Ok(())
}
```

### Spawning tasks

```rust
let handle = tokio::spawn(async move {          // task: a lightweight (~KB) green "thread"
    process(item).await
});
let result = handle.await??;    // outer ?: JoinError (panic/cancel); inner: your Result
```

- `tokio::spawn` requires the future to be `Send + 'static` → `move` captures, `Arc` for sharing.
- Tasks run **concurrently on a work-stealing thread pool**; spawning is cheap enough for one task per connection.
- Dropping a `JoinHandle` detaches the task (it keeps running); `handle.abort()` cancels it.

### Concurrency combinators

```rust
// Run a fixed set concurrently, wait for all:
let (a, b) = tokio::join!(fetch_user(1), fetch_orders(1));       // no spawn needed, same task
let results = futures::future::try_join_all(ids.iter().map(fetch)).await?;

// First one wins:
tokio::select! {
    res = fetch_primary()  => handle(res),
    res = fetch_fallback() => handle(res),
    _ = tokio::time::sleep(Duration::from_secs(5)) => return Err(Timeout),
}

// Timeout wrapper:
let res = tokio::time::timeout(Duration::from_secs(2), fetch_user(1)).await; // Result<inner, Elapsed>
```

`join!` runs futures concurrently **within one task** (no Send needed, no parallelism); `spawn` creates independent tasks (parallelism, needs Send). Interview-worthy distinction.

### Bounded concurrency (don't hammer that API)

```rust
use futures::stream::{self, StreamExt};

let results: Vec<_> = stream::iter(urls)
    .map(|u| async move { fetch(u).await })
    .buffer_unordered(10)          // at most 10 in flight
    .collect().await;
// Alternative: Arc<tokio::sync::Semaphore> + acquire per task
```

## 12.3 Async Sync Primitives and Channels

Use **tokio's** versions inside async code — std's block the whole worker thread:

| Need | Tool |
|---|---|
| Mutual exclusion held across `.await` | `tokio::sync::Mutex` |
| Short lock, never held across await | `std::sync::Mutex` is fine (and faster) |
| Work queue | `tokio::sync::mpsc` (bounded → backpressure) |
| One-shot result/handshake | `tokio::sync::oneshot` |
| Fan-out events to all listeners | `tokio::sync::broadcast` |
| Latest-value config/shutdown signal | `tokio::sync::watch` |
| Limit concurrency | `tokio::sync::Semaphore` |

```rust
let (tx, mut rx) = tokio::sync::mpsc::channel::<Job>(100);
tokio::spawn(async move {
    while let Some(job) = rx.recv().await { work(job).await; }
});
tx.send(job).await?;             // .await = backpressure when the buffer is full
```

## 12.4 Streams — Async Iterators

```rust
use futures::StreamExt;                       // Stream = async Iterator

let mut lines = tokio_stream::wrappers::LinesStream::new(reader.lines());
while let Some(line) = lines.next().await {
    handle(line?);
}
// Adapters mirror Iterator: .map .filter .take .buffer_unordered .collect
```

No stable `for await` syntax yet — `while let Some(x) = s.next().await` is the loop shape.

## 12.5 Pinning, Send Bounds, and Traits — The Hard Parts, Briefly

- **Why `Pin`?** The compiled state machine may hold references to its *own* fields across awaits (self-referential). Moving it in memory would invalidate them, so futures must be pinned (address-stable) before polling. In practice: runtimes pin for you; you'll only touch `Box::pin`/`tokio::pin!` when manually `select!`-ing on a future in a loop or storing unnamed futures.
- **`Send` errors** (`future cannot be sent between threads safely`): something non-Send (an `Rc`, a `RefCell` guard, a `std::sync::MutexGuard`) is alive **across an `.await`**. Fix: drop it before awaiting (scope it in `{}`), or use the tokio equivalents.
- **Async in traits:** native `async fn` in traits works (Rust 1.75+) for generic use; for `dyn Trait` objects you still typically use the `#[async_trait]` macro (boxes the returned future).

## 12.6 The Classic Pitfalls (learn these before they learn you)

```rust
// 1. Forgetting .await — future created, never run. #[must_use] warns.
do_thing();            // ⚠️ does nothing!
do_thing().await;      // ✅

// 2. BLOCKING the executor — freezes ALL tasks on that worker thread:
std::thread::sleep(d);                 // ❌ never in async
tokio::time::sleep(d).await;           // ✅
let data = std::fs::read("big")?;      // ❌ sync IO in async fn
let data = tokio::fs::read("big").await?;   // ✅

// 3. CPU-heavy work in a task — starves the reactor:
let out = tokio::task::spawn_blocking(move || heavy_compute(input)).await?;  // ✅ dedicated pool
// (or send it to a rayon pool and await a oneshot)

// 4. Holding a std MutexGuard across .await — can deadlock the pool:
let g = std_mutex.lock().unwrap();
some_io().await;                       // ❌ guard alive across await (also breaks Send)
// ✅ scope the guard, or use tokio::sync::Mutex

// 5. Cancellation surprises: dropping a future/task cancels it AT ANY await point.
//    tokio::select! drops the losing branches — partial writes, half-done state.
//    Design cancel-safe: idempotent steps, cleanup in Drop guards, or shield critical
//    sections by spawning them as their own task.
```

## 12.7 A Realistic Skeleton — Server With Graceful Shutdown

```rust
use tokio::{net::TcpListener, sync::watch};

#[tokio::main]
async fn main() -> anyhow::Result<()> {
    let (shutdown_tx, shutdown_rx) = watch::channel(false);
    let listener = TcpListener::bind("0.0.0.0:8080").await?;

    let server = tokio::spawn({
        let mut shutdown = shutdown_rx.clone();
        async move {
            loop {
                tokio::select! {
                    Ok((sock, _)) = listener.accept() => {
                        let mut shutdown = shutdown.clone();
                        tokio::spawn(async move {
                            tokio::select! {
                                r = handle_conn(sock) => { if let Err(e) = r { tracing::warn!(?e); } }
                                _ = shutdown.changed() => { /* drain & close */ }
                            }
                        });
                    }
                    _ = shutdown.changed() => break,
                }
            }
        }
    });

    tokio::signal::ctrl_c().await?;
    shutdown_tx.send(true)?;              // broadcast shutdown
    server.await?;
    Ok(())
}
```

Patterns on display: task-per-connection, `watch` for shutdown broadcast, `select!` to race work against cancellation.

## 12.8 When to Use Async At All

| Workload | Choice |
|---|---|
| Network server, many concurrent connections | async (this is the sweet spot) |
| HTTP calls in a CLI, a handful at a time | async is fine; blocking `reqwest::blocking` also fine |
| CPU-bound data crunching | threads / rayon — async adds nothing |
| Simple sequential tool | no async — don't pay the complexity tax |
| Embedded / no_std | async via embassy is surprisingly strong |

**Rule:** async is for *waiting on many things at once*. If you aren't IO-bound with high concurrency, plain threads are simpler and just as fast.
