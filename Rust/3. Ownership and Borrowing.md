# 3. Ownership and Borrowing

> **This is the chapter.** Ownership is Rust's central innovation — memory safety without a garbage collector, enforced entirely at compile time. Everything else in the language is shaped by it.

## 3.1 The Rules (memorize these)

**Ownership:**
1. Every value has exactly **one owner**.
2. When the owner goes out of scope, the value is **dropped** (freed).
3. Assigning or passing a value **moves** ownership (unless the type is `Copy`).

**Borrowing:**
4. At any time you may have **either** any number of immutable references (`&T`) **or** exactly one mutable reference (`&mut T`) — never both.
5. References must **never outlive** the data they point to.

Rules 4–5 are what the **borrow checker** enforces. Rule 4 is often summarized as *"aliasing XOR mutation"* — data may be shared, or mutated, but not both simultaneously. This one invariant kills data races, iterator invalidation, and use-after-free in a single stroke.

## 3.2 Stack, Heap, and Why Ownership Exists

```
STACK (fast, fixed-size, auto-managed)     HEAP (flexible size, must be managed)
┌──────────────────────────┐
│ s: String                │
│  ├─ ptr    ──────────────┼──────────▶  ┌───────────────┐
│  ├─ len: 5               │             │ h e l l o     │
│  └─ capacity: 5          │             └───────────────┘
└──────────────────────────┘
```

A `String` is a small stack struct (pointer, length, capacity) owning a heap buffer. The question every language must answer: *when is the heap buffer freed?*

- **C/C++:** you call `free`/`delete` manually → use-after-free, double-free, leaks.
- **Java/Go/Python:** a garbage collector finds unreachable memory at runtime → safe, but with runtime cost and nondeterministic timing.
- **Rust:** the compiler inserts the free (a `drop` call) at the exact point the single owner goes out of scope. Deterministic, zero runtime cost, verified safe.

This is RAII (Resource Acquisition Is Initialization) made mandatory — and it applies to *all* resources, not just memory: files close, mutexes unlock, sockets shut down, all deterministically when their owner is dropped.

## 3.3 Move Semantics

```rust
let s1 = String::from("hello");
let s2 = s1;                      // MOVE: s1 is now invalid
// println!("{s1}");              // ❌ compile error: borrow of moved value `s1`
println!("{s2}");                 // ✅
```

Assignment copies only the stack part (ptr/len/cap) and **invalidates the source**. There is never a moment where two owners could both free the same heap buffer. The same applies to function calls and returns:

```rust
fn take(s: String) { }            // ownership moves INTO the function...
fn give() -> String { String::from("hi") }  // ...and OUT via return

let s = String::from("hello");
take(s);                          // s moved; unusable afterwards
let t = give();                   // t now owns the returned String
```

**Key insight:** a move is always a cheap, shallow `memcpy` of the stack portion — moving a 10 GB `Vec` copies three machine words. The compiler simply forbids using the old name.

## 3.4 Copy vs Clone

```rust
let x = 5;
let y = x;              // COPY — both valid; integers are trivially duplicable
println!("{x} {y}");    // ✅ fine

let s1 = String::from("hi");
let s2 = s1.clone();    // CLONE — explicit deep copy of the heap buffer
println!("{s1} {s2}");  // ✅ both valid, two separate buffers
```

| Trait | What | Cost | Who has it |
|---|---|---|---|
| `Copy` | implicit bitwise duplication on assignment | trivial, always cheap | integers, floats, `bool`, `char`, shared refs `&T`, tuples/arrays of `Copy` types |
| `Clone` | explicit `.clone()` call, arbitrary duplication logic | can be expensive (heap allocation) | almost everything; supertrait of `Copy` |

A type can be `Copy` only if duplicating its bits is fully correct — which is why nothing owning a heap allocation (`String`, `Vec`, `Box`) can ever be `Copy`. `&mut T` is also not `Copy` (that would create two simultaneous mutable references).

Derive both on small plain-data types: `#[derive(Clone, Copy)]`.

**Pragmatic note:** liberally `.clone()`-ing to escape borrow-checker fights is fine while learning and often fine in production — profile before optimizing clones away.

## 3.5 Borrowing: References

Moving ownership into every function would be unbearable, so you **lend** values instead:

```rust
fn len(s: &String) -> usize { s.len() }     // borrows; does not own

let s = String::from("hello");
let n = len(&s);          // lend s
println!("{s} has {n}");  // s still valid ✅
```

```rust
// Mutable borrow: exactly one at a time
fn push_world(s: &mut String) { s.push_str(" world"); }

let mut s = String::from("hello");
push_world(&mut s);
```

### The aliasing rules in action

```rust
let mut s = String::from("hello");

let r1 = &s;          // ✅ shared borrow
let r2 = &s;          // ✅ another shared borrow — fine
// let r3 = &mut s;   // ❌ cannot borrow mutably while shared borrows are live
println!("{r1} {r2}");

let r3 = &mut s;      // ✅ NOW fine: r1/r2 last used above (non-lexical lifetimes)
r3.push('!');
```

**Non-Lexical Lifetimes (NLL):** a borrow ends at its *last use*, not at the end of the block. Modern Rust is far more permissive than folklore suggests.

### Why the "one mutable XOR many shared" rule?

The canonical demonstration — iterator invalidation, a real bug class in C++ and Java (`ConcurrentModificationException`, but at compile time):

```rust
let mut v = vec![1, 2, 3];
for x in &v {              // shared borrow of v is live for the whole loop
    v.push(*x);            // ❌ compile error: cannot borrow `v` as mutable
}
```

Growing the `Vec` could reallocate the buffer, leaving the iterator dangling. Rust rejects the program instead of corrupting memory at runtime.

### Dangling references are impossible

```rust
fn dangle() -> &String {              // ❌ compile error
    let s = String::from("hello");
    &s                                // s is dropped at end of fn; reference would dangle
}
fn no_dangle() -> String {            // ✅ move ownership out instead
    String::from("hello")
}
```

## 3.6 Slices — Borrowed Views

A slice is a reference to a contiguous chunk of a collection: a pointer + a length ("fat pointer").

```rust
let s = String::from("hello world");
let hello: &str = &s[0..5];      // view into s's buffer — no copy
let world: &str = &s[6..];

let v = vec![1, 2, 3, 4, 5];
let mid: &[i32] = &v[1..4];      // [2, 3, 4]
```

- `&str` is a string slice; `&[T]` is an array/vec slice.
- Slices borrow, so while a slice is alive the owner can't be mutated — `s.clear()` while `hello` exists is a compile error (it would dangle).
- **API guideline:** accept `&str` instead of `&String`, and `&[T]` instead of `&Vec<T>`. Deref coercion converts automatically at call sites, and your function accepts more input types (literals, slices, arrays).

```rust
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}
first_word("hi there");            // works with a literal
first_word(&String::from("hi"));   // and with &String (deref coercion)
```

## 3.7 Ownership in Function Design — Decision Table

| Your function needs to… | Take | Example |
|---|---|---|
| Read the data | `&T` (or `&str`/`&[T]`) | `fn print(s: &str)` |
| Modify in place | `&mut T` | `fn sort(v: &mut Vec<i32>)` |
| Consume / store / send elsewhere | `T` (by value) | `fn spawn_task(cfg: Config)` |
| Return new data | `-> T` (by value) | `fn build() -> String` |
| Maybe-clone flexibility | `Cow<'_, str>` / generics | advanced (ch. 10, 15) |

Default order of preference: `&T` → `&mut T` → `T`. Take ownership only when you genuinely need it — signatures then document intent: *by-value parameter = "I'm keeping this."*

## 3.8 Common Borrow-Checker Errors, Decoded

| Error | Meaning | Typical fix |
|---|---|---|
| `borrow of moved value` | used a variable after ownership moved | borrow instead (`&x`), `.clone()`, or restructure |
| `cannot borrow as mutable more than once` | two `&mut` alive at once | shrink borrow scopes; NLL usually helps once uses are separated |
| `cannot borrow as mutable because also borrowed as immutable` | read borrow still live at write | finish reads first; hoist values out (`let len = v.len();` before `v.push`) |
| `does not live long enough` | reference would outlive its data | return owned data; move value into the longer-lived scope |
| `cannot move out of borrowed content` | tried to take ownership through `&` | `.clone()`, `std::mem::take/replace`, or take `self`/by-value |
| `use of partially moved value` | moved one field out of a struct then used the struct | `mem::take` the field, destructure fully, or borrow it |

Two idioms worth knowing early:

```rust
// mem::take — move a field out, leaving a default in its place
let data = std::mem::take(&mut self.buffer);   // self stays valid

// Split borrows: borrowing two DIFFERENT fields simultaneously is fine
let a = &mut self.left;
let b = &mut self.right;   // ✅ disjoint fields
// ...but calling &mut self methods twice is not — the checker tracks fields, not methods.
```

## 3.9 The Mental Model, Compressed

```
        OWNED  T          BORROWED &T           BORROWED &mut T
        "I own it"        "I'm reading it"      "I'm the sole editor"
        drop when done    many readers OK       exactly one, no readers
        can move/consume  can't mutate*         can mutate
                          (*without interior mutability — chapter 10)
```

Ask three questions about any value:
1. **Who owns it?** (exactly one binding at any time)
2. **Who is borrowing it right now?** (many readers XOR one writer)
3. **Will any borrow outlive the owner?** (must be no)

When the checker rejects your code, it is almost always pointing at a genuine design question: *"you have two places wanting to control this data — which one is in charge?"* Answer that, and the fix writes itself. Lifetimes — the annotations that let you *name* borrow durations in signatures — are covered with generics in chapter 7.
