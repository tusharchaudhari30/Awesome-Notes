# 11. Concurrency and Parallelism

> "Fearless concurrency": the ownership system makes data races a **compile-time error**. The same rules that manage memory — one writer XOR many readers, values have owners — are exactly the rules that make threading safe.

## 11.1 Threads

```rust
use std::thread;

let handle = thread::spawn(|| {
    println!("hello from spawned thread: {:?}", thread::current().id());
    42
});
let result: i32 = handle.join().unwrap();   // wait; unwrap panics if the thread panicked
```

- OS (1:1) threads — real parallelism, ~MB stack each. For thousands of concurrent *waits*, use async (chapter 12); for CPU work across cores, threads/rayon.
- Closures given to `spawn` must be `move` + `'static`: the thread may outlive the caller's stack frame, so it cannot borrow from it:

```rust
let v = vec![1, 2, 3];
let h = thread::spawn(move || println!("{v:?}"));   // v moved in — no dangling possible
h.join().unwrap();
```

### Scoped threads (Rust 1.63+) — borrowing IS allowed when lifetime is provable

```rust
let data = vec![1, 2, 3];
let mid = data.len() / 2;
let (left, right) = data.split_at(mid);

thread::scope(|s| {
    s.spawn(|| println!("left  {:?}", left));    // borrows OK: scope guarantees join
    s.spawn(|| println!("right {:?}", right));   // disjoint slices → parallel reads fine
});                                              // all joined here, before data can drop
```

`split_at_mut` even hands out two *mutable* halves safely — disjointness proven by the API.

## 11.2 Message Passing — Channels

> "Do not communicate by sharing memory; share memory by communicating."

```rust
use std::sync::mpsc;   // multi-producer, single-consumer

let (tx, rx) = mpsc::channel();          // unbounded; sync_channel(n) = bounded/backpressure

let tx2 = tx.clone();                    // multiple producers
thread::spawn(move || tx.send("from worker 1").unwrap());
thread::spawn(move || tx2.send("from worker 2").unwrap());

for msg in rx {                          // rx is an iterator; ends when ALL senders drop
    println!("{msg}");
}
```

- `send` **moves** the value — after sending, the producer can't touch it. Ownership transfer through the channel is what makes this race-free by construction.
- `recv()` blocks; `try_recv()` doesn't; dropping all senders ends the loop cleanly (built-in shutdown signaling).
- Ecosystem: `crossbeam-channel` (faster, `select!`, MPMC), `flume`; async channels in tokio (`mpsc`, `oneshot`, `broadcast`, `watch`).

**Worker-pool shape:** wrap the receiver in `Arc<Mutex<Receiver>>` so several workers can pull jobs; or use an MPMC channel and skip the mutex.

## 11.3 Shared State — Arc + Mutex

```rust
use std::sync::{Arc, Mutex};
use std::thread;

let counter = Arc::new(Mutex::new(0));

let handles: Vec<_> = (0..10).map(|_| {
    let counter = Arc::clone(&counter);          // clone the handle, move it in
    thread::spawn(move || {
        let mut n = counter.lock().unwrap();     // blocks; returns MutexGuard
        *n += 1;
    })                                           // guard drops → UNLOCKS automatically
}).collect();

for h in handles { h.join().unwrap(); }
println!("total = {}", *counter.lock().unwrap()); // 10
```

Why each piece is mandatory (great interview answer):
- **`Mutex<T>` owns its data** — the *only* way to reach `T` is through `lock()`. "Forgot to take the lock" is a compile error, not a code-review hope. Unlock is automatic via `Drop` on the guard — no "forgot to unlock" either.
- **`Arc`** (atomic refcount) gives every thread an owner-handle. Plain `Rc` won't compile here (`!Send`), and a bare `Mutex` can't be moved into 10 closures.
- `lock().unwrap()`: the `Err` case is **poisoning** — a thread panicked while holding the lock; data may be mid-mutation. `unwrap` propagates the panic; recover explicitly with `e.into_inner()` if you must.

**Lock hygiene:** keep critical sections tiny (compute outside, lock to swap); never hold a guard across `.await` (see ch. 12); acquire multiple locks in one fixed global order to dodge deadlocks — Rust prevents races, **not deadlocks**.

### RwLock — many readers or one writer

```rust
use std::sync::RwLock;
let config = Arc::new(RwLock::new(Config::default()));
let c = config.read().unwrap();      // many concurrent readers
let mut c = config.write().unwrap(); // exclusive
```

The runtime mirror of `&T`/`&mut T`. Wins over `Mutex` for read-heavy data; watch for writer starvation.

### Atomics — lock-free primitives

```rust
use std::sync::atomic::{AtomicU64, AtomicBool, Ordering};

static REQUESTS: AtomicU64 = AtomicU64::new(0);
REQUESTS.fetch_add(1, Ordering::Relaxed);            // perfect for counters/metrics

static SHUTDOWN: AtomicBool = AtomicBool::new(false);
SHUTDOWN.store(true, Ordering::Release);             // publish
while !SHUTDOWN.load(Ordering::Acquire) { /* work */ }   // observe
```

Orderings in one line each: `Relaxed` = just atomic, no cross-variable ordering (counters); `Acquire`/`Release` = paired publish/consume of *other* writes (flags, handoffs); `SeqCst` = single global order, safe default when unsure. Building lock-free structures beyond counters/flags is expert territory — use crossbeam.

## 11.4 Send and Sync — The Traits Behind the Magic

| Trait | Meaning | Intuition |
|---|---|---|
| `Send` | ownership can move to another thread | "safe to give away" |
| `Sync` | `&T` can be shared across threads (`T: Sync` ⟺ `&T: Send`) | "safe to look at together" |

- **Auto traits**: derived structurally — a type is Send/Sync iff all its fields are. You never implement them by hand (that's `unsafe`); you *lose* them by containing a non-Send/Sync field.
- Notable exceptions: `Rc<T>` (neither — non-atomic counter), `RefCell<T>` (Send but **not Sync** — borrow flag isn't atomic), raw pointers (neither, by default).
- `thread::spawn` requires `F: Send + 'static` — so sending an `Rc` across threads is a **type error**, with a compiler suggestion to use `Arc`. This is the entire "fearless" mechanism: thread-safety is encoded in types and checked like any other bound.

```
Send + Sync :  i32, String, Vec<T>, Arc<Mutex<T>>   → share & move freely
Send + !Sync:  RefCell<T>, mpsc::Receiver           → move it, don't share it
!Send + !Sync: Rc<T>, raw pointers                  → single thread only
```

## 11.5 Rayon — Data Parallelism in One Line

```rust
use rayon::prelude::*;

let sum: u64 = (0..10_000_000u64).into_par_iter().map(|x| x * x).sum();
let processed: Vec<_> = items.par_iter().map(expensive).collect();
v.par_sort();
```

Change `iter()` → `par_iter()` and rayon work-steals across a global thread pool. All the borrow rules still apply, so a data race remains impossible — if the closure captured something mutably shared, it wouldn't compile. Use rayon for **CPU-bound** batch work; channels/async for coordination and IO.

## 11.6 Choosing a Tool

| Situation | Reach for |
|---|---|
| Parallelize a big computation over a collection | `rayon` |
| Pipeline of stages, producers/consumers | channels |
| Small shared state (counters, flags) | atomics |
| Shared config, read-heavy | `Arc<RwLock<T>>` |
| Shared mutable structure | `Arc<Mutex<T>>` — keep sections short |
| Fork-join over borrowed data | `thread::scope` |
| Thousands of concurrent IO waits | async (next chapter) |

## 11.7 What Rust Does and Doesn't Prevent

✅ Prevented at compile time: data races, sending non-thread-safe types across threads, forgetting the lock, unlocking bugs, use-after-free across threads.

❌ Still your job: **deadlocks**, livelock, starvation, priority inversion, logical race conditions (TOCTOU at the application level), and channel backpressure design.
