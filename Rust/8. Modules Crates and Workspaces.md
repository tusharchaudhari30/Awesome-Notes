# 8. Modules Crates and Workspaces

## 8.1 The Hierarchy

```
Workspace  →  Package  →  Crate  →  Module  →  Items (fn, struct, trait, …)
(optional)    (Cargo.toml)  (compilation     (namespace +
                             unit)            privacy boundary)
```

- **Crate** = compilation unit. A package has at most one **library crate** (`src/lib.rs`) and any number of **binary crates** (`src/main.rs`, `src/bin/*.rs`).
- **Module** = namespace and privacy boundary *inside* a crate. Modules are about organization and visibility — they are **not** separate compilation units (unlike Java packages or Go packages).

## 8.2 Defining Modules

Three equivalent ways; the file-based ones are standard:

```rust
// 1. Inline (small stuff, tests)
mod network {
    pub fn connect() {}
    mod internal { pub fn helper() {} }
}

// 2. File: src/network.rs           ← mod network; in lib.rs
// 3. Directory: src/network/mod.rs  (older style)
//    or src/network.rs + src/network/tcp.rs (modern style)
```

```
src/
├── lib.rs          // crate root:  mod network;  mod storage;
├── network.rs      // contains:    pub mod tcp;  pub mod udp;
├── network/
│   ├── tcp.rs
│   └── udp.rs
└── storage.rs
```

**Key rule:** files do NOT automatically become modules. The module tree is built explicitly by `mod` declarations starting at the crate root (`lib.rs`/`main.rs`). A file never declared with `mod` is simply not compiled.

## 8.3 Paths and `use`

```rust
crate::network::tcp::connect();     // absolute path (from crate root)
self::helper();                     // current module
super::shared();                    // parent module
std::collections::HashMap           // external crate path

use crate::network::tcp;            // bring module in: tcp::connect()
use std::collections::{HashMap, HashSet};       // nested
use std::io::{self, Read};                      // io AND io::Read
use serde_json::Value as JsonValue;             // rename
pub use crate::network::tcp::connect;           // RE-EXPORT (see 8.5)
```

**Idiom:** import *functions'* parent module (`use std::fs;` → `fs::read_to_string(...)` — reads clearly), but import *types* directly (`use std::collections::HashMap;` → `HashMap::new()`). Avoid glob imports (`use x::*`) outside tests and preludes.

## 8.4 Visibility

Everything is **private by default** — visible only to its own module and descendants.

```rust
pub fn f() {}                  // visible wherever the parent module is visible
pub(crate) fn g() {}           // visible anywhere in THIS crate — the practical workhorse
pub(super) fn h() {}           // visible to parent module
pub(in crate::network) fn i() {}   // visible within a specific ancestor

pub struct Config {
    pub name: String,          // fields need their OWN pub
    secret: String,            // private field → outsiders can't construct Config literally
}

pub enum Status { Active, Idle }   // enum variants inherit the enum's visibility
```

**A private field makes the struct non-constructible from outside** — this is how you enforce invariants: expose a `pub fn new(...) -> Result<Config, E>` that validates, and the type can never exist in an invalid state. (To allow `..Default::default()`-style construction while keeping the option to add fields, see `#[non_exhaustive]`.)

## 8.5 API Design: Re-exports

Deep internal structure, flat public API:

```rust
// lib.rs
mod client; mod config; mod error;         // internal layout, private

pub use client::Client;                     // users write my_crate::Client
pub use config::{Config, ConfigBuilder};    // not my_crate::config::Config
pub use error::Error;
```

`pub use` decouples your file organization from your public interface — you can refactor internals freely without breaking users. Check what you're actually exporting with `cargo doc --open`.

## 8.6 Workspaces — Multi-Crate Repos

```toml
# Root Cargo.toml (no [package] — a "virtual manifest")
[workspace]
members = ["crates/core", "crates/api", "crates/cli"]
resolver = "2"

[workspace.dependencies]        # single source of truth for versions
serde = { version = "1", features = ["derive"] }
tokio = { version = "1", features = ["full"] }
```

```toml
# crates/api/Cargo.toml
[dependencies]
core = { path = "../core" }             # in-workspace dependency
serde = { workspace = true }            # inherit version from workspace
```

- One shared `Cargo.lock` and one `target/` directory → consistent versions, shared build cache.
- `cargo build -p api` / `cargo test --workspace` to target one crate or all.
- **When to split into a workspace:** compile-time isolation (touching the CLI shouldn't rebuild core), enforcing layering (api can depend on core, never the reverse — the dependency graph *is* the architecture), publishing crates separately, or sharing code between a lib and several binaries.

## 8.7 Feature Flags — Conditional Compilation

```toml
[features]
default = ["json"]                 # on unless user opts out (default-features = false)
json = ["dep:serde_json"]          # feature gates an optional dependency
metrics = []
full = ["json", "metrics"]

[dependencies]
serde_json = { version = "1", optional = true }
```

```rust
#[cfg(feature = "json")]
pub fn to_json(&self) -> String { /* ... */ }

#[cfg(test)]           mod tests { }          // cfg works for more than features:
#[cfg(target_os = "linux")] fn epoll() { }
#[cfg(debug_assertions)]    fn dev_only() { }
```

**Cardinal rule: features must be additive.** Cargo *unions* features across the whole dependency graph (if crate A wants `serde/derive` and crate B doesn't, everyone gets it) — so enabling a feature must never break or change behavior for other users, only add capabilities. "Mutually exclusive features" are a design bug.

## 8.8 Dependencies Beyond crates.io

```toml
[dependencies]
mylib = { path = "../mylib" }                                     # local
mylib = { git = "https://github.com/me/mylib", tag = "v0.3.0" }   # git (prefer tag/rev over branch)

[patch.crates-io]
serde = { path = "../serde-fork" }     # override transitively, everywhere in the graph
```

## 8.9 Semantic Versioning and Publishing

Cargo treats versions as semver: `1.2.3` → major.minor.patch, and **for `0.x` crates the minor position acts as major** (`0.8` → `0.9` is breaking).

Breaking changes (major bump) include: removing/renaming public items, adding fields to a public struct with all-public fields, adding trait methods without defaults, adding a *required* argument, bumping a public dependency's major version. Non-breaking: adding items, adding enum variants/struct fields **if** marked `#[non_exhaustive]`, adding defaulted trait methods.

```rust
#[non_exhaustive]                 // outsiders must use ..Default or a constructor,
pub struct Config { pub port: u16 }   // and match with a `_` arm → you can add fields/variants later
```

Publishing flow: `cargo login` → ensure `description`, `license`, `repository` in Cargo.toml → `cargo publish --dry-run` → `cargo publish`. Versions are **immutable** once published; `cargo yank` hides a version from new resolutions without deleting it.

## 8.10 Layout Conventions Recap

| Path | Meaning |
|---|---|
| `src/lib.rs` | library crate root — put logic here |
| `src/main.rs` | binary crate root — keep it a thin wrapper calling the lib |
| `src/bin/*.rs` | extra binaries |
| `tests/` | integration tests (each file its own crate, uses your lib as a dependency) |
| `examples/` | runnable examples, `cargo run --example x` |
| `benches/` | benchmarks |
| `build.rs` | build script (codegen, C compilation) run before your crate compiles |

**The lib + thin binary split** (`main.rs` just calls `mylib::run()`) is the standard structure: integration tests and other binaries can only exercise code that lives in the library crate.
