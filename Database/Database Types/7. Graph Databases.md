# 7. Graph Databases

> Neo4j, Amazon Neptune, ArangoDB, Memgraph; language: Cypher/Gremlin/SPARQL. For data where **relationships are the workload** — social graphs, fraud rings, recommendations, knowledge graphs, dependency/impact analysis. Their storage trick: make "follow an edge" a **pointer dereference (O(1))** instead of a join (O(log n) index probe per hop).

## 7.1 Data Model

- **Property graph:** vertices (nodes) and directed, typed edges (relationships), both carrying key-value properties. Labels group nodes (`:User`, `:Product`).

```cypher
(:User {name:'Tushar'})-[:FOLLOWS {since:2024}]->(:User {name:'Asha'})

// friends-of-friends up to 3 hops who bought product P:
MATCH (me:User {id:$id})-[:FOLLOWS*1..3]->(f)-[:BOUGHT]->(p:Product {id:$p})
RETURN DISTINCT f
```

- **Variable-length traversal** (`*1..3`) is the signature capability — in SQL this is recursive CTEs with exploding self-joins; here it's native.
- Alternative model: **RDF triple stores** (subject–predicate–object, SPARQL) for semantic/knowledge-graph interop.
- Schema-light: new edge/vertex types slot in without migrations → graphs evolve gracefully (good for heterogeneous connected data).

## 7.2 How They Store Data — Index-Free Adjacency (Neo4j)

- **Fixed-size records:** node store and relationship store are arrays of fixed-size records → a node's id × record-size = its disk offset (O(1) access, no index).
- Each **node record** points to its first relationship and first property; each **relationship record** holds pointers to source/target nodes *and* to the previous/next relationship in **each** node's relationship chain (doubly-linked lists threading through both endpoints).

```
[Node A] ──▶ rel-chain: (A─FOLLOWS─▶B) ⇄ (A─BOUGHT─▶P) ⇄ ...
                 each rel record: src, dst, type, next/prev per endpoint
Traversal = chase pointers.  No index probe per hop.
```

- **Consequence — the core performance claim:** traversing an edge costs O(1) regardless of total graph size; a join costs an index lookup that grows with table size and, worse, *joins compound per hop*. Multi-hop queries on graphs scale with the **size of the subgraph touched**, not the size of the database.
- Indexes exist only to find **entry points** (`User by id`) — after that, it's pointer-chasing.
- Native engines (Neo4j, Memgraph) vs **graph layers over other stores** (Neptune on a quad store, JanusGraph over Cassandra): layered ones scale storage more easily but pay index lookups per hop — always ask "is adjacency index-free?"

## 7.3 Performance Profile

| Operation | Character |
|---|---|
| Multi-hop traversal from an entry node | Excellent — milliseconds where SQL recursive joins take seconds/minutes |
| Pattern matching (cycles, triangles — fraud shapes) | Native strength |
| Entry-point lookup | Index (B-tree) like anywhere |
| Global scans/aggregations ("average age of all users") | Weak — wrong tool; export to columnar/graph-compute (Spark GraphX, Pregel-style) |
| **Supernodes** (celebrity with 10 M edges) | The classic hot spot — traversals through them explode; mitigate by edge-type partitioning, relationship sampling, or modeling around |
| Write throughput | Moderate — pointer surgery + ACID (Neo4j is fully transactional); not an ingestion engine |

## 7.4 Consistency & Scaling

- Neo4j: **ACID transactions**, single-leader clustering (Raft) — replicas scale *reads*; the graph itself resists sharding.
- **Partitioning a graph is fundamentally hard:** any cut severs edges → cross-partition traversals become network hops (the min-cut problem); this is *the* scaling weakness of the family. Approaches: application-level partition by natural community, Neo4j Fabric (federated graphs), or accept a scale ceiling.
- Distributed graph engines (Neptune, TigerGraph, JanusCassandra) trade index-free adjacency or latency for horizontal scale.

## 7.5 When to Choose / Avoid

**Choose when:** queries are ≥ 2–3 hops deep or variable-depth (friends-of-friends, "shortest path", "everything connected to X"), pattern detection (fraud rings, money-laundering cycles), recommendations via graph proximity, knowledge graphs/lineage/impact analysis, access-control graphs (Zanzibar-style).

**Avoid when:** relationships are shallow (1 hop = a foreign key — Postgres does that fine), workload is aggregate/scan-shaped, write-ingestion-heavy, or dataset must shard horizontally. Rule of thumb: **if every query starts `WHERE` and rarely says "via", you don't need a graph database.**

## 7.6 Interview Sound Bites

- "Index-free adjacency: each node physically points at its edges, so a hop is a pointer dereference — traversal cost tracks the subgraph you touch, not the data you store."
- "SQL joins compound per hop; graph traversals don't — that's the entire performance argument, and it only pays at depth ≥ 2–3."
- "Supernodes are the graph world's hot keys — the celebrity problem again, in pointer form."
- "Graphs shard badly because every cut severs edges — I scale reads with replicas and keep the graph on one logical instance as long as possible."
