# 10. Vector Databases

> pgvector, Pinecone, Milvus, Weaviate, Qdrant, Chroma; plus vector search inside Elasticsearch/OpenSearch/Redis. Store **embeddings** — high-dimensional float vectors that encode *meaning* — and answer "find the k most similar items" (**k-NN**) fast. The backbone of RAG, semantic search, recommendations, and deduplication.

## 10.1 Data Model

- Record = **id + vector (e.g., 384–3072 float32 dims) + metadata payload** (for filtering: `tenant_id`, `doc_type`, `date`).
- Similarity metric: **cosine similarity** (angle; the text-embedding default), dot product, or Euclidean distance — must match how the embedding model was trained.
- The DB never creates meaning: an **embedding model** (OpenAI/Cohere/sentence-transformers) maps text/images → vectors; nearby vectors ≈ similar meaning. Change the model → **re-embed and rebuild the index** (vectors from different models are incomparable).

## 10.2 The Core Problem — and How They Store Data

- Exact k-NN = compare against *every* vector: O(n·d) per query — fine to ~100 K vectors (brute force on SIMD is underrated), hopeless at 100 M.
- Answer: **ANN (approximate nearest neighbor)** indexes — trade a little **recall** (fraction of true neighbors found) for orders-of-magnitude speed.

### HNSW — Hierarchical Navigable Small World (the default)

```
Layer 2:   few nodes, long-range links      ── enter here, greedy-hop toward query
Layer 1:   more nodes, medium links                    │ descend
Layer 0:   ALL vectors, short links         ── refine to true neighborhood, return top-k
```

- A multi-layer **proximity graph** (skip-list spirit): search greedily walks toward the query vector, descending layers → **O(log n)-ish** search, recall ~95–99 %.
- Knobs: `M` (links per node — memory), `efConstruction` (build quality), `efSearch` (recall vs latency at query time).
- Costs: the graph (and usually vectors) lives **in RAM** — memory-hungry; inserts fine, **deletes/updates degrade the graph** (tombstone + periodic rebuild).

### IVF — inverted file (cluster-based)

- k-means the vectors into `nlist` cells; query probes only the nearest `nprobe` cells. Less RAM, faster build; recall cliff if the true neighbor sits in an unprobed cell. Often combined with compression → IVF-PQ.

### Quantization (compression for vectors)

- **PQ (product quantization):** split vector into subvectors, replace each with a codebook id → 10–100× smaller, approximate distances in compressed space; **SQ** (float32→int8, 4×); **binary/Matryoshka** embeddings shrink further. Standard recipe at scale: **IVF-PQ or HNSW-on-quantized + re-rank the top candidates with full-precision vectors** (DiskANN-style for SSD-resident billions).

### Metadata filtering — the sleeper difficulty

- "Nearest neighbors *where* tenant_id=42" is hard: **post-filtering** (search then filter — may return < k), **pre-filtering** (restrict candidate set — breaks graph connectivity if selective). Real engines do filter-aware graph traversal; filtering behavior is a top evaluation criterion when picking an engine.

## 10.3 Performance Profile

| Operation | Character |
|---|---|
| Top-k similarity (HNSW, RAM) | ~1–10 ms for millions of vectors, recall ~95 %+ |
| Brute-force exact | Fine small-scale; linear death beyond ~10⁵–10⁶ |
| Insert stream | OK (HNSW incremental); index build for IVF is batch |
| Delete/update heavy | Weak spot — graph decay, periodic rebuilds |
| Filtered search (selective filter) | The stress test — measure recall, not just latency |
| Memory | The cost driver: e.g., 10 M × 1536 dims × 4 B ≈ 60 GB + graph overhead → quantize or pay |

## 10.4 Consistency & Scaling

- Shard by id-hash; replicate for reads; ANN results are already approximate, so eventual consistency of the index is usually acceptable — freshness SLA (when does a new doc become findable?) matters more than linearizability.
- Same **derived data** doctrine: source documents live in the system of record; embeddings + index are rebuildable artifacts of (data × embedding-model-version). Version them together.

## 10.5 RAG & Hybrid Search (usage patterns)

- **RAG pipeline:** chunk documents → embed chunks → store (vector + metadata + text) → at query time embed the question → top-k similar chunks → feed as LLM context. Chunking strategy and metadata filters affect quality more than the engine choice.
- **Hybrid search = BM25 (Ch. 9) + vector similarity**, fused (e.g., reciprocal rank fusion) — lexical catches exact terms/ids, semantic catches paraphrase; the production default, often + a cross-encoder **re-ranker** on the fused top-50.
- **pgvector rule of thumb:** < ~1–10 M vectors and you already run Postgres → pgvector (HNSW index in an extension) keeps vectors next to relational data, transactionally. Dedicated engines earn their ops cost at larger scale, high QPS, or hard filtering needs.

## 10.6 Interview Sound Bites

- "Vector DBs answer 'what's *similar*', not 'what's *equal*' — the index is an ANN structure trading recall for logarithmic search."
- "HNSW is a skip-list over a proximity graph: enter sparse, hop greedily, descend, refine."
- "Memory math first: vectors × dims × 4 bytes; then quantize (PQ/int8) and re-rank top candidates at full precision."
- "Filtered ANN is the hidden hard problem — pre-filter breaks the graph, post-filter breaks k; ask any engine how it handles selective filters."
- "Embeddings are derived data keyed by model version: change the model, rebuild the world."
