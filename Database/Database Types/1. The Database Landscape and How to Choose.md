# 1. The Database Landscape and How to Choose

> "Which database?" is really three questions: what **shape** is the data (model), how is it **stored and indexed** (engine → performance profile), and how does it **scale and fail** (distribution). This chapter maps the landscape; each following chapter dissects one family — how it stores data on disk, what that costs, and when to pick it.

## 1.1 The Taxonomy

| Family | Data model | Canonical storage engine | Examples | Chapter |
|---|---|---|---|---|
| Relational (OLTP) | Tables, rows, joins | B-tree, row-oriented, WAL, MVCC | PostgreSQL, MySQL, Oracle | 2 |
| Key-Value | key → opaque value | Hash table (RAM) or LSM | Redis, Memcached, DynamoDB | 3 |
| Document | key → JSON/BSON document | B-tree over documents | MongoDB, CouchDB, Firestore | 4 |
| Wide-Column | (partition key, clustering cols) → columns | LSM-tree | Cassandra, ScyllaDB, HBase | 5 |
| Columnar (OLAP) | Tables stored column-wise | Compressed column segments | ClickHouse, Redshift, BigQuery, Snowflake | 6 |
| Graph | Vertices + edges | Adjacency lists / index-free adjacency | Neo4j, Neptune | 7 |
| Time-Series | (series, timestamp) → measurements | Time-partitioned columnar/LSM | InfluxDB, TimescaleDB, Prometheus | 8 |
| Search Engine | Documents → inverted index | Immutable segments, postings lists | Elasticsearch, OpenSearch | 9 |
| Vector | Embeddings → nearest-neighbor index | HNSW / IVF graphs & quantization | pgvector, Pinecone, Milvus | 10 |
| NewSQL / Distributed SQL | Tables + SQL over global shards | LSM + Raft per shard | Spanner, CockroachDB, TiDB | 11 |

## 1.2 The Three Deciding Axes

### Axis 1 — Data model (what are the relationships?)
- Self-contained aggregates → document. Many-to-many everywhere → relational. Relationship-traversal *is* the workload → graph. Value opaque to the DB → key-value.

### Axis 2 — Storage engine (what's the read/write profile?)
The engine choice explains almost every performance claim (details in System Design → Storage and Retrieval):
- **B-tree** (update-in-place, page-oriented): balanced read/write, predictable latency, great range scans and secondary indexes. The relational default.
- **LSM-tree** (append + compact): the write-throughput champion; reads pay amplification (memtable + SSTables + Bloom filters); compaction can spike p99. The NoSQL-at-scale default.
- **Hash-in-RAM:** microsecond point lookups, no range queries. Caches.
- **Column segments** (compressed, immutable, bulk-written): scan millions of rows/sec for a few columns; terrible at point updates. Analytics.
- **Inverted index:** term → documents. Relevance search; near-real-time (not instant) visibility.

### Axis 3 — Distribution (how does it scale and fail?)
- Single node + replicas (most RDBMS): simple, strong transactions, vertical ceiling.
- Hash-partitioned + leaderless/multi-leader (Cassandra, Dynamo): linear write scaling, tunable/eventual consistency.
- Range-sharded + consensus per shard (Spanner, CockroachDB, TiDB, HBase): horizontal scale *with* strong consistency, paying consensus latency.

## 1.3 Decision Flow (interview-speed)

```
Need ACID transactions across entities / ad-hoc joins?  ──▶ Relational (2)
  └─ outgrown one node but still need SQL+ACID?         ──▶ Distributed SQL (11)
Massive write throughput, key-addressed, multi-DC?      ──▶ Wide-column (5)
Sub-ms lookups, cache, counters, sessions?              ──▶ Key-value in-memory (3)
Flexible/nested schema, aggregate-per-request?          ──▶ Document (4)
Analytics over billions of rows, few columns?           ──▶ Columnar OLAP (6)
Multi-hop relationship queries?                         ──▶ Graph (7)
Metrics/IoT: time-stamped append + retention windows?   ──▶ Time-series (8)
Relevance-ranked / fuzzy / faceted text?                ──▶ Search engine (9)
Semantic similarity over embeddings?                    ──▶ Vector (10)
```

## 1.4 Polyglot Persistence — the Real-World Answer

Production systems combine stores, with **one system of record** and the rest as **derived data** kept in sync via CDC/streams (System Design → Stream Processing):

```
            ┌────────── CDC / outbox ──────────┐
PostgreSQL ─┤──▶ Redis (cache)                 │  source of truth: relational
 (truth)    ├──▶ Elasticsearch (search)        │  everything else: rebuildable
            └──▶ ClickHouse (analytics)        ▼  followers of the changelog
```

**Rules of thumb:**
- Start with PostgreSQL. It's the best default: transactions, `jsonb` documents, full-text search, pgvector — you may not need a second database for a long time.
- Add a specialized store only when a *measured* access pattern demands it, and add it as derived data, not a second source of truth.
- Every extra store = another consistency boundary, another operational surface, another failure mode.

## 1.5 Vocabulary You'll Reuse All Notes Long

- **Write/read/space amplification** — extra physical work per logical operation (LSM compaction, B-tree page writes, index copies).
- **Working set** — the hot fraction of data; if it fits in RAM (buffer pool/page cache), disk layout matters less.
- **Point read / range scan / scatter-gather** — the three query shapes; each store is optimized for some and pathological at others.
- **Tunable consistency** — per-request consistency levels (quorums) in leaderless stores.
- **Schema-on-write vs schema-on-read** — where structure is enforced.
