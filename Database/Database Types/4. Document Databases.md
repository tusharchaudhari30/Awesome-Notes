# 4. Document Databases

> MongoDB, CouchDB, Firestore, Couchbase. Store **self-contained JSON/BSON documents** addressed by id, with secondary indexes and rich queries over their fields. The pitch: your aggregate (order + items + address) is *one* record — one read, one write, no joins, no ORM impedance mismatch.

## 4.1 Data Model

- Collections of documents; each document a nested tree (objects, arrays) with flexible, per-document schema (**schema-on-read**).
- Model for **locality**: embed what you read together ("data that is accessed together should be stored together"); reference what is shared or unbounded.

| Embed | Reference |
|---|---|
| 1-to-few, read with parent (order items) | Many-to-many (products ↔ orders) |
| Bounded growth | Unbounded arrays (comments on a viral post) |
| Child meaningless alone | Child queried independently |

- Anti-patterns: unbounded array growth (documents rewritten, 16 MB cap in MongoDB), deep nesting you must query into, treating it as relational (join-shaped schemas without join support).

## 4.2 How They Store Data (MongoDB/WiredTiger)

- Documents serialized as **BSON** (typed, traversable binary JSON) and stored in **WiredTiger**, a **B-tree** engine: collections and each index are B-trees; leaf pages hold full documents.
- **Journal (WAL)** for durability + periodic **checkpoints**; **block compression** (snappy/zstd — JSON's repetitive field names compress well; at scale, shorten hot field names or accept the trade).
- **Concurrency:** document-level locking with MVCC-style snapshots in WiredTiger.
- **Updates rewrite the document** (or a leaf page of it): the locality dividend on reads is paid on writes — growing documents are the classic performance bug.
- **Indexes:** secondary B-trees on any field, including **inside nested objects and arrays** (multikey indexes — one index entry per array element), compound, TTL, partial, text, geo. Same rules as relational: leftmost prefix, write amplification per index, covered queries.
- CouchDB contrast: append-only B-tree + MVCC revisions, conflict-tolerant multi-master replication (offline-first pedigree).

## 4.3 Performance Profile

| Operation | Character |
|---|---|
| Read whole document by id / indexed field | Excellent — one B-tree descent, aggregate arrives in one I/O |
| Query on indexed nested/array field | Good (multikey B-tree) |
| Unindexed field query | Full collection scan — same disease as SQL, easier to catch late because schema didn't force thinking |
| Update small field in big document | Deceptively costly — document (page) rewrite + all affected indexes |
| Joins (`$lookup`) | Exists, but no optimizer heritage — poor at scale; embedding is the intended answer |
| Aggregation pipeline | Capable (group/project/unwind), but analytics at scale still → columnar store |

## 4.4 Consistency & Transactions

- Single-document writes are **atomic** — and because the aggregate *is* one document, this covers most business operations that would need a multi-row transaction in SQL. This is the core design trick of the model.
- MongoDB: multi-document ACID transactions exist (replica set/sharded) but cost more and signal your schema may be fighting the model.
- **Replica sets:** single-leader (primary) with automatic elections (Raft-like); tunable `writeConcern` (`majority` = survives failover) and `readConcern`/`readPreference` (secondary reads = replication-lag anomalies — see System Design → Replication).

## 4.5 Scaling Story

- **Sharding** built in: choose a **shard key** (hashed → uniform, no ranged queries; ranged → range queries, hot-spot risk) — same trade-offs as System Design → Partitioning. Config servers hold the map; `mongos` routes; queries without the shard key = scatter/gather.
- Shard-key mistakes are the #1 MongoDB-at-scale war story: low-cardinality or monotonically-increasing keys create jumbo chunks and hot shards.

## 4.6 When to Choose / Avoid

**Choose when:** aggregate-shaped access (fetch/store a whole entity per request — user profiles, catalogs, CMS content, event payloads), heterogeneous/evolving schemas, rapid iteration where migrations hurt, hierarchical data read as a unit.

**Avoid when:** many-to-many relationships dominate (you'll rebuild joins in app code), cross-entity invariants need multi-record transactions constantly, heavy ad-hoc analytics, or strong schema governance is a feature (relational constraints are your friend).

**Note:** PostgreSQL `jsonb` covers "some documents inside a relational app" surprisingly far (GIN indexes, full SQL around it); choose a document *database* when the document model is the primary model, not a garnish.

## 4.7 Interview Sound Bites

- "Document DBs turn the multi-row transaction into a single atomic document write — that's the model's core trick, and it works exactly when your aggregate boundaries are right."
- "Locality is a loan: one read fetches everything, but every update rewrites the document — unbounded array growth is how it defaults."
- "Schema-on-read doesn't remove the schema; it moves enforcement into every reader's code."
- "Sharding MongoDB is easy; picking the shard key is the actual design decision — hashed for uniformity, ranged for range queries, and cardinality above all."
