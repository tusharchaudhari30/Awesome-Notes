# 8. Time-Series Databases

> InfluxDB, TimescaleDB, Prometheus, QuestDB, VictoriaMetrics. For data that is **append-only, timestamp-keyed, arrives in relentless volume, is queried by time range + aggregation, and ages out**. A TSDB is what you get when you co-design storage around exactly those five facts: time-partitioned chunks, per-series columnar layout, wicked timestamp/value compression, and retention as a first-class operation.

## 8.1 Data Model

```
measurement:  cpu_usage
tags (indexed identity):     host=web-01, region=ap-south, core=0     → series identity
fields (values, unindexed):  usage=87.3, iowait=2.1
timestamp:                   1754300000000
```

- A **series** = measurement + unique tag combination. Queries slice by tags and time, then aggregate: `avg(usage) by region, 5m window, last 24h`.
- **Cardinality is the resource that matters:** total series count = product of tag values. Putting an unbounded value (user_id, request_id, container hash) in a *tag* explodes the series index — the #1 way people kill a TSDB ("cardinality explosion").
- TimescaleDB variant: ordinary SQL tables (a "hypertable") auto-partitioned by time — full SQL/joins retained.

## 8.2 How They Store Data

### Time partitioning (chunks)

- Data physically split into **time-bounded chunks** (e.g., 1 day). Effects:
  - Queries prune to relevant chunks (`WHERE time > now()-1h` touches one chunk).
  - **Retention = drop the chunk** — O(1) file deletion instead of millions of row deletes (and no tombstone problem).
  - Recent chunk stays hot in memory (writes are always to "now"); old chunks compress and cool.

### Per-series columnar layout + compression

- Within a chunk, each series' timestamps and values are stored as **contiguous columns** — enabling the specialized encodings (the Facebook **Gorilla** paper's tricks, used by Prometheus/Influx):
  - **Timestamps — delta-of-delta:** regular intervals (every 10 s) make second-order deltas ≈ 0 → ~1–2 bits each.
  - **Float values — XOR encoding:** consecutive sensor values are similar; XOR of consecutive floats has long zero runs → store only the changed bits.
  - Integers: delta + zigzag + varint; strings: dictionary.
- Net: **~1–2 bytes per data point** vs ~16+ raw — 10× more history in RAM/disk, 10× faster scans.
- Write path is LSM-flavored: WAL → in-memory recent block → flush immutable compressed chunks → background compaction (Influx TSM, Prometheus head block + 2h blocks).
- **Inverted index on tags** (label index) maps tag=value → series ids → the cardinality bill lives here.

### Continuous aggregates / downsampling

- Precompute rollups (1s → 1m → 1h) via continuous queries/recording rules; keep raw data briefly, rollups for years. Dashboards hit rollups — this is the standing performance answer.

## 8.3 Performance Profile

| Operation | Character |
|---|---|
| Ingest | Millions of points/s/node (append + columnar batch + WAL) |
| Range query on few series, recent data | Excellent — chunk-pruned, in-memory, compressed scans |
| Aggregation across many series | Good if pre-aggregated (rollups); costly ad-hoc across high cardinality |
| Point update / delete of old rows | Anti-pattern — chunks are immutable; out-of-order writes cost extra (buffering/merge) |
| Query by unindexed field value | Scan — fields aren't indexed by design |
| Cardinality growth | The scaling cliff — series index RAM/CPU, slow tag queries |

## 8.4 Consistency & Scaling

- Typically single-leader or per-shard leadership; durability via WAL; replication async (metrics tolerate small loss; billing-grade series need care).
- Scale-out: shard by series (hash of measurement+tags) and/or by time; query layer scatter-gathers (VictoriaMetrics/Thanos/Mimir for Prometheus federate this).
- Prometheus model note: **pull-based scraping**, local storage, remote-write to long-term stores — monitoring architecture, not a general TSDB.

## 8.5 When to Choose / Avoid

**Choose when:** metrics/observability, IoT/sensor telemetry, financial ticks, fleet/vehicle tracking, any "append now, aggregate by time window, expire later" workload — at volumes where a B-tree table + DELETE-based retention falls over.

**Avoid when:** data is updated in place, queried by non-time predicates primarily, low-volume (Postgres + a timestamp index is fine), or series identity is unbounded (rethink the model first — move identity to fields/logs).

**TimescaleDB vs Influx-style rule:** need SQL/joins with relational data → Timescale; standalone metrics pipeline at max ingest → purpose-built TSDB.

## 8.6 Interview Sound Bites

- "A TSDB is co-designed around five facts: append-only, time-keyed, high-volume, range-aggregated, expiring. Every internal follows."
- "Gorilla compression — delta-of-delta timestamps, XOR floats — gets a data point to ~1–2 bytes; that's why a year of metrics fits."
- "Retention is `DROP CHUNK`, not `DELETE WHERE` — O(1) instead of tombstone hell."
- "Tags are identity, fields are data: put an unbounded id in a tag and the series index explodes — cardinality is the real capacity limit."
- "Dashboards read rollups, not raw points — continuous aggregates are the standing answer to slow range queries."
