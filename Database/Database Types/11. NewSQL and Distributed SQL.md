# 11. NewSQL and Distributed SQL

> Google Spanner, CockroachDB, TiDB, YugabyteDB. The promise: **SQL + ACID transactions + horizontal scale + survive-a-region availability** — the combination the 2000s said you couldn't have. The recipe underneath is remarkably consistent: **range-shard the keyspace, run consensus (Raft/Paxos) per shard, store in LSM engines, and coordinate transactions with 2PC made non-blocking by consensus + smart timestamps.**

## 11.1 Why This Category Exists

- Relational DBs (Ch. 2) hit a single-node write ceiling; manual sharding loses cross-shard joins, transactions, and sanity.
- NoSQL (Ch. 3/5) scaled by *dropping* transactions and joins — and a decade of application-level workarounds (saga spaghetti, dual writes) showed how expensive that is.
- NewSQL puts the guarantees back *on top of* the NoSQL-style distribution machinery.

## 11.2 How They Store Data

### Ranges + Raft groups

```
Table rows → sorted key space → split into ranges (~64–512 MB)
Each range = one Raft group of 3/5 replicas across nodes/zones/regions
   [range A: leader n1, followers n2,n3]  [range B: leader n2, ...]  ...
Writes to a range go through its Raft leader → majority commit → applied to LSM (RocksDB)
```

- **Range partitioning** (sorted, like HBase — not hash): preserves range scans and lets ranges **split/merge/rebalance** dynamically; leaders spread across nodes so write load distributes.
- **Storage engine per node: RocksDB/Pebble (LSM)** — the write-optimized engine under the SQL veneer; MVCC implemented as timestamped versions of each key inside the LSM.
- The SQL layer compiles queries into distributed plans over range leaders (pushdown of filters, distributed joins); secondary indexes are just another keyspace of ranges (globally consistent, unlike Cassandra's local indexes).

### Distributed transactions

- **2PC over Raft groups:** each participant range durably logs its prepare via consensus → the classic "coordinator dies, everyone blocks" failure of 2PC (System Design → Transactions) disappears because *every* decision is replicated; a new leader finishes the protocol.
- **Ordering via timestamps:**
  - **Spanner — TrueTime:** GPS/atomic-clock-backed bounded clock uncertainty; transactions **commit-wait** out the uncertainty interval → **external consistency** (strict serializability) globally.
  - **CockroachDB/TiDB — no atomic clocks:** hybrid logical clocks + NTP bounds, transaction restarts on uncertain reads (CRDB, serializable), or a **central timestamp oracle** (TiDB/Percolator model, snapshot isolation).
- Reads: leaseholder/leader reads avoid consensus round trips; **follower/stale reads** offered as an explicit, cheaper option.

## 11.3 Performance Profile

| Operation | Character |
|---|---|
| Single-range transaction (good locality) | A Raft majority round trip — ~1–10 ms intra-region; solid |
| Cross-region write | Physics: majority ack across regions → tens–hundreds of ms (+ commit-wait on Spanner) |
| Cross-shard transaction | 2PC + consensus per participant — works, costs multiples of single-range |
| Range scan | Good (sorted ranges) — but sequential keys hot-spot the tail range (same HBase lesson: avoid monotonic PKs or use hash-sharded indexes) |
| Contended row (hot counter) | Serialized through one Raft leader + transaction retries — no better than Postgres, sometimes worse |
| Read scaling | Excellent (follower reads, more nodes) |
| Analytics | TiDB's answer: **TiFlash columnar replicas (HTAP)** — Raft-replicated column copies for OLAP alongside row OLTP |

**The honest framing:** you pay a **latency tax on every write** (consensus) to buy scale-out and availability. If your data fits one beefy Postgres with replicas, that's faster and simpler.

## 11.4 Operational & Consistency Properties

- Default isolation: serializable (CockroachDB), snapshot (TiDB), external consistency (Spanner) — dramatically stronger than most sharded-MySQL setups.
- Survivability: lose a node/zone/region (with the right replica placement) with **no data loss (RPO=0)** and automatic failover (Raft re-election in seconds).
- Geo-partitioning: pin rows' replica homes to regions (EU data in EU — latency *and* compliance).
- Ops: mostly self-healing rebalancing; the hard parts are hot ranges, transaction retry storms under contention, and understanding EXPLAIN plans that span the cluster.

## 11.5 When to Choose / Avoid

**Choose when:** you need relational semantics *and* one of: write volume beyond a single node, multi-region active-active with RPO=0, regulatory geo-placement, or elastic scale without re-sharding projects. Sweet spots: payments/ledgers at scale, global inventory, SaaS control planes, metadata stores.

**Avoid when:** a single node + replicas suffices (most apps!), ultra-low-latency single-region writes are critical (consensus tax), heavy analytics is the real problem (→ Ch. 6), or the team can't absorb distributed-systems operability. Migration nuance: SQL compatibility ≠ performance compatibility — schema/keys must be re-thought for ranges and hot spots.

## 11.6 Interview Sound Bites

- "NewSQL = range-sharded keyspace, a Raft group per range, LSM underneath, 2PC on top — with consensus making 2PC non-blocking."
- "Spanner's trick is TrueTime: bound clock uncertainty with hardware, then *wait it out* at commit — global strict serializability from clocks."
- "Every write costs a majority round trip; that's the entry fee for RPO=0 and scale-out — don't pay it if one Postgres box fits."
- "Monotonic primary keys hot-spot the last range — the auto-increment habit dies in range-sharded systems."
- "TiDB's HTAP move: columnar Raft replicas (TiFlash) so OLAP reads never touch the OLTP path."
