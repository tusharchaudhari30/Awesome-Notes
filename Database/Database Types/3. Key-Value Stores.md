# 3. Key-Value Stores

> The simplest data model — `get(key)`, `put(key, value)`, value opaque to the database — which is exactly why they're the fastest. Two very different species share the name: **in-memory** stores (Redis, Memcached: microsecond latency, cache-shaped) and **durable distributed** KV stores (DynamoDB, Riak, etcd: partitioned, replicated, SLA-shaped).

## 3.1 Data Model

- Key (string/bytes) → value (bytes or typed structures). No joins, no secondary access paths (unless bolted on), no schema.
- **You can only query by key** → the data model exercise is *key design*: `user:42:profile`, `session:<token>`, composite keys encoding the lookup pattern.
- Redis extends values to **data structures**: strings, hashes, lists, sets, **sorted sets (ZSET)**, streams, HyperLogLog, bitmaps, geo — each with O(1)/O(log n) operations server-side. This is Redis's real superpower: the *operations*, not just storage (leaderboard = ZSET, rate limiter = INCR+EXPIRE, queue = LIST/Streams).

## 3.2 How They Store Data

### In-memory (Redis, Memcached)

- Primary structure: **hash table in RAM** → O(1) lookups, ~100 K+ ops/s/core, sub-ms (often µs) latency. Redis is (mostly) **single-threaded** — no locks, no context switches; commands are atomic by construction (I/O threads and Memcached's multithreading vary the theme).
- **Redis durability options** (see Redis notes for depth):
  - **RDB** snapshots — fork + copy-on-write dump; fast restarts, lose last minutes on crash.
  - **AOF** append-only command log (fsync every write/every second) — better durability, bigger files, rewrite compaction.
  - Common production stance: cache-only (no persistence) or RDB+AOF hybrid; **never treat cache-mode Redis as a system of record.**
- Memory is the budget: eviction policies (LRU/LFU approximations, TTL) make it a cache; `maxmemory` + eviction policy is the most important config line.

### Durable distributed (DynamoDB, Riak, Voldemort)

- Values stored in **LSM/B-tree engines on SSD**, **hash-partitioned** across nodes (consistent hashing), replicated N ways (leaderless or leader-per-partition).
- DynamoDB specifics worth knowing: partition key (+ optional sort key → range queries *within* a partition, Cassandra-style); throughput per partition is capped → hot partition = throttling; **GSIs** are asynchronously maintained global secondary indexes (eventually consistent); single-digit-ms SLA at any scale; DAX for a caching layer.

## 3.3 Performance Profile

| | In-memory (Redis) | Distributed KV (DynamoDB) |
|---|---|---|
| Point read | ~0.1–1 ms (µs in-process of DC) | ~1–10 ms, flat *at any scale* |
| Throughput | 100 K+ ops/s/node | Effectively unlimited (pay per partition throughput) |
| Range queries | Only via structures (ZSET) / SCAN | Only within a partition (sort key) |
| Ceiling | RAM size, single-thread CPU for hot commands | Hot partitions, item size limits (400 KB) |
| Durability | Optional, configurable, weaker | Replicated, durable by default |

**Performance traps:** big keys (multi-MB values block the single thread), `KEYS`/full scans in production, hot keys (one partition/shard takes all traffic → key-splitting or local caching), fan-out `MGET` across a cluster, treating TTL expiry as precise (it's lazy+sampled).

## 3.4 Consistency & Transactions

- Redis: atomic single commands; MULTI/EXEC batches and Lua scripts for atomic multi-step logic on one node; **no rollback**, cross-slot transactions unsupported in cluster mode. Replication is async → failover can lose acknowledged writes (see Redis notes: Sentinel/Cluster).
- DynamoDB: per-item strong or eventual reads (your choice per request); `TransactWriteItems` for limited multi-item ACID; conditional writes (CAS) are the idiomatic concurrency tool.
- Dynamo-style leaderless (Riak): quorum R/W tuning, version vectors, siblings (System Design → Replication).

## 3.5 Scaling Story

- **Redis Cluster:** 16,384 hash slots spread over shards; client-side routing (MOVED/ASK); multi-key ops must share a slot (hash tags `{user:42}`). Replicas per shard + automatic failover.
- **Memcached:** dumb-but-effective — client-side consistent hashing, no server coordination at all.
- **DynamoDB:** fully managed auto-partitioning; your only lever is key design (spread load, avoid hot partitions) and capacity mode (on-demand vs provisioned).

## 3.6 When to Choose / Avoid

**Choose when:** caching (the #1 use), sessions, rate limiting, leaderboards/counters, feature flags, distributed locks (with care + fencing), pub/sub signaling; or (DynamoDB-style) massive-scale key-addressed data with tight latency SLAs and known access patterns.

**Avoid when:** ad-hoc queries, relationships/joins, large scans, evolving access patterns you can't predict — query-by-key-only is a straitjacket unless the access pattern is truly fixed.

## 3.7 Interview Sound Bites

- "A KV store moves the query planning into *key design* — you decide every access path at write time."
- "Redis is fast because it's a hash table in RAM behind a single thread — atomic by construction, and the same thread is why one big key can stall everyone."
- "Cache-mode Redis is not a database: async replication plus eviction means acknowledged data can vanish."
- "DynamoDB gives flat single-digit-ms latency at any scale, but the contract is: know your access patterns up front and design keys so no partition is hot."
