# 5. Wide-Column Stores

> Cassandra, ScyllaDB, HBase, Bigtable. Despite the name, these are **not** columnar/OLAP databases — they're partitioned row stores whose rows can each have many (sparse) columns, built on **LSM-trees** for extreme write throughput and on **hash partitioning + replication** for linear horizontal scale. The model in one sentence: *a two-level map — partition key → (clustering key → columns) — physically sorted within each partition.*

## 5.1 Data Model (Cassandra/CQL)

```sql
CREATE TABLE messages (
  conversation_id uuid,        -- PARTITION KEY: which node(s), hash-distributed
  message_id      timeuuid,    -- CLUSTERING KEY: sort order *within* partition
  author          text,
  body            text,
  PRIMARY KEY ((conversation_id), message_id)
) WITH CLUSTERING ORDER BY (message_id DESC);
```

- **Partition key** → hashed → placement (uniform load, no cross-partition ordering). **Clustering columns** → on-disk sort within the partition → efficient "range scan within a key" (`WHERE conversation_id=? AND message_id > ?`).
- **Query-first modeling:** you design one table per query pattern and **denormalize freely** (disk is cheap, writes are cheap; joins don't exist). Need messages by author too? Second table, written in parallel.
- Rows are sparse — absent columns cost nothing; wide partitions can hold many thousands of rows (but keep partitions < ~100 MB / low millions of rows; unbounded partitions are the classic modeling failure — bound them, e.g., bucket by day: `((sensor_id, day), ts)`).

## 5.2 How They Store Data — LSM Machinery

Full LSM mechanics in System Design → Storage and Retrieval; Cassandra specifics:

```
write ──▶ commit log (append, fsync) ──▶ memtable (sorted by key)
                                            │ flush
                                            ▼
                             immutable SSTables + Bloom filters + partition index
                                            │ background compaction (size-tiered / leveled / time-window)
```

- **Writes never read** — an update/insert is just an append with a timestamp; newest timestamp wins at read/compaction. This is why write latency is flat and throughput enormous.
- **Deletes are writes:** a **tombstone** marker; the data physically dies at compaction after `gc_grace_seconds` (kept long enough for repair to spread the tombstone — or deleted data resurrects). **Tombstone pile-ups** (queue-like workloads, repeated overwrite/delete) poison read latency — the famous "don't build a queue on Cassandra" rule.
- **Reads:** memtable + (Bloom-filtered) SSTables merged by timestamp → read amplification grows with SSTables-per-read; compaction strategy is the knob (leveled = read-optimized, size-tiered = write-optimized, TWCS = time-series).
- HBase/Bigtable contrast: same LSM ideas but **range-partitioned** (sorted regions, master-assigned) on HDFS/Colossus, single-leader per region → strong per-row consistency, global sort order, hot-spotting risk on sequential keys.

## 5.3 Distribution & Consistency (Cassandra)

- **Leaderless, masterless ring:** consistent hashing with vnodes; replication factor (RF=3 typical), any node coordinates any request; multi-datacenter replication is first-class.
- **Tunable consistency per query:** `ONE` / `QUORUM` / `LOCAL_QUORUM` / `ALL` for both reads and writes; W+R > RF ⇒ overlap (see System Design → Replication). Sloppy details: hinted handoff, read repair, anti-entropy repair (Merkle trees) — **you must run repairs**.
- Conflicts resolved by **last-write-wins on cell timestamps** → clock skew can silently drop writes; lightweight transactions (Paxos-based CAS) exist but are expensive — if you need them often, wrong database.
- No joins, no foreign keys, secondary indexes are local (scatter/gather) — use denormalized tables or materialized views instead.

## 5.4 Performance Profile

| Operation | Character |
|---|---|
| Write | Superb — sub-ms, linearly scalable, flat under load (append-only) |
| Point read / partition range read | Good (ms) with healthy compaction; single-partition queries only |
| Multi-partition query / scan | Bad by design — scatter to all nodes; that's a modeling error or a Spark job |
| Tail latency | Compaction, GC (JVM Cassandra), tombstones → p99 spikes; ScyllaDB (C++, shard-per-core) exists precisely for this |
| Scale | Linear with node count; petabytes and millions of writes/s in production fleets |

## 5.5 When to Choose / Avoid

**Choose when:** write-heavy, key-addressed, time-ordered-within-key data at scale — messaging/feeds, IoT and metrics ingestion, activity/audit logs, "inbox" patterns; multi-DC active-active; availability over strong consistency.

**Avoid when:** ad-hoc queries or evolving access patterns (schema is frozen per query), transactions/invariants across rows, small datasets (operational overhead dwarfs benefit), queue-like delete-heavy workloads (tombstones).

## 5.6 Interview Sound Bites

- "Wide-column = two-level map: hash the partition key for placement, sort by clustering key within — 'all messages for this conversation, newest first' is one node, one range scan."
- "Writes never read — that's the whole speed secret, and its costs are read amplification and tombstones."
- "Cassandra deletes are writes; compaction is the real delete. Queue-shaped workloads turn reads into tombstone archaeology."
- "It's LWW on cell timestamps under the hood — clock skew is a silent write-loss risk, so I avoid designs where concurrent writes to the same cell matter."
- "Model rule: one table per query, denormalize on write, and bound every partition."
