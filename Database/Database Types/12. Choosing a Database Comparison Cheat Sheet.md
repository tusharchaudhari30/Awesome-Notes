# 12. Choosing a Database — Comparison Cheat Sheet

## 12.1 Master Comparison

| Family | Storage engine | Write perf | Read perf | Query flexibility | Consistency | Scale-out | System of record? |
|---|---|---|---|---|---|---|---|
| Relational (Postgres/MySQL) | B-tree + WAL + MVCC | Good (WAL-bound) | Excellent indexed; poor analytics | ★★★★★ ad-hoc SQL/joins | Full ACID | Replicas easy; shards hard | **Yes — the default** |
| Key-Value in-memory (Redis) | Hash table in RAM (+AOF/RDB) | Extreme | Extreme (µs–ms) | Key-only (+ structures) | Atomic ops; async repl | Cluster slots | No (cache/ephemeral) |
| Key-Value managed (DynamoDB) | LSM, hash-partitioned | Excellent, flat SLA | Excellent point reads | Key + sort-key only | Per-request choice; item ACID | Automatic, unlimited | Yes, for key-shaped data |
| Document (MongoDB) | B-tree (WiredTiger), BSON | Good (doc rewrite cost) | Excellent by id/indexed field | ★★★★ rich, weak joins | Doc-atomic; multi-doc txn ok | Built-in sharding | Yes |
| Wide-Column (Cassandra) | LSM + leaderless ring | **Best-in-class** | Good single-partition only | ★★ pre-designed queries only | Tunable (quorum), LWW | Linear, multi-DC native | Yes (with modeling care) |
| Columnar OLAP (ClickHouse/Snowflake) | Compressed immutable column segments | Bulk-only | **Best for scans/aggregates** | ★★★★ analytical SQL | Batch-atomic; derived data | MPP / storage-compute split | No (derived) |
| Graph (Neo4j) | Index-free adjacency records | Moderate | **Best multi-hop traversals** | ★★★★ pattern/path queries | ACID | Weak (graphs cut badly) | Yes (niche) |
| Time-Series (Timescale/Influx) | Time chunks + Gorilla compression | Excellent append | Excellent time-range | ★★★ time+tag queries | Relaxed | Shard by series/time | Usually derived |
| Search (Elasticsearch) | Inverted index, immutable segments | Good bulk; costly updates | **Best ranked text search** | ★★★★ search DSL/facets | NRT, eventual | Shards + scatter-gather | **No (derived)** |
| Vector (pgvector/Milvus) | HNSW/IVF-PQ graphs | OK insert; weak delete | Best top-k similarity | Similarity + filters | Eventual/freshness SLA | Shard by id | No (derived, model-versioned) |
| Distributed SQL (Spanner/CRDB) | Ranges + Raft + RocksDB | Good (+consensus tax) | Good; follower reads | ★★★★★ full SQL | Serializable / external | **Native, RPO=0, geo** | Yes |

## 12.2 Storage-Engine Lens (one idea per family)

| Engine idea | Who uses it | Performance consequence |
|---|---|---|
| B-tree, update-in-place + WAL | Relational, MongoDB | Balanced R/W, great ranges; page-split sensitivity |
| LSM append + compaction | Cassandra, RocksDB, DynamoDB, CRDB | Fast writes; read amp, tombstones, p99 compaction spikes |
| Hash table in RAM | Redis, Memcached | µs point ops; no ranges, RAM budget |
| Compressed column segments | ClickHouse, Parquet, warehouses | GB/s scans of few columns; no point updates |
| Inverted index | Elasticsearch, Lucene | ms ranked text search; NRT visibility, re-index on update |
| Index-free adjacency | Neo4j | O(1) per hop; shards badly |
| Time-chunked + delta/XOR codecs | TSDBs | ~1–2 B/point, O(1) retention; cardinality cliff |
| ANN graphs (HNSW/IVF-PQ) | Vector DBs | ms approximate top-k; RAM-heavy, recall trade-off |
| Ranges + Raft per shard | Spanner, CRDB, TiDB | ACID at scale; consensus latency on every write |

## 12.3 Requirement → Database (decision table)

| Requirement | First reach | Second look |
|---|---|---|
| General app data, invariants, joins | PostgreSQL | MySQL |
| Same, but beyond one node / multi-region RPO=0 | CockroachDB / Spanner | Vitess/Citus-sharded PG |
| Cache, sessions, counters, rate limits | Redis | Memcached |
| Key-addressed data, huge scale, flat SLA | DynamoDB | Cassandra |
| Write firehose: events, messages, IoT | Cassandra/Scylla | Kafka + OLAP |
| Aggregate-shaped flexible entities | MongoDB | Postgres jsonb |
| Dashboards/analytics over billions of rows | ClickHouse / Snowflake | BigQuery/Redshift |
| Metrics/telemetry with retention | Prometheus/Timescale/Influx | VictoriaMetrics |
| Product search, log search, facets | Elasticsearch/OpenSearch | Postgres FTS, Typesense |
| Semantic/RAG similarity | pgvector (small), Milvus/Pinecone (large) | ES/Redis vector |
| Multi-hop relationships, fraud rings | Neo4j | Postgres recursive CTE (shallow) |
| Files/blobs | Object storage (S3) — not a database | — |

## 12.4 Cross-Cutting Principles (carry into every design)

1. **One system of record; everything else is derived** — caches, indexes, warehouses, vectors fed by CDC/outbox, rebuildable, allowed to lag (System Design → Stream Processing).
2. **The partition/shard/key design *is* the performance design** — pick it from the dominant query; check for hot keys/celebrities/monotonic keys in every store.
3. **Storage engine predicts behavior** — before benchmarking, ask: B-tree, LSM, column, inverted, or graph? You already know the trade-offs.
4. **Consistency is a budget** — spend transactions/linearizability on invariants (money, uniqueness); buy latency/availability with eventual consistency elsewhere.
5. **Start with Postgres; specialize under measured pressure** — every additional store is a consistency boundary plus an ops burden that must pay rent.

## 12.5 Rapid-Fire Interview Q&A

- **"SQL vs NoSQL?"** — Wrong axis. Ask: data model fit, storage engine fit for the R/W profile, and required consistency/scale. Modern SQL scales out (Ch. 11); modern NoSQL has transactions (Mongo).
- **"Why is Cassandra fast at writes?"** — Appends to commit log + memtable; never reads before writing; sequential I/O; leaderless parallelism. Bill: read amplification + tombstones + LWW.
- **"Why not Elasticsearch as primary DB?"** — NRT visibility, eventual consistency, costly updates, historically lossy under partition — it's a derived index, keep truth elsewhere.
- **"When is a graph DB justified?"** — Query depth ≥ 2–3 hops or variable-length paths; otherwise joins are fine.
- **"DynamoDB vs Cassandra?"** — Managed, flat SLA, pay-per-throughput, GSIs vs self-run, multi-DC control, tunable consistency, no per-partition throughput caps.
- **"Why does everyone end up with 5 databases?"** — Different access patterns want different physical layouts; the discipline is one source of truth + CDC-fed derived stores, not five sources of truth.
