# 6. Columnar (OLAP) Databases

> ClickHouse, Redshift, BigQuery, Snowflake, DuckDB; file formats Parquet/ORC. Built for the opposite workload of everything so far: **scan billions of rows, touch few columns, aggregate**. The entire design follows from one storage decision — store each **column** contiguously instead of each row.

## 6.1 The Workload (OLAP vs OLTP recap)

- Queries look like: `SELECT region, SUM(revenue) FROM sales WHERE date >= '2026-01-01' GROUP BY region` — millions/billions of rows in, a handful of aggregate rows out.
- No point updates, no per-row transactions; data arrives in **bulk batches or streams**, is rarely modified, accumulates history (facts + dimensions, star schema — System Design → Storage and Retrieval).

## 6.2 How They Store Data

### Column-wise layout

```
Row store:    [id,date,region,revenue][id,date,region,revenue]...   → read all to get one column
Column store: [id,id,id,...][date,date,...][region,region,...][revenue,revenue,...]
                                          → read ONLY the columns the query touches
```

Three compounding wins:

1. **I/O pruning** — 3 columns of 100 = ~3 % of bytes read.
2. **Compression** — same-typed, similar values compress brutally well:
   - **Dictionary encoding** (low-cardinality strings → small ints), **run-length encoding** (sorted/repetitive columns collapse to (value, count)), **delta encoding** (timestamps, ids), then general LZ4/ZSTD on top. 10–30× is routine → more data per disk read and per RAM byte.
3. **Vectorized execution** — operators process **batches of column values in tight loops** (SIMD, cache-friendly), instead of interpreting row-at-a-time; modern engines add code generation.

### Physical organization

- Data lives in **immutable sorted segments/blocks** (ClickHouse "parts", Parquet row-groups): writes buffer → sorted column files → background **merges** (LSM philosophy applied to columns). Point updates/deletes are second-class (versioned rows merged out later, or copy-on-write of files).
- **Sort key / clustering** determines pruning power: each block stores **min/max per column (zone maps)** — a `WHERE date >= X` skips whole blocks without reading them. Choosing the sort/partition key ≈ choosing your indexes.
- **Partitioning** (usually by date) → partition pruning + cheap retention (`DROP PARTITION`).
- Little to no B-tree indexing — sequential scan bandwidth + pruning replaces per-row lookup machinery.

### Architecture split (cloud warehouses)

- **Separation of storage and compute** (Snowflake, BigQuery): data on object storage (S3-like), stateless compute clusters spun up per workload, scaled/parked independently; local SSD caches hide object-storage latency. ClickHouse/Redshift classic: coupled shared-nothing nodes (faster hot path, less elastic).

## 6.3 Performance Profile

| Operation | Character |
|---|---|
| Aggregation/scan over few columns | Spectacular — GB/s–TB/s scan rates, billions of rows/s/node (ClickHouse) |
| Point lookup by id | Poor — that's what zone maps *can't* do well; use an OLTP store |
| Update/delete single row | Awkward and expensive (segment rewrite/merge) |
| Ingestion | Great in batches (columnar segments are built per batch); trickle inserts create too many small parts (merge pressure) — buffer/micro-batch |
| Joins | Star-schema joins fine (broadcast small dimensions); giant fact-to-fact joins = shuffle cost (System Design → Batch) |
| Concurrency | Tens of analysts, not tens of thousands of app threads |

## 6.4 Consistency & Freshness

- Bulk-loaded warehouse: data is as fresh as the last ETL/ELT run (minutes–hours).
- Streaming ingestion (Kafka → ClickHouse/materialized views, or warehouse streaming inserts) narrows to seconds; still **eventually consistent derived data**, not a system of record.
- Transactions: coarse-grained (atomic per load/partition swap), not OLTP semantics.

## 6.5 The Lakehouse Neighborhood

- **Data lake:** raw files (Parquet) on object storage; query engines (Spark, Trino, DuckDB) read them in place — schema-on-read, cheapest storage.
- **Lakehouse table formats** (Delta Lake, Iceberg, Hudi): add ACID-ish transactions, snapshots/time travel, schema evolution *on top of Parquet files* via a metadata/manifest layer — warehouse ergonomics on lake storage.
- **HTAP** (TiDB/TiFlash, SingleStore): one system keeping a row replica for OLTP and a columnar replica for OLAP in sync — avoids the ETL hop for operational analytics.

## 6.6 When to Choose / Avoid

**Choose when:** dashboards/BI, ad-hoc analytics over history, event/log analytics at scale, feature computation over billions of rows — anything shaped "scan many rows, few columns, aggregate."

**Avoid when:** the app's request path needs point reads/updates (OLTP), sub-second freshness of the source of truth, or high-concurrency small queries. Standard architecture: OLTP system of record → **CDC/ETL** → columnar store as derived analytics data.

## 6.7 Interview Sound Bites

- "Columnar wins by multiplication: read 3 % of the columns × 10× compression × SIMD batch execution."
- "Zone maps + sort key replace indexes: the engine skips blocks whose min/max can't match the predicate."
- "Column segments are immutable — analytics engines are LSM at heart: batch in, sort, merge in the background; single-row UPDATE is the anti-pattern."
- "Snowflake's real innovation is separating storage from compute — park the compute, keep the data."
- "The warehouse is derived data: the OLTP store owns truth; CDC feeds analytics."
