# 2. Relational (OLTP) Databases

> PostgreSQL, MySQL/InnoDB, Oracle, SQL Server. The default database: tables + SQL + ACID transactions, built on **B-trees, a write-ahead log, a buffer pool, and MVCC**. Understanding those four internals explains both why relational DBs feel "safe" and where they hit walls.

## 2.1 Data Model

- **Tables of rows** with a declared schema (schema-on-write); relationships by foreign key; arbitrary joins at query time.
- Strengths: many-to-many relationships, ad-hoc queries (the optimizer finds a plan), constraints (unique, FK, check) enforce invariants *in one place*.
- Modern hybrid: `jsonb`/JSON columns give document flexibility inside a relational engine — indexable, queryable.

## 2.2 How They Store Data

### Pages and heap/clustered layout

- Storage unit = fixed-size **page** (PostgreSQL 8 KB, InnoDB 16 KB). Rows live in pages; pages are read/written whole.
- **PostgreSQL:** table = **heap** (rows in no particular order); all indexes are secondary, pointing to row locations (ctid).
- **MySQL InnoDB:** table = **clustered index** — rows physically stored in the B-tree of the primary key. Primary-key lookups are one tree descent; secondary indexes store the PK and pay a second descent ("double lookup"). Consequence: sequential PKs (auto-inc/UUIDv7) insert append-style; random UUIDv4 PKs cause page splits and cache-hostile inserts.

### B-tree indexes

- O(log n) point lookups and **excellent range scans**; composite indexes obey the leftmost-prefix rule; covering indexes answer queries without touching the table.
- Every extra index = extra write amplification on every INSERT/UPDATE (System Design → Storage and Retrieval).

### WAL + buffer pool

```
COMMIT ──▶ append change record to WAL (sequential write, fsync) ──▶ ack client
                     dirty pages in buffer pool flushed to disk lazily (checkpoints)
```

- **Durability comes from the WAL**, not from writing the table pages at commit — commits are sequential-log-fast; random page I/O is deferred and batched.
- The **buffer pool** (RAM cache of pages) is why "small" databases are fast: if the working set fits, reads rarely touch disk. Watch buffer-pool hit ratio before blaming the engine.
- The WAL is also the replication feed and the CDC tap (Debezium reads it).

### MVCC (multi-version concurrency control)

- Updates create a **new row version**; readers see the version visible to their snapshot → readers and writers never block each other.
- PostgreSQL keeps old versions *in the heap* → needs **VACUUM** to reclaim them (table/index **bloat** and transaction-ID wraparound are the classic operational traps). InnoDB keeps old versions in a separate **undo log** → different trade-off (long transactions bloat undo, not the table).
- Long-running transactions are toxic in both: they pin old versions everywhere.

## 2.3 Performance Profile

| Operation | Character |
|---|---|
| Point read by indexed key | Sub-ms (buffer pool hit) to a few ms; 3–4 page reads worst case |
| Range scan on index | Excellent — sorted pages |
| Write (single row) | Fast (WAL append) — but each index adds work; fsync policy dominates |
| Join | Great at OLTP sizes with proper indexes (nested-loop/hash/merge chosen by optimizer) |
| Full-table analytical scan | Poor fit — row layout reads all columns; hammers the buffer pool (→ Columnar, Ch. 6) |
| Write throughput ceiling | Single-node: thousands–tens of thousands TPS; then partition or move to Ch. 11 |

**What makes it slow in practice (interview checklist):** missing indexes (seq scans), over-indexing (write amplification), random-UUID clustered PKs, N+1 query patterns, long transactions (MVCC bloat + lock waits), lock contention on hot rows (counters!), unbounded `OFFSET` pagination (use keyset pagination).

## 2.4 Transactions & Consistency

- Full ACID; default isolation usually Read Committed (PG) / Repeatable Read (InnoDB); serializable available (PG's SSI). Anomalies and levels: see System Design → Transactions.
- Constraints + transactions = the cheapest correctness you'll ever buy. This is the store for **money, inventory, uniqueness**.

## 2.5 Scaling Story

1. **Vertical** first — a big modern box goes remarkably far.
2. **Read replicas** (async WAL shipping) → read scaling + HA; brings replication-lag anomalies (read-your-writes).
3. **Connection pooling** (PgBouncer) — Postgres connections are processes; pools are mandatory at scale.
4. **Partitioning within one node** (declarative partitions) — prunes scans, eases retention.
5. **Sharding** (application-level or Vitess/Citus) — powerful but you lose cross-shard joins/transactions → at this point compare with Distributed SQL (Ch. 11).

## 2.6 When to Choose / Avoid

**Choose when:** invariants and transactions matter; query patterns evolve (ad-hoc joins); data is naturally relational; you want the largest talent/tooling ecosystem. **Default choice — deviate with a reason.**

**Avoid / augment when:** write throughput beyond a node's ceiling with simple key access (→ wide-column), heavy analytics (→ columnar), aggregate-shaped flexible schemas dominate (→ document), sub-ms cache reads (→ key-value).

## 2.7 Interview Sound Bites

- "Commit = WAL fsync; the table pages catch up later — that's why OLTP commits are fast despite random-update workloads."
- "MVCC means readers don't block writers; the bill arrives as VACUUM/undo maintenance and long-transaction bloat."
- "InnoDB clusters rows by primary key — random UUID PKs turn appends into page-split storms."
- "Postgres with jsonb, full-text, and pgvector is four databases in one; I start there and specialize only under measured pressure."
