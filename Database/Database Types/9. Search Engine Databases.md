# 9. Search Engine Databases

> Elasticsearch/OpenSearch (on Apache Lucene), Solr, Typesense, Meilisearch. Purpose: **relevance-ranked, typo-tolerant, faceted full-text search** — queries a B-tree can't answer (`LIKE '%term%'` is a full scan with no ranking). The core structure: the **inverted index** — instead of document → words, store **word → documents**.

## 9.1 Data Model

- JSON documents in an index; each field has a **mapping** (type + how it's analyzed). Two field personalities:
  - `text` — analyzed for full-text search (tokenized, normalized).
  - `keyword` — stored verbatim for exact filters, sorting, aggregations.
- **Analysis pipeline** (at index *and* query time): tokenize → lowercase → strip stopwords → **stem** ("running"→"run") → synonyms. Search quality is mostly analyzer configuration, not query cleverness.

## 9.2 How They Store Data (Lucene internals)

### Inverted index

```
Documents:                      Inverted index:
D1: "quick brown fox"           quick  → [D1, D3]          (postings list:
D2: "lazy brown dog"            brown  → [D1, D2]           doc ids + term freq
D3: "quick red dog"             dog    → [D2, D3]           + positions for
                                red    → [D3] ...            phrase queries)
```

- **Term dictionary** (sorted, FST-compressed in RAM) → **postings lists** (delta-encoded, block-compressed doc ids on disk). A query looks up terms, then intersects/unions postings — set operations over compressed integer lists, which is why multi-term search over millions of docs takes milliseconds.
- Positions enable phrase/proximity queries; per-term statistics feed scoring.

### Immutable segments (LSM, again)

- Writes buffer in RAM → periodically **flushed as immutable segments**; background **segment merging** compacts them (deletes = tombstone bitmap until merge). Identical philosophy to LSM/columnar stores.
- **Near-real-time, not real-time:** documents become searchable at the next **refresh** (default ~1 s), durable via a translog (WAL). Say "NRT" in interviews.

### Beyond the inverted index

- **Doc values** — columnar per-field storage used for sorting, aggregations, faceting (the OLAP-ish half of Elasticsearch).
- **BKD trees** for numeric/geo ranges.
- **Relevance scoring — BM25** (default): term frequency (saturating) × inverse document frequency (rare terms weigh more) × length normalization. Modern stacks add semantic/vector rerankers (→ Chapter 10, hybrid search).

## 9.3 Performance Profile

| Operation | Character |
|---|---|
| Multi-term ranked search, filters, facets | Excellent — ms over tens of millions of docs |
| Aggregations (doc values) | Strong, memory-hungry at high cardinality |
| Indexing throughput | Good but write-amplified (analysis + many structures per doc); bulk API, tune refresh interval for ingest |
| Update single field | Full document re-index (segments immutable) — updates are expensive |
| Get by id right after write | Only after refresh (NRT gap) |
| Deep pagination (`from: 100000`) | Pathological — coordinator must sort offset+size from every shard; use `search_after` |

## 9.4 Distribution & Consistency

- Index → **shards** (each a Lucene index) × replicas; a query **scatter-gathers**: coordinator fans out to one copy of each shard, merges top-k. More shards = more parallelism *and* more merge overhead — oversharding is the classic ops mistake (aim ~10–50 GB/shard).
- Primary-backup replication per shard; cluster state managed by elected master nodes.
- **Not a system of record:** eventual consistency, NRT visibility, historically imperfect partition-failure behavior. **Standard architecture: DB is truth → CDC/outbox → indexer → Elasticsearch as derived, rebuildable data** (System Design → Stream Processing).

## 9.5 When to Choose / Avoid

**Choose when:** product/site search (typo tolerance, synonyms, relevance), log/APM search at scale (the ELK half of observability), faceted navigation (e-commerce filters + counts), geo + text combined queries, autocomplete.

**Avoid when:** exact-match lookups a B-tree serves (cheaper in the main DB), transactional/consistent reads, frequently-updated fields (re-index cost), or Postgres full-text (`tsvector`/GIN) already covers your modest search needs — a second cluster is a big operational bill.

## 9.6 Interview Sound Bites

- "An inverted index flips document→words into word→documents; search becomes intersection of compressed postings lists."
- "Search quality lives in the analyzer: tokenize, normalize, stem, synonyms — at both index and query time, consistently."
- "Elasticsearch is near-real-time: searchable at the next refresh (~1 s), and that gap is a feature of immutable segments."
- "BM25 in one line: rare terms matter more, repeated terms saturate, long documents get discounted."
- "Search is derived data — the database owns truth, CDC feeds the index, and I must be able to rebuild it from scratch."
