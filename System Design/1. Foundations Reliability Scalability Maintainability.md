# 1. Foundations — Reliability, Scalability, Maintainability

> Every data-intensive system is judged on three axes: does it keep working when things go wrong (**reliability**), does it keep working as load grows (**scalability**), and can humans keep working on it (**maintainability**). Everything else in system design is a technique in service of these three.

## 1.1 What is a Data-Intensive Application?

An application is **data-intensive** when data — its volume, complexity, or rate of change — is the primary challenge, rather than raw CPU cycles (which would be *compute-intensive*).

Standard building blocks almost every such system composes:

| Building block | Purpose | Examples |
|---|---|---|
| Database | Store data so it can be found again | PostgreSQL, MongoDB, Cassandra |
| Cache | Remember expensive results to speed up reads | Redis, Memcached |
| Search index | Search by keyword or filter arbitrarily | Elasticsearch, Solr |
| Stream processing | Send a message to another process, handle it asynchronously | Kafka, Flink |
| Batch processing | Periodically crunch large accumulated data | Spark, Hadoop |

**Key insight:** no single tool does all of this well. Real systems are *composed* — the application code becomes the glue that keeps caches, indexes, and databases consistent with each other. You are effectively building a special-purpose data system from general-purpose parts.

```
                 ┌──────────────┐
   Client ──────▶│  Application │
                 └──┬───┬───┬───┘
        ┌───────────┘   │   └───────────┐
        ▼               ▼               ▼
   ┌─────────┐    ┌──────────┐    ┌───────────┐
   │  Cache  │    │ Database │    │   Queue   │──▶ async workers
   └─────────┘    └──────────┘    └───────────┘
     (fast reads)  (source of truth)  (decoupling)
```

## 1.2 Reliability

**Reliability** = the system continues to work *correctly* (right result, desired performance) even when things go wrong.

- A **fault** is one component deviating from spec.
- A **failure** is the system as a whole stopping to provide service.
- Goal: build **fault-tolerant** systems where faults do not become failures. You cannot reduce fault probability to zero, so design to *tolerate* them.

### Types of faults

| Fault type | Characteristics | Mitigation |
|---|---|---|
| **Hardware** | Random, independent (disk crash, RAM error, power loss). Disks have MTTF ~10–50 years → in a 10,000-disk cluster, one dies daily | Redundancy (RAID, dual power), and increasingly *software* fault tolerance (replication) so whole machines can die |
| **Software** | Systematic, correlated — a bug hits every node at once (leap-second bugs, runaway process, cascading failures) | Thorough testing, process isolation, measuring/monitoring assumptions, allowing crash + restart |
| **Human** | Config errors are a leading cause of outages | Well-designed abstractions/APIs, sandbox environments, easy + fast rollback, gradual rollouts, telemetry |

**Practical tip:** deliberately inducing faults (chaos engineering, e.g., Netflix Chaos Monkey) verifies that your fault-tolerance machinery actually works.

## 1.3 Scalability

**Scalability** = the system's ability to cope with increased load. It is not a boolean label ("X is scalable"); it's a question: *if load grows in a particular way, what are our options for coping?*

### Step 1 — Describe load

Pick **load parameters** that matter for *your* system: requests/sec, read/write ratio, concurrent users, cache hit rate, fan-out.

**Classic example — Twitter timeline fan-out:**
- Approach A (fan-out on read): store tweets in one table; building a timeline queries all followees at read time. Cheap writes, expensive reads.
- Approach B (fan-out on write): on tweet, push it into every follower's cached timeline. Write cost = followers count; reads are instant.
- Twitter's answer: **hybrid** — fan-out on write for most users, fan-out on read for celebrities (millions of followers). The *distribution* of followers per user is the decisive load parameter, not just average tweet rate.

### Step 2 — Describe performance

- **Throughput** — records processed per second (batch systems).
- **Response time** — what the client sees: service time + network + queueing delays.
- Use **percentiles, not averages**. The median (p50) says half of requests are faster; **p95/p99/p999 (tail latencies)** capture the worst experiences — often the most valuable customers (most data → slowest queries).
- **Tail latency amplification:** if one user request requires 100 backend calls, the slowest of the 100 dominates — even rare slow calls make *most* user requests slow.
- **Head-of-line blocking:** a few slow requests hold up queued ones behind them; measure response time client-side.

```
p50 ──── 20 ms      "typical"
p95 ──── 150 ms     1 in 20 requests slower than this
p99 ──── 800 ms     1 in 100 — SLOs/SLAs usually pin this
p999 ─── 2.5 s      1 in 1000 — cost of optimizing may exceed benefit
```

### Step 3 — Cope with load

| Strategy | Description | Trade-off |
|---|---|---|
| **Vertical scaling** (scale up) | Bigger machine | Simple, but cost grows super-linearly; hard ceiling |
| **Horizontal scaling** (scale out) | More machines, shared-nothing | Cheap machines, no ceiling, but adds distributed-system complexity |
| **Elastic scaling** | Auto add/remove capacity on detected load | Great for unpredictable load; harder to reason about |

**Rules of thumb:**
- Stateless services are easy to scale out; **state is what makes scaling hard** — keep databases on one node until forced to distribute.
- There is no one-size-fits-all architecture. A system for 100,000 small requests/sec looks nothing like one for 3 huge requests/min, even at equal throughput.
- Design for the *next* order of magnitude, not for hypothetical Google scale. Premature scaling machinery is wasted complexity.

## 1.4 Maintainability

The majority of software cost is not initial development but **ongoing maintenance**. Three design principles:

1. **Operability** — make life easy for operations: good monitoring/observability, automation support, avoiding single-machine dependencies, good documentation, sane defaults, predictable behavior.
2. **Simplicity** — manage complexity via **abstraction**. Symptoms of accidental complexity: state-space explosion, tight coupling, tangled dependencies, inconsistent naming, special-case hacks. A big ball of mud raises the cost of every future change.
3. **Evolvability** — make change easy: agility at the data-system level. Simple, well-abstracted systems are easier to modify; schema evolution and rolling upgrades (see Chapter 4) are the concrete mechanisms.

## 1.5 Interview Sound Bites

- "Fault ≠ failure — we build fault-tolerant systems so component faults don't become user-visible failures."
- "Scalability is meaningless without a load parameter — scale *with respect to what?*"
- "We track p99, not average, because tail latency is what users on the slow end feel, and fan-out amplifies it."
- "Scaling out is a trade: you exchange hardware ceilings for distributed-systems complexity — replication lag, partial failure, consensus."
- "Simplicity is a feature: every clever component you add is something on-call has to understand at 3 a.m."
