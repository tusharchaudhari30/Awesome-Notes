# 7. Transactions

> A transaction groups several reads/writes into one all-or-nothing unit so the application doesn't have to reason about partial failure and concurrent interleavings. Transactions are not a law of nature — they're a *simplifying abstraction* you pay for, and every "NoSQL doesn't need transactions" claim is really a claim about which anomalies your app can tolerate.

## 7.1 ACID, Precisely

| Letter | Real meaning | Common misreading |
|---|---|---|
| **A**tomicity | *Abortability* — on error, all writes are undone; safe to retry | "Concurrency safety" (that's isolation) |
| **C**onsistency | App-level invariants hold (e.g., accounts balance) — a property of *your code*, the DB only helps (constraints) | A database guarantee |
| **I**solation | Concurrent transactions can't step on each other; ideal = **serializability** (as if run one at a time) | "Everyone runs serializable" — almost nobody defaults to it |
| **D**urability | Committed data survives crashes (WAL + fsync, replication) | Absolute — it's always a spectrum (see async replication) |

**BASE** ("basically available, soft state, eventual consistency") is mostly a marketing antonym.

Even single-object writes need atomicity/isolation (a crash mid-20KB-write must not leave half a document); multi-object transactions are about **keeping related data in sync**: foreign keys, denormalized copies, secondary indexes.

## 7.2 Weak Isolation Levels and Their Anomalies

Most databases default to weak isolation. Know each anomaly + the level that kills it:

### Read Committed (default in PostgreSQL, Oracle, SQL Server)
- Guarantees: **no dirty reads** (only see committed data), **no dirty writes** (only overwrite committed data).
- Implementation: row locks for writes; for reads, remember old committed value (no read locks — readers never block writers).
- Still allows: **read skew / nonrepeatable reads** — during your transaction, another commits, and you see the DB in two different states (e.g., a backup or analytics query reading a mid-transfer bank balance: money appears to vanish).

### Snapshot Isolation / Repeatable Read (MySQL InnoDB RR, PostgreSQL RR)
- Each transaction reads from a **consistent snapshot** — the DB as of transaction start.
- Implementation: **MVCC (multi-version concurrency control)** — keep multiple committed versions of each row; each transaction sees versions per its snapshot's visibility rules. *Readers never block writers; writers never block readers.*
- Kills read skew. Still allows: **lost updates, write skew, phantoms.**

### The write anomalies

| Anomaly | Pattern | Example | Fixes |
|---|---|---|---|
| **Lost update** | read → modify → write; two do it concurrently, one overwrites the other | Two users incrementing a counter; both read 42, both write 43 | Atomic ops (`UPDATE ... SET x = x+1`), `SELECT ... FOR UPDATE`, automatic detection (PG snapshot isolation aborts the loser), or CAS |
| **Write skew** | Two transactions read the same objects, then update *different* objects, breaking a shared invariant | Two on-call doctors both check "≥2 on call" then both go off call; meeting-room double booking; username claims | Serializable isolation; or materialize the conflict into a lockable row |
| **Phantom** | A write changes the *result set of a search query* another transaction ran | The doctor check queries rows that the other transaction's insert would have matched — nothing to lock | Serializable (index-range/predicate locks) |

**Interview gold:** write skew is the anomaly people forget — snapshot isolation does **not** prevent it, and it's exactly the shape of most business-rule invariants ("at most N", "must remain unique", "no overlap").

## 7.3 Achieving Serializability

Three real implementations:

1. **Actual serial execution** (Redis, VoltDB): one transaction at a time on a single thread — viable when data fits in RAM and transactions are short (often stored procedures); scales only by partitioning.
2. **Two-Phase Locking (2PL)** — the classic: readers block writers *and vice versa*, shared/exclusive locks held to commit; predicate/index-range locks for phantoms. Correct but poor concurrency and unstable latencies (lock queues, deadlocks → detection + retry).
3. **Serializable Snapshot Isolation (SSI)** (PostgreSQL `SERIALIZABLE`): **optimistic** — run on snapshots without blocking, track read/write dependencies, **abort at commit** any transaction whose premise was invalidated. Full serializability at a modest overhead when contention is low; under high contention, abort rate soars.

| | 2PL (pessimistic) | SSI (optimistic) |
|---|---|---|
| Contention low | Unnecessary blocking | Excellent |
| Contention high | Queues but progresses | Abort storms, wasted work |
| Read-only queries | Can block/get blocked | Free (snapshot) |

## 7.4 Distributed Transactions (across partitions/services)

- **Two-Phase Commit (2PC):** coordinator asks all participants to *prepare* (promise to commit), then broadcasts *commit/abort*. Guarantees atomicity across nodes, but: the promise must survive crashes, and **if the coordinator dies after prepare, participants are stuck "in doubt" holding locks** until it recovers — a blocking protocol. XA transactions in practice: operationally fragile, kill throughput; avoid across heterogeneous systems.
- **Modern practice:** avoid distributed transactions; instead use
  - **single-partition design** (choose keys so transactions stay local),
  - **idempotent async workflows / sagas** — sequence of local transactions with compensating actions on failure,
  - **outbox pattern / CDC** — atomically record intent locally, propagate via log,
  - or databases with built-in cross-shard transactions paid for with consensus (Spanner, CockroachDB — see Database Types notes).

## 7.5 Choosing an Isolation Strategy (checklist)

1. Default (read committed / snapshot) + **atomic single-statement updates** for counters and read-modify-writes.
2. Invariants over *sets* of rows ("at most N", uniqueness, non-overlap)? → serializable, `FOR UPDATE` on a materialized conflict row, or a DB constraint.
3. Cross-service invariants? → saga + compensation, not 2PC.
4. Retries: every transaction (and every API triggering one) must be **idempotent** — aborts are a feature, and networks duplicate requests.

## 7.6 Interview Sound Bites

- "Atomicity is about *abort and retry*, not concurrency — isolation handles concurrency."
- "MVCC is why readers and writers don't block each other: everyone reads a consistent snapshot of versions."
- "Snapshot isolation's blind spot is write skew: two transactions each validate an invariant on a snapshot, then jointly break it."
- "2PC's dark side: a crashed coordinator leaves participants in-doubt, holding locks — that's why I reach for sagas/outbox between services."
- "SSI is optimistic 2PL: no blocking, but you pay in aborts under contention."
