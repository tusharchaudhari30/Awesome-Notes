# 3. Storage and Retrieval

> How does a database actually lay bytes on disk, and why does that determine its performance profile? Two families dominate OLTP storage engines — **log-structured (LSM-trees)** and **page-oriented (B-trees)** — and a third layout, **column-oriented**, dominates analytics. Knowing all three explains almost every database's read/write trade-offs.

## 3.1 The Simplest Database

An append-only file: `set(k,v)` appends a line; `get(k)` scans for the last occurrence.

- Writes: O(1), sequential — blazingly fast (appending is the cheapest disk operation).
- Reads: O(n) — terrible.
- Fix reads with an **index** — but every index is *extra structure maintained on writes*. **Fundamental trade-off: indexes speed up reads, slow down writes.** That's why databases make you choose indexes rather than indexing everything.

## 3.2 Hash Indexes (Bitcask model)

In-memory hash map: key → byte offset in the append-only log.

- Append-only segments + **compaction** (drop overwritten values) + merging keep disk bounded.
- Crash recovery via snapshotting the hash maps; partial writes handled with checksums.
- **Why append-only beats overwrite-in-place:** sequential writes ≫ random writes; concurrency and crash recovery are far simpler; no file fragmentation.
- **Limits:** all keys must fit in RAM; range queries (`key BETWEEN a AND b`) are impossible — keys are scattered.

## 3.3 SSTables and LSM-Trees

**SSTable (Sorted String Table):** a segment file where entries are *sorted by key*.

Advantages over unsorted logs:
1. Merging segments = **mergesort** — streaming, efficient, even for files bigger than RAM.
2. Sparse in-memory index suffices (one entry per few KB); binary-search within blocks.
3. Blocks can be compressed → less disk I/O.

**LSM-tree (Log-Structured Merge-tree) write path** — used by Cassandra, RocksDB, LevelDB, HBase, ScyllaDB:

```
write ──▶ WAL (crash safety, append) 
      └─▶ memtable (in-memory balanced tree, sorted)
              │  when full, flush sequentially
              ▼
          SSTable L0 ─┐
          SSTable L1  ├── background compaction & merging
          SSTable L2 ─┘   (size-tiered or leveled)
```

**Read path:** memtable → newest SSTable → older SSTables. A **Bloom filter** per SSTable answers "definitely not here" without touching disk — critical for missing-key lookups.

- **Compaction strategies:** *size-tiered* (merge similar-sized tables; better write throughput, more space overhead) vs *leveled* (key ranges split into levels; more predictable reads, more write amplification).
- **Strengths:** high **write throughput** (all sequential I/O), good compression, sorted data → range scans work.
- **Weaknesses:** reads may touch several structures (**read amplification**); background compaction competes for disk bandwidth and can fall behind under sustained writes (**write amplification**: one logical write is rewritten many times over its life).

## 3.4 B-Trees

The standard index of relational databases (PostgreSQL, MySQL/InnoDB, Oracle) — and most others.

- Data broken into **fixed-size pages** (~4–16 KB), forming a balanced tree; each page holds keys and child pointers. **Branching factor** ~several hundred → a 4-level tree of 4 KB pages addresses ~256 TB. Lookups: O(log n), typically 3–4 page reads.
- **Update-in-place:** overwrite the page on disk (vs LSM's append-only). Page splits handle overflow.
- **Crash safety:** **WAL (write-ahead log)** — every modification is appended to a log before being applied to pages; recovery replays the WAL.
- **Concurrency:** latches (lightweight locks) on pages; more intricate than LSM's immutable segments.

## 3.5 B-Tree vs LSM-Tree — The Decision Table

| Dimension | B-tree | LSM-tree |
|---|---|---|
| Write throughput | Lower — random page writes + WAL | Higher — sequential appends |
| Write amplification | Whole page rewritten for one row | Repeated rewrite during compaction (still usually lower) |
| Read latency | Predictable, O(log n) pages | Variable — memtable + N SSTables + Bloom filters |
| Range scans | Excellent | Good (sorted), but across segments |
| Space | Fragmentation from splits | Better — compression + compaction removes dead space |
| Consistency features | Key exists in exactly one place → easy transactional locking | Multiple copies of a key across segments |
| Tail latency | Steady | Compaction spikes can hit p99 |

**Rule of thumb:** write-heavy, append-mostly workloads (event ingestion, messaging, metrics) → LSM engines. Read-heavy, transactional workloads with strong secondary-index needs → B-tree engines. Benchmarks on *your* workload beat rules of thumb.

## 3.6 Other Index Structures

- **Secondary indexes:** map an attribute → row locations; keys aren't unique so values are lists (postings). Both B-tree and LSM variants exist.
- **Clustered index:** the row data lives *in* the index (InnoDB primary key); reads for that key need no extra hop, but secondary lookups go through the primary key.
- **Covering index:** stores selected columns in the index so queries can be answered without touching the row.
- **Multi-column / composite:** (last_name, first_name) — order matters; leftmost-prefix rule.
- **Full-text / fuzzy:** inverted indexes (see Search Engines chapter in Database Types notes).
- **In-memory databases:** Redis, VoltDB — faster not mainly because "RAM vs disk" but because they skip the *overhead of encoding data for disk* and heavyweight buffer management.

## 3.7 OLTP vs OLAP and Column-Oriented Storage

| Property | OLTP | OLAP |
|---|---|---|
| Access pattern | Small reads/writes by key | Scan millions of rows, few columns |
| Used by | End users | Analysts, dashboards |
| Data | Latest state | History of events |
| Bottleneck | Random seek time / concurrency | Scan bandwidth |
| Layout | Row-oriented (B-tree/LSM) | **Column-oriented** |

**Data warehouse:** separate OLAP copy of the data (via **ETL/ELT** or CDC) so analytics never disturbs the OLTP system. Modeled as a **star schema**: a huge *fact table* of events with foreign keys into *dimension tables* (who/what/where/when).

**Column-oriented storage** (Redshift, ClickHouse, BigQuery, Parquet):
- Store each column's values contiguously → a query reading 3 of 100 columns does ~3 % of the I/O.
- Same-type values compress spectacularly (**bitmap encoding + run-length encoding** for low-cardinality columns).
- Compressed columns fit CPU caches → **vectorized execution** (SIMD over batches of values).
- Writes are harder (can't insert into the middle of sorted compressed columns) — solved LSM-style: buffer writes in memory, merge into column files in bulk.
- **Materialized views / data cubes:** precomputed aggregates as a read optimization — faster queries, less flexibility, more write cost.

## 3.8 Interview Sound Bites

- "Every index is a bet: pay on the write path to win on the read path."
- "LSM = sequential writes + background compaction; B-tree = update-in-place + WAL. That single sentence predicts most of their trade-offs."
- "Bloom filters are how LSM engines keep missing-key reads from touching every SSTable."
- "Column stores win analytics because they turn 'read the whole table' into 'read the columns you need, compressed 10×, with SIMD.'"
- "p99 spikes on an LSM store? First suspect: compaction falling behind."
