# 12. Caching, Load Balancing and CDNs

> The classic "web-scale trio." Caching converts repeated work into memory lookups; load balancing spreads requests across replicas; CDNs move bytes next to users. Each is simple until invalidation, session state, and failure modes show up.

## 12.1 Caching Fundamentals

**Where a cache can live** (each layer answers before the next):

```
Browser cache → CDN/edge → API gateway cache → App-level cache (Redis/Memcached)
     → DB internal caches (buffer pool) → OS page cache
```

**Core metrics:** hit ratio (the only number that matters first), latency, eviction rate, staleness tolerance.

### Caching patterns

| Pattern | Write path | Read path | Trade-offs |
|---|---|---|---|
| **Cache-aside (lazy)** | App writes DB, invalidates key | On miss: read DB, fill cache | Simplest; first read slow; stale window between DB write and invalidation |
| **Read-through** | — | Cache itself loads from DB on miss | Centralizes loading logic in cache layer |
| **Write-through** | Write to cache, cache writes DB synchronously | Always warm | Write latency ↑; cache holds everything written, even never-read data |
| **Write-behind (write-back)** | Write to cache, flush to DB async | Fast writes, batching | **Data loss on cache crash**; complex ordering |
| **Refresh-ahead** | — | Proactively refresh hot keys before expiry | Wasted work if predictions wrong |

### Eviction and expiry

- **LRU** (default), **LFU** (better for stable popularity), **FIFO**, random-sampling approximations (Redis actually samples, not true LRU).
- **TTL** bounds staleness; add **jitter** to TTLs so keys don't expire simultaneously.

### The classic cache failure modes (name all three in interviews)

| Problem | What happens | Fixes |
|---|---|---|
| **Stampede / thundering herd** | Hot key expires → thousands of concurrent DB reads | Per-key mutex/single-flight (one loader, rest wait), stale-while-revalidate, TTL jitter |
| **Penetration** | Requests for keys that *never exist* bypass cache to DB | Cache negative results (short TTL), Bloom filter of valid keys |
| **Avalanche** | Cache node/cluster dies → full load hits DB | Redundant cache (replicas), circuit breakers + load shedding, gradual warm-up, staggered TTLs |

### Invalidation ("one of the two hard things")

- Explicit invalidation on write (cache-aside) has a race: *(read miss → DB read old) interleaved with (write DB new → invalidate)* → cache filled with stale value until TTL. Mitigations: short TTLs as backstop, versioned keys, or **CDC-driven invalidation** (subscribe to the DB changelog and update/invalidate caches in log order — see Chapter 11).
- Delete vs update-in-place: delete is safer (update-in-place races harder).
- Distributed caches scale by **consistent hashing** across nodes (Chapter 6) — resharding moves few keys.

## 12.2 Load Balancing

### Layers

- **L4 (transport):** routes by IP/port, per-connection; blazing fast, no request awareness (e.g., IPVS, NLB).
- **L7 (application):** parses HTTP → routes by path/host/header, TLS termination, retries, per-request balancing (NGINX, Envoy, ALB).
- **DNS load balancing:** coarse geographic/failover distribution; slow to react (TTL caching).
- Typical stack: DNS/anycast → L4 edge → L7 per-service (service mesh sidecars are L7 LBs per pod).

### Algorithms

| Algorithm | Notes |
|---|---|
| Round robin / weighted RR | Uniform work; weights for heterogeneous nodes |
| **Least connections** | Better when request cost varies |
| Least response time | Reacts to real latency |
| Hash-based (source IP / key) | Sticky routing, cache affinity — via consistent hashing |
| Random-2-choices | Pick 2 random, take less loaded — near-optimal, avoids herd behavior |

### Health, resilience, sessions

- Active health checks (probe endpoint) + passive (eject on error rate) → remove bad backends; **outlier ejection**.
- **Retries with budget/jitter** and only for idempotent methods; **circuit breakers** stop hammering failing backends; **load shedding** rejects early when saturated (protect p99 for what you *can* serve).
- **Session state:** prefer **stateless services** (JWT, or session store in Redis) → any node serves anyone; sticky sessions are a workaround that skews load and breaks on node loss.

## 12.3 CDNs (Content Delivery Networks)

Geographically distributed reverse-proxy caches (PoPs) that terminate user connections near them.

- **What they accelerate:** static assets (obvious), but also API/dynamic traffic — TLS/TCP termination at the edge (short RTT handshakes) + optimized backbone to origin; edge compute for personalization.
- **Pull CDN** (origin fetch on miss — default) vs **push** (pre-publish, e.g., video releases).
- **Cache keys & control:** `Cache-Control` (max-age, s-maxage, stale-while-revalidate), `ETag`/conditional requests, `Vary`.
- **Invalidation strategy of champions: versioned/fingerprinted URLs** (`app.3f9a2c.js`, immutable, cache forever) — deploys change the URL, no purge needed. Purge APIs exist but are the slow path.
- Protecting the origin: **request coalescing** (one origin fetch per key per PoP), tiered caching (regional shield PoPs), `stale-if-error` (serve stale during origin outages).

## 12.4 Composed Read Path — Worked Picture

```
User ──▶ CDN PoP ──hit?──▶ respond (~10–50 ms)
           │ miss
           ▼
       L7 LB ──▶ App (stateless) ──▶ Redis (cache-aside) ──hit?──▶ respond
                                        │ miss (single-flight)
                                        ▼
                                     Database ──▶ fill cache (TTL+jitter)
   Writes: App ──▶ DB ──CDC──▶ invalidate/update Redis, purge CDN if needed
```

## 12.5 Interview Sound Bites

- "Hit ratio first: a 99 % vs 90 % hit rate is a 10× difference in DB load."
- "The three cache pathologies — stampede, penetration, avalanche — each have a canonical fix: single-flight, negative caching/Bloom filter, and shed-plus-warm."
- "I invalidate by deleting (not updating), keep a TTL as a backstop, and for correctness-critical caches drive invalidation from CDC so it follows the DB's own ordering."
- "Stateless services turn load balancing into a solved problem; sticky sessions turn it back into a hard one."
- "Fingerprinted URLs make CDN invalidation a non-event: deploy = new URL, old assets age out."
