# 6. Partitioning and Sharding

> When one machine can't hold the data or serve the load, **partition (shard)**: split the dataset so each piece lives on its own node. Goal: spread data *and query load* evenly. Enemy: **skew** and **hot spots** — a partitioning scheme that puts all load on one node buys you nothing.

Partitioning is combined with replication: each partition has multiple replicas (each node typically leads some partitions and follows others).

## 6.1 Partitioning by Key Range

Assign each partition a contiguous range of keys (like encyclopedia volumes A–B, C–D...). Used by HBase, and range-sharded MongoDB.

- **Pros:** range scans are efficient (keys sorted within partitions); boundaries can adapt to data distribution.
- **Cons:** access patterns create **hot spots** — e.g., timestamp-keyed sensor data sends *all today's writes* to one partition.
  - Classic fix: prefix the key with something that spreads load (`sensor_id, timestamp`) — trading one range scan for a scatter across sensors.

## 6.2 Partitioning by Hash of Key

`partition = hash(key) mod N` (conceptually; real systems assign hash *ranges* to partitions). Used by Cassandra, DynamoDB, Voldemort.

- **Pros:** uniform distribution, destroys most hot spots.
- **Cons:** destroys ordering → **no efficient range scans** (scatter to all partitions).
- **Hybrid (Cassandra compound key):** hash the **partition key** to place the row; sort by the remaining **clustering columns** *within* the partition → efficient "all messages for user X, ordered by time" queries. This is the single most important NoSQL data-modeling idea.
- **Residual hot keys** (celebrity problem): hashing identical keys doesn't help — one key's load still lands on one partition. Mitigations: application-level key splitting (append random suffix `key#1..N`, fan-in on read), dedicated caching for hot keys.

## 6.3 Secondary Indexes on Partitioned Data

The hard problem: secondary indexes don't map to the partition key.

| Approach | How | Writes | Reads |
|---|---|---|---|
| **Local index** (document-partitioned) | Each partition indexes only its own rows | Cheap — one partition | **Scatter/gather** all partitions, tail-latency amplification |
| **Global index** (term-partitioned) | Index itself partitioned by indexed value | Expensive — one write touches multiple index partitions (usually async) | Efficient — one index partition |

- Cassandra/Mongo local indexes: fine when queries almost always include the partition key.
- DynamoDB Global Secondary Indexes: term-partitioned, asynchronously updated → eventually consistent reads on the index.

## 6.4 Rebalancing

Data grows, nodes come and go → partitions must move. Requirements: even spread after; keep serving during; move no more than necessary.

- **Never `hash mod N`:** changing N remaps almost *every* key → full reshuffle.
- **Fixed number of partitions** (Riak, Elasticsearch, Kafka-style): create many more partitions than nodes (e.g., 1000 partitions / 10 nodes); rebalancing = moving whole partitions to new nodes; assignments change, key→partition mapping never does. Choose the count generously up front — it's hard to change later.
- **Dynamic partitioning** (HBase, MongoDB): split partitions when they exceed a size threshold, merge when small — adapts to data volume.
- **Consistent hashing** (ring + virtual nodes): each physical node owns many virtual points on a hash ring; adding a node steals a small slice from everyone → minimal movement. The idea behind Dynamo/Cassandra placement and most distributed caches.

```
   Hash ring (consistent hashing, virtual nodes)
        A₁      B₁
     ┌───●──────●───┐        key k → walk clockwise to
     C₂ ●          ● C₁      first vnode → owning node
     └───●──────●───┘        add node D → D's vnodes steal
        B₂      A₂           small arcs from A, B, C only
```

- **Automatic vs manual rebalancing:** fully automatic is convenient but dangerous — a slow (not dead) node can trigger cascading rebalance under load. Best practice: automatic *proposal*, human *approval*.

## 6.5 Request Routing

How does a client find the node for key k? (An instance of the general **service discovery** problem.)

1. **Any node forwards** (gossip-based, Cassandra) — no external coordination; clients connect anywhere.
2. **Routing tier** (proxy) — e.g., mongos; needs the partition map.
3. **Partition-aware client** — client learns the map, contacts the right node directly (fastest, most coupling).

Coordination service: many systems (HBase, Kafka pre-KRaft, SolrCloud) keep the authoritative partition→node map in **ZooKeeper/etcd**; routing layers subscribe to changes.

## 6.6 Practical Sharding Checklist (Interviews)

1. **Pick the partition key first** — it determines which queries are single-partition (fast) vs scatter/gather (slow). Model your dominant query, then choose the key so that query hits one partition.
2. Estimate partitions: (total data ÷ target partition size ~10–50 GB), with headroom for growth.
3. Plan for the hot key (celebrity) — key-splitting or caching strategy.
4. Cross-partition operations (joins, transactions, unique constraints) become *distributed* problems — avoid by schema design or accept the cost (Chapter 7/9).
5. Rebalancing story: fixed partitions or consistent hashing; never mod-N.

## 6.7 Interview Sound Bites

- "The partition key is a query-routing decision disguised as a storage decision."
- "Hash partitioning trades range scans for uniform load; Cassandra's hash-then-sort compound key buys both back."
- "Local secondary indexes make writes cheap and reads scatter/gather; global ones invert that."
- "hash mod N is the sharding scheme you use exactly once — the first rebalance teaches you consistent hashing."
- "Hot keys don't shard: hashing a celebrity's id still puts all their load on one node — you split the key or cache it."
