# 8. The Trouble with Distributed Systems

> A single machine is deterministic: things either work or crash completely. A distributed system fails *partially* — some nodes broken in some ways, sometimes, nondeterministically — and you often **can't even know what state anything is in**. This chapter is the pessimism catalogue: unreliable networks, unreliable clocks, and process pauses. Everything in Chapter 9 exists to cope with what's here.

## 8.1 Partial Failure

- On one node: deterministic, fail-stop. In a distributed system: **partial failure** — nondeterministic, and *knowing whether something worked is itself unreliable*.
- Design stance: assume everything that can go wrong *will*; build tolerance in software; test failure scenarios deliberately (chaos engineering).
- Scale trade-off: supercomputers checkpoint and treat any fault as total failure; internet services must serve users through faults with commodity hardware — fault tolerance in *software* is non-negotiable.

## 8.2 Unreliable Networks

Asynchronous packet networks make **no guarantees** about delivery or timing. When you send a request and hear nothing, you cannot distinguish:

```
  1. request lost          ──▶ ✗
  2. remote node crashed       ──▶ ☠
  3. remote node slow (queue)  ──▶ ⏳ (will answer later)
  4. response lost         ◀── ✗   (action WAS performed!)
```

**The only tool is a timeout — and a timeout tells you nothing about whether the action happened.** Consequences:

- Every remote call needs: timeout + retry + **idempotency** (case 4 means retries can double-execute).
- Network partitions happen constantly in real datacenters (switch failures, misconfigurations, shark bites on undersea cables); even "reliable" managed clouds have them.
- **Timeout tuning dilemma:** short → false positives (declaring live nodes dead → duplicate actions, cascading load shifts during spikes); long → slow failure recovery. Better: measure response-time distribution and adapt (jittered, percentile-based like TCP RTO, Phi-accrual failure detectors).
- **Why can't networks guarantee latency?** Packet switching maximizes utilization via queueing (bursty traffic); guaranteed latency needs circuit-style reservation → wasted capacity. Queueing delay (switch buffers, OS, VM scheduling, TCP retransmit) is why tail latency exists.

## 8.3 Unreliable Clocks

Two very different clocks per machine:

| | Time-of-day clock | Monotonic clock |
|---|---|---|
| Returns | Wall-clock date/time (epoch) | Elapsed nanoseconds since arbitrary point |
| Can jump backwards? | **Yes** (NTP step, leap seconds) | Never |
| Comparable across machines? | Only approximately | **Meaningless across machines** |
| Use for | Timestamps in data (carefully) | Timeouts, durations, rate measurement |

- NTP sync in practice: drift (~ppm level, tens of ms typical, can be *seconds* when misconfigured — and it usually goes unnoticed).
- **Dangers of trusting wall clocks:**
  - **LWW conflict resolution:** a node with a fast clock silently *loses future writes* from nodes with slower clocks; causality violated with no error anywhere. Logical clocks (Lamport/version vectors) order by causality instead.
  - Ordering events across nodes by timestamp is unsound at millisecond scales.
- **Confidence intervals:** a clock reading is really a range. Google **Spanner TrueTime** returns [earliest, latest]; Spanner *waits out the uncertainty interval* before commit so timestamp order matches real order — the trick that makes globally-consistent snapshots possible (and why it needs GPS/atomic clocks to keep the interval small).

## 8.4 Process Pauses

A running thread can stop for *seconds* at any point, without noticing:

- Stop-the-world **GC pauses**, VM live-migration, laptop lid close, CPU steal in clouds, page faults/swap, synchronous disk I/O in unexpected places (class loading, core dumps), SIGSTOP.
- Deadly pattern: node checks "I hold the lease" → **pauses** → lease expires, another node takes over → node wakes and writes as if still leader → corruption.

### Fencing tokens — the antidote

```
Client A: acquire lease  ── token 33 ──▶  [ GC pause... ]
Client B: acquire lease  ── token 34 ──▶  write(token 34) ✓ accepted
Client A (wakes):                          write(token 33) ✗ REJECTED (34 seen)
```

The lock service issues a **monotonically increasing token** with each grant; the *storage/resource* rejects writes with stale tokens. **The resource must participate** — a client that merely "checks the lock" can never be safe against its own pauses.

## 8.5 Knowledge, Truth, and Lies

- A node cannot trust its own judgment ("am I leader?", "am I alive?") — the **majority (quorum)** decides truth; a node declared dead by quorum must step down even if it feels fine.
- **Byzantine faults:** nodes that *lie* (malicious or buggy). Consensus protocols in DBs assume non-Byzantine (honest-but-faulty) nodes; Byzantine tolerance (aerospace, blockchains) costs 3f+1 replicas and is out of scope for typical infrastructure. Cheap partial defenses: checksums, input validation, sanity checks.
- **System models** (vocabulary for interviews): *partially synchronous* timing (usually well-behaved, occasionally unbounded) + *crash-recovery* nodes (may crash, may return with stable storage intact) — the realistic model most algorithms target.
- **Safety vs liveness:** safety = "nothing bad ever happens" (must hold *always*, even in total meltdown); liveness = "something good eventually happens" (may depend on the network healing). Consensus algorithms guarantee safety unconditionally and liveness conditionally.

## 8.6 Design Checklist Against This Chapter

1. Every remote call: timeout, bounded retries with backoff + jitter, idempotency key.
2. Never use wall-clock timestamps for ordering or conflict resolution across nodes; use logical clocks/version vectors.
3. Monotonic clocks for all durations/timeouts.
4. Any lease/lock protecting external writes → **fencing tokens enforced by the resource**.
5. Leadership and liveness decided by quorum, not self-assessment.
6. Assume GC pauses of seconds; keep critical sections short, heartbeat from a separate thread honestly.

## 8.7 Interview Sound Bites

- "A timeout is the only failure detector the network gives you, and it can't distinguish 'dead' from 'slow' from 'my response was lost.'"
- "Case 4 is the killer: the operation *succeeded* but you don't know it — that's why retries require idempotency."
- "LWW with wall clocks means the node with the fastest clock wins all conflicts — clock skew becomes silent data loss."
- "A lease check is worthless without a fencing token, because you can pause *after* the check."
- "In distributed systems, truth is defined by the majority, not by the node itself."
