# 10. Batch Processing

> Batch systems take a large, **bounded**, immutable input, crunch it, and produce derived output — no user is waiting, throughput is the metric. The philosophy matters more than the frameworks: **immutable inputs, explicit dataflow, retry-safe (idempotent) stages** — ideas that echo from Unix pipes to Spark, and that reappear in stream processing (Chapter 11).

## 10.1 The Unix Philosophy — Batch Processing's DNA

`cat access.log | awk '{print $7}' | sort | uniq -c | sort -rn | head -5` — a log analysis "pipeline" with:

- **Uniform interface** (text streams / stdin-stdout) → arbitrary composition of small single-purpose tools.
- **Immutable input**, output separated from input → rerun any stage safely; debug by inspecting intermediate results.
- `sort` spills to disk automatically → handles data larger than memory.

Limitation: one machine. MapReduce = "Unix pipes across a thousand machines."

## 10.2 MapReduce Model

Runs over a distributed filesystem (**HDFS**: files split into blocks, replicated across commodity nodes; shared-nothing).

```
Input blocks ──▶ MAP (extract key-value pairs)      ── local computation
                    │ shuffle: partition by hash(key),
                    ▼ sort by key, copy over network
                REDUCE (all values for a key together) ──▶ output files
```

- **Put the computation near the data:** the scheduler runs mappers on nodes holding the input blocks (saves network).
- The **shuffle** (partition + sort + merge) is the expensive heart — it's what brings "all records with the same key to the same place," the primitive behind joins and grouping.
- Fault tolerance: any failed task is simply **re-executed** — safe because inputs are immutable and outputs are written once (retries need determinism/idempotence).
- Workflows: real jobs are chains of MapReduce stages, with each stage's output materialized to HDFS.

## 10.3 Joins and Grouping at Scale

The core question of any join: how do the matching records find each other?

| Join type | How | When |
|---|---|---|
| **Sort-merge join** (reduce-side) | Map both datasets by join key; shuffle brings matching records to the same reducer | General-purpose; both sides large; pays full shuffle |
| **Broadcast hash join** (map-side) | Small side fits in RAM → load as hash table in every mapper; stream the big side through | Big ⨝ small (fact ⨝ dimension) — avoids shuffle entirely |
| **Partitioned hash join** | Both sides already partitioned identically → each mapper joins one partition pair | Pre-partitioned pipelines |

- **Skew (hot keys):** one celebrity key can send millions of records to one reducer → the whole job waits on it. Fixes: skewed-join handling (spread the hot key over random reducers + replicate the other side), two-stage aggregation (local pre-aggregation / combiners, then final merge).
- **Why not just query a DB from the mappers?** Network round trip per record → throughput death + hammering the DB. Batch philosophy: **take a snapshot/copy of the DB into the batch environment** and join locally.

## 10.4 Batch Outputs — Build, Don't Mutate

- Typical outputs: search indexes, recommendation/ML models, precomputed views, key-value stores for serving.
- Pattern: **build the output file fully, then atomically swap it in** (immutable build artifacts, e.g., write SSTable/index files and bulk-load them). Never issue per-record writes to a live DB from a batch job (slow, non-atomic, can overwhelm the store).
- Benefits: rollback = repoint to previous artifact ("**human fault tolerance**" — bad code produces a bad artifact, not corrupted state); reruns are idempotent; the *inputs stay pristine* so multiple experiments can run off the same data.

## 10.5 Beyond MapReduce — Dataflow Engines

MapReduce's weaknesses: every stage materializes to disk (HDFS) before the next starts; sort at every boundary; poor fit for iterative algorithms (ML, graphs).

**Dataflow engines (Spark, Flink, Tez):** model the whole workflow as a **DAG of operators**:
- Pipeline between stages **without full materialization**; sort only when needed; keep intermediate data in memory / spill selectively.
- Fault tolerance without materialized checkpoints: **recompute lost partitions from lineage** (Spark RDDs) — requires deterministic operators.
- Iterative/graph processing (Pregel model): vertices exchange messages across supersteps until convergence (PageRank-style).

| | MapReduce | Spark/Flink |
|---|---|---|
| Intermediate state | HDFS files (durable, slow) | Memory/pipelined (fast) |
| Recovery | Re-run task | Recompute from lineage / checkpoints |
| Iterations | New job per iteration | Native loops |
| Today's role | Conceptual foundation | What you actually use |

## 10.6 Batch in Modern Architectures

- **ETL/ELT into warehouses and lakes:** raw immutable event data (data lake, Parquet on S3) → batch transforms → warehouse marts ("schema-on-read at the lake, schema-on-write at the mart").
- Batch as the **backfill/rebuild arm** of derived data: whenever a stream pipeline's logic changes, you re-run a batch job over history to rebuild views (foreshadows the lambda/kappa discussion, Chapter 11).
- Scheduling/orchestration: DAG schedulers (Airflow/Dagster) sequence jobs, retry failures, track data dependencies.

## 10.7 Interview Sound Bites

- "Batch = bounded immutable input, derived output, throughput over latency. Retry safety falls out of immutability."
- "The shuffle *is* the join: bring same-keyed records to the same place, then it's a local problem."
- "Big-table-joins-small-table? Broadcast hash join — ship the small table, skip the shuffle."
- "Batch outputs should be immutable artifacts you swap atomically — rollback becomes 'repoint,' and bad code can't corrupt the source."
- "Spark's real edge over MapReduce is not 'memory' as magic — it's pipelining a DAG instead of materializing every stage, with lineage-based recovery."
