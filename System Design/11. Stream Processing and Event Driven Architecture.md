# 11. Stream Processing and Event-Driven Architecture

> Streams are batch processing's unbounded sibling: instead of yesterday's snapshot, process **events as they happen**. The core abstractions: the **event** (immutable fact + timestamp), the **log** (append-only, replayable), and the insight that **a database and an event log are two views of the same thing** (the log is the write path; tables/views are derived read paths).

## 11.1 Messaging Systems — Two Camps

| | Message broker (AMQP/JMS: RabbitMQ, SQS) | **Log-based broker (Kafka, Pulsar, Kinesis)** |
|---|---|---|
| Model | Queue; message deleted after ack | Append-only partitioned log; consumers track **offsets** |
| Delivery | Load-balance individual messages across workers | Each partition consumed in order by one consumer per group |
| Replay | Gone once acked | **Re-read anytime** — messaging with database-like durability |
| Ordering | Lost under redelivery/competing consumers | Per-partition total order |
| Fit | Task queues, per-message expensive work, no ordering need | Event streams, fan-out to many consumers, reprocessing |

Log-based details worth saying in interviews: consumer position = a single offset number (cheap bookkeeping, batchable); a slow consumer delays only itself (buffer = disk); fan-out is free (independent consumer groups); **ordering only within a partition** — choose partition keys so events that must be ordered (same user/account) share a partition. Head-of-line: one slow *message* blocks its partition — queues handle that case better.

## 11.2 Databases Meet Streams

- **Dual-write problem:** app writes DB *and* cache *and* index → race conditions and partial failures cause silent divergence (no atomicity across systems).
- **Change Data Capture (CDC):** tail the database's replication log and publish every change to a stream → the DB stays the **system of record (leader)**; caches/indexes/warehouses become **followers** applying the same ordered changes. Tools: Debezium (MySQL/Postgres binlog → Kafka).
- **Log compaction:** Kafka retains the *latest* value per key forever → a new consumer can bootstrap the full current state from the compacted topic, then stay current — the log doubles as a database snapshot.
- **Outbox pattern:** within the DB transaction, insert the event into an outbox table; a relay publishes it → atomic "write + publish" without 2PC.

## 11.3 Event Sourcing and the Log-Table Duality

- **Event sourcing:** store the *history of immutable domain events* ("ItemAddedToCart") as truth; current state = a fold/replay of events. Benefits: complete audit trail, temporal queries ("state as of Tuesday"), new views derivable retroactively. Costs: event schema evolution, snapshotting for replay speed, harder "read current state" path (CQRS: separate write model from derived read models).
- **Duality:** *the changelog is the write-optimized truth; tables, caches, and indexes are just materialized views over it.* Applications built this way ("turning the database inside out", Kafka Streams/Materialize): state at any consumer = a deterministic function of the log — rebuildable, debuggable, replayable.
- **Immutability caveats:** truly deleting data (GDPR) requires excision machinery; very high-churn keys make replay expensive.

## 11.4 Stream Processing Operations

Three broad uses: **CEP** (pattern matching over event sequences — fraud), **analytics** (windowed aggregations — metrics), **materialized view maintenance** (keeping derived stores fresh).

### Time — the hard part

- **Event time** (when it happened) vs **processing time** (when it arrived). Confusing them under lag/restart produces artifact spikes.
- **Straggler events** arrive after their window closed → either drop+correct later, or wait via **watermarks** ("no events older than X expected"); late events beyond the watermark handled by updates/corrections.

### Windows

| Window | Example (size 5 min) | Use |
|---|---|---|
| Tumbling | 00:00–00:05, 00:05–00:10 (disjoint) | Per-interval counts |
| Hopping | 00:00–00:05, 00:01–00:06 (overlap) | Smoothed aggregates |
| Sliding | Any 5-min span containing events | "Rate over the last N minutes" |
| Session | Grouped by user activity, closed on idle gap | User sessions |

### Stream joins

- **Stream-stream:** join events within a time window (search events ⨝ click events) — state = recent events on both sides.
- **Stream-table (enrichment):** events ⨝ database state; keep a local copy of the table *updated via CDC* (no per-event DB round trips).
- **Table-table:** two changelogs → materialized join view maintained incrementally.
- Time-dependence: join results depend on arrival order (e.g., which tax rate applied?) — solve by versioning the slowly-changing dimension.

## 11.5 Fault Tolerance and Exactly-Once

An "exactly-once" *effect* (not literal single processing) = at-least-once delivery + de-duplication of results:

1. **Checkpointing + replay** (Flink): periodic state snapshots; on failure, restore + replay from offset — internal state exactly-once.
2. **Idempotent writes:** results keyed so reprocessing overwrites identically (offset-tagged writes, deterministic keys) — the workhorse technique.
3. **Transactional sinks** (Kafka transactions): atomically commit output + consumer offsets together.

Rule: **end-to-end exactly-once = at-least-once + idempotent (or transactional) sink.** Say that sentence in interviews.

## 11.6 Architecture Patterns Cheat Sheet

| Pattern | What it solves |
|---|---|
| CDC → stream → derived stores | Cache/index/warehouse consistency without dual writes |
| Outbox | Atomic DB-write + event-publish |
| Event sourcing + CQRS | Audit trail, temporal queries, independent read models |
| Log compaction | Bootstrapping consumers with full current state |
| Lambda (batch + stream in parallel) → **Kappa** (stream-only + replay for reprocessing) | Reprocessing after logic changes; Kappa avoids maintaining two codebases |
| Backpressure (pull-based consumers, bounded buffers) | Fast producer vs slow consumer without OOM |

## 11.7 Interview Sound Bites

- "Kafka's trick is making messaging durable and *replayable*: consumer state is one offset, and rewinding it is time travel."
- "Dual writes are a distributed-systems bug pattern; CDC turns 'keep the cache in sync' into ordered log-following."
- "Tables are caches of their changelog — every index, cache, and view is a materialized fold over the event stream."
- "Exactly-once means exactly-once *effects*: at-least-once delivery plus idempotent or transactional sinks."
- "Windowed results need event time + watermarks; processing time lies whenever there's lag or a restart replay."
