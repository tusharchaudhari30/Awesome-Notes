# 9. Consistency and Consensus

> Chapter 8 catalogued what goes wrong; this chapter is the toolkit of *guarantees* we can still build: linearizability (the strongest single-object consistency), ordering/causality, and consensus — the primitive under leader election, atomic commit, and every coordination service (ZooKeeper/etcd).

## 9.1 Linearizability

**Definition:** the system behaves as if there were **one copy of the data**, and every operation takes effect **atomically at one point in time** between its start and end. Once any read returns a new value, *all* later reads must return it (no flickering back). It's a *recency guarantee* — the strongest common meaning of "strong consistency."

**Who needs it:**
- **Leader election / distributed locks** — two nodes must never both believe they hold the lock.
- **Uniqueness constraints** (usernames, seat booking, balance ≥ 0).
- **Cross-channel dependencies** — e.g., write image → send queue message → worker reads image: if storage isn't linearizable, the worker may read the old version despite the message arriving "after."

**What is / isn't linearizable:**

| System | Linearizable? |
|---|---|
| Single-leader DB, reads from leader (careful failover) | Potentially yes |
| Read replicas / async followers | No (stale reads) |
| Dynamo-style quorums (w+r>N) | **No** in general (concurrent writes, sloppy quorums, partial failures) |
| Consensus systems (ZooKeeper, etcd) | Yes (writes; reads with quorum/read-index) |
| Multi-leader | No (concurrent conflicting writes by design) |

*Linearizability ≠ serializability:* linearizability = single-object recency; serializability = multi-object transaction isolation. Combined = **strict serializability**.

### CAP, stated usefully

During a network **P**artition, choose: remain **C**onsistent (linearizable — some nodes must refuse requests) or remain **A**vailable (every node keeps serving — giving up linearizability). No partition → you can have both; the theorem says nothing else. Better framing: **"consistent or available *when partitioned*."**

**The latency angle (why systems drop linearizability even without partitions):** linearizable ops require coordination — round trips — so they're *slow everywhere, all the time*. Most systems choose performance, not just partition tolerance.

## 9.2 Ordering and Causality

- **Causal consistency:** causes precede effects (question before answer, create before edit). It's the strongest consistency that doesn't require blocking on network round trips — concurrent (causally unrelated) operations may be seen in different orders.
- Linearizability ⇒ total order ⇒ causal order. Causality is a **partial** order — that's what makes it cheaper.
- **Lamport timestamps:** (counter, nodeId); every message carries the max counter seen; recipients fast-forward. Gives a **total order consistent with causality** — but only *after the fact*; it can't answer "is this username claim safe **right now**?" For that you need to know the order is *final*: → total order broadcast.
- **Total order broadcast:** all nodes deliver the same messages in the same order, reliably. Equivalent in power to consensus. It's exactly a **replicated log** (state machine replication: apply the same ordered ops everywhere → identical replicas). Linearizable storage can be built from it (append your claim; it's yours iff it's the first claim for that name in the log).

## 9.3 Consensus

**Problem:** several nodes must **agree on a value** such that the decision is final (uniform agreement, integrity, validity) and eventually happens if a majority is alive (termination). Equivalent problems: atomic commit, leader election, total order broadcast, linearizable CAS, locks/leases, membership.

- **FLP result:** no deterministic algorithm can *guarantee* consensus in a fully asynchronous model — but timeouts/randomness make it practical.
- **2PC is not fault-tolerant consensus:** the coordinator is a single point of failure (in-doubt participants block holding locks).

### How Raft/Paxos/Zab actually work (interview level)

1. **Epochs (terms):** each leadership has a monotonically increasing epoch number; higher epoch wins — this defuses split brain from zombie leaders (an epoch is a fencing token).
2. **Two quorum rounds:** to be elected, a candidate needs a **majority vote**; to decide a value, the leader needs a **majority ack**. The quorums overlap → any new leader is guaranteed to see (and preserve) previously decided values.
3. In steady state it degenerates to: leader appends to a replicated log, followers ack, majority ack = committed → **total order broadcast**, i.e., continuous consensus on each log slot.

Costs: majority round trip per decision (latency), needs 2f+1 nodes to tolerate f failures, sensitive to flaky networks (leader churn), and quorum loss = unavailability for writes — **consensus buys safety at the price of latency and minority-partition availability.**

## 9.4 ZooKeeper / etcd — Consensus as a Service

Outsource the hard part. They provide a small, replicated, linearizable key-value store plus:

- **Atomic CAS** → distributed locks/leases; **ephemeral nodes** → liveness-linked registrations (session dies → node vanishes); **monotonic sequence numbers** → fencing tokens; **watches** → change notifications.
- Built on these: leader election, service discovery, membership, partition→node assignment (Kafka controllers, HBase, Flink HA...).
- Usage rule: keep **slow-changing coordination metadata** there ("who leads partition 7"), never application data — it's a coordination service, not a database.

## 9.5 Putting It Together — What to Use When

| Need | Reach for |
|---|---|
| "At most one X globally" (lock, leader, unique name) | Consensus service (etcd/ZooKeeper) + fencing token at the resource |
| Ordered, replayable multi-consumer feed | Replicated log (Kafka) — total order per partition |
| Recency-critical read after write | Linearizable read (leader read / quorum read-index) — accept the latency |
| Social-feed-style "causes before effects" | Causal consistency / same-partition ordering — cheap |
| Cross-node agreement without majority available | **Impossible** — degrade explicitly (read-only mode, queue writes) |

## 9.6 Interview Sound Bites

- "Linearizability = one-copy illusion + recency; serializability = transaction isolation. Different axes; together they're strict serializability."
- "CAP is only about behavior *during* a partition; the everyday reason to drop linearizability is latency, not partitions."
- "Lamport timestamps order events after the fact; uniqueness *now* needs total order broadcast — i.e., consensus."
- "Raft's two overlapping majorities — election and replication — are precisely what guarantees a new leader can't lose committed writes."
- "Epoch numbers are consensus's fencing tokens: any decision is double-checked against a majority that would reveal a newer leader."
