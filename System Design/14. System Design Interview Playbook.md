# 14. System Design Interview Playbook

> A repeatable framework, back-of-envelope numbers worth memorizing, and two worked designs that exercise the whole book: a URL shortener (read-heavy, simple) and a chat system (stateful, fan-out, ordering).

## 14.1 The 5-Step Framework (45-minute pacing)

1. **Requirements (~5 min)** — Functional: core flows only ("shorten URL, redirect, expiry?"). Non-functional: scale (DAU, QPS, data size), latency targets, consistency needs, availability. *Ask, don't assume; write them down.*
2. **Estimation (~5 min)** — QPS (avg + peak ≈ 2–5×), storage/year, bandwidth, cache size (80/20 rule). Only compute numbers that will drive a decision.
3. **High-level design (~10 min)** — Boxes and arrows: clients → LB/gateway → services → data stores + cache + queue. Define APIs (a few REST/gRPC signatures) and the data model (key entities, partition keys).
4. **Deep dives (~15 min)** — Interviewer-guided. Have depth ready for: the data store choice (Chapter 2, Database Types), sharding/replication (5–6), the hot path's cache strategy (12), async workflows (11, 13), the consistency story (7, 9).
5. **Wrap-up (~5 min)** — Bottlenecks and evolution: single points of failure, hot keys, next 10× (what breaks first?), monitoring, cost.

**Meta-signals interviewers grade:** driving the conversation, justifying trade-offs ("X over Y *because* requirement Z"), quantifying ("that's ~2 TB/year, fits one Postgres box"), and naming failure modes unprompted.

## 14.2 Numbers Worth Knowing

### Latency (orders of magnitude)

| Operation | Time |
|---|---|
| L1 cache / branch mispredict | ~1 ns |
| RAM access | ~100 ns |
| SSD random read | ~100 µs |
| Same-DC network round trip | ~0.5 ms |
| Read 1 MB sequentially: RAM / SSD / disk | 10 µs / 1 ms / 20 ms |
| HDD seek | ~10 ms |
| Cross-continent round trip | ~70–150 ms |

### Capacity rules of thumb

- 1 day ≈ 86,400 s (round to 100 K for arithmetic). 1 M requests/day ≈ **12 QPS**; 100 M/day ≈ 1,200 QPS.
- One modern server: ~10–50 K simple HTTP QPS; Redis: ~100 K ops/s/node; Postgres: thousands of TPS (transactional).
- Char ≈ 1 B; UUID 16 B; typical row/event ≈ 0.1–1 KB; image ≈ 100 KB–1 MB; 1 min HD video ≈ 50–100 MB.
- Storage math template: `writes/day × object size × replication (×3) × retention`.

## 14.3 Worked Example A — URL Shortener (read-heavy)

**Requirements:** shorten (custom alias optional), redirect, TTL, click stats. 100 M new/month (~40 writes/s), 100:1 read:write (~4 K reads/s, peak 20 K). Redirect p99 < 50 ms. High availability; eventual consistency fine *except alias uniqueness*.

**Estimation:** 100 M × 12 mo × 5 yr = 6 B URLs. ~500 B/record → ~3 TB raw. 7-char base62 = 62⁷ ≈ 3.5 T ids — ample.

**Design:**
- **ID strategy:** pre-generated **Key Generation Service** (batches of unused keys handed to app servers — no per-request coordination) or base62(Snowflake id). Uniqueness of *custom* aliases = unique constraint / linearizable claim (Chapter 9 flavor).
- Store: KV-shaped access (`code → url`) → DynamoDB/Cassandra partitioned by code (uniform hash, no hot ranges), or Postgres + read replicas at this modest size — *say the trade-off out loud*.
- **Read path is a cache problem:** CDN/edge cache hot codes (~20 % of codes = 80 % of traffic; 3 TB × hot fraction fits Redis cluster). Cache-aside, TTL+jitter, negative-caching for unknown codes (penetration), 301 vs 302 (301 = browser-cached, fewer hits but no analytics; **302 for stats**).
- **Clicks:** never synchronous DB writes — emit event to Kafka → stream aggregation (windowed counts, Chapter 11) → analytics store.
- Failure notes: hot celebrity link → CDN absorbs; region loss → multi-region replicas (async; alias claims pinned to a home region).

## 14.4 Worked Example B — Chat System (write-heavy, stateful)

**Requirements:** 1:1 + small groups, online presence, delivery/read receipts, history, push when offline. 50 M DAU × 40 msgs ≈ 2 B msgs/day (~23 K avg / 100 K peak msg/s). Ordering within a conversation; no message loss.

**Design:**
- **Connections:** WebSocket gateways (stateful, connection-affine); session registry (userId → gateway node) in Redis. Messages route: sender → gateway → **chat service** → Kafka (partition key = conversationId → per-conversation ordering, Chapter 11) → delivery service → recipient's gateway (or push notification if offline).
- **Storage:** write-heavy append workload → **LSM wide-column store** (Cassandra/Scylla): partition key `conversation_id`, clustering by `(message_id)` where message_id = Snowflake (time-sortable) → "recent messages of conversation" is one-partition range scan (Chapters 3, 6).
- **Delivery semantics:** at-least-once + client-side dedupe by message_id; receipts as separate lightweight events; sequence numbers per conversation expose gaps for pull-based repair.
- **Presence:** heartbeat every ~10 s into Redis with TTL; subscribers get debounced online/offline events (don't broadcast flapping).
- **Group fan-out:** per-recipient delivery via consumer of the conversation partition; large groups → batched delivery, no per-member synchronous writes.
- Deep-dive ammo: gateway node dies (clients reconnect → registry updates → replay from last acked offset); hot conversation (celebrity broadcast → split to announcement channel semantics); multi-region (home-region per conversation to keep ordering, async geo-replication).

## 14.5 Design-Decision Cheat Table

| Requirement signal | Reach for |
|---|---|
| Read-heavy, tolerable staleness | Cache + read replicas + CDN |
| Write-heavy append stream | LSM store / Kafka ingestion |
| Strict uniqueness / counters / money | Single-leader RDBMS + transactions (or consensus service) |
| "Must never lose a message" | Durable log + at-least-once + idempotent consumers |
| Fan-out to followers | Hybrid push/pull by audience size |
| Cross-service workflow | Saga/outbox + queue, never 2PC |
| Full-text / faceted search | Derived search index via CDC |
| Files/media | Object storage + pre-signed URLs + CDN |
| Global low latency | Regional deployments + geo-DNS + async cross-region replication (+ conflict story) |

## 14.6 Interview Sound Bites

- "Peak ≈ 2–5× average; I design for peak and autoscale the difference."
- "Every derived store (cache, index, feed) gets the same treatment: fed from the source of truth's changelog, rebuildable, allowed to lag."
- "I pick the partition key from the dominant query, then check it doesn't create a celebrity hot spot."
- "The consistency budget is spent where invariants live — uniqueness and money get transactions; timelines get eventual."
- "My wrap-up is always: SPOFs, hot keys, what breaks at 10×, and what I'd monitor to see it coming."
