# 13. Scalable System Building Blocks

> The recurring supporting cast of every system-design answer: gateways, rate limiters, ID generators, task queues, notification fan-out, blob storage, and observability. Each is a small, well-understood component — knowing the standard options and their trade-offs makes designs fast to assemble.

## 13.1 API Gateway & Edge

Single entry point in front of services: **routing, authN/Z (JWT/OAuth validation), rate limiting, TLS termination, request/response transformation, caching, canary routing, WAF**.

- Gateway (north-south traffic, client→services) vs **service mesh** (east-west, service↔service: mTLS, retries, telemetry via sidecars).
- Keep it thin: business logic in the gateway is a classic architectural smell ("smart endpoints, dumb pipes").
- **BFF (Backend-for-Frontend):** per-client-type gateway/aggregator (mobile vs web) that composes internal APIs into client-shaped responses.

## 13.2 Rate Limiting

Protects against abuse, protects downstream capacity, enforces fairness/quotas.

| Algorithm | Mechanics | Character |
|---|---|---|
| **Token bucket** | Bucket refills at rate r, holds burst b; request takes a token | Allows bursts; the default answer (AWS, Stripe) |
| Leaky bucket | Fixed-rate drain queue | Smooths to constant outflow; adds queueing delay |
| Fixed window | Counter per window | Simple; 2× burst at window edges |
| **Sliding window (log/counter)** | Weighted count over rolling window | Accurate, modest cost — common in practice |

- **Distributed limiting:** counters in Redis (atomic Lua for check-and-increment); or local buckets syncing quota asynchronously (accept small overshoot for latency).
- Respond `429` + `Retry-After`; decide **fail-open vs fail-closed** when the limiter itself is down (usually fail-open for availability, fail-closed for billing/abuse).
- Related: **load shedding** (drop by priority when saturated), **backpressure** (bounded queues propagate slowdown upstream — better than unbounded queues that OOM).

## 13.3 Unique ID Generation

Requirements to state: uniqueness, rough time-ordering (index locality, sortable), no coordination on hot path, size.

| Option | Structure | Trade-offs |
|---|---|---|
| Auto-increment | DB sequence | Coordination bottleneck; leaks volume; awful for sharding |
| UUIDv4 | 128-bit random | No coordination; random → **index page splits / poor B-tree locality** |
| **Snowflake** | 41-bit timestamp + 10-bit worker id + 12-bit sequence (64-bit) | Sortable, 4M ids/sec/worker; needs worker-id assignment + **clock-skew handling** (refuse to go backwards) |
| UUIDv7 / ULID | Timestamp-prefixed random | Sortable + coordination-free; the modern default |

## 13.4 Async Work: Task Queues & Schedulers

- **Task queue** (SQS/RabbitMQ/Sidekiq pattern): enqueue jobs (email, thumbnails, webhooks); workers pull; scale workers on queue depth. Essentials: **visibility timeout** (redeliver on worker death), **retries with exponential backoff + jitter**, **dead-letter queue** after N failures, **idempotent handlers** (at-least-once delivery is the norm).
- **Delayed/scheduled jobs:** broker-native delays, or a timing-wheel/sorted-set (Redis ZSET by fire-time) poller.
- **Exactly-once illusion:** dedupe keys / idempotency at the effect side, never trust the transport (see Chapters 8, 11).
- **Workflow orchestration** (multi-step, long-running, compensations): durable state machines — Temporal/Step Functions; or choreography via events (lighter, harder to trace).

## 13.5 Fan-out & Notifications

- **Feed fan-out:** on-write (precompute per-follower inboxes; fast reads, celebrity write storms) vs on-read (compute at request; slow reads, cheap writes) → **hybrid by follower count** (Chapter 1's Twitter example).
- **Push notifications:** app servers → queue → notification service → APNs/FCM; store device tokens, dedupe, respect rate/preferences; deliveries are at-least-once, unordered.
- **WebSockets / SSE / long-polling** for live updates: WebSocket = bidirectional (chat, games); SSE = server→client only, auto-reconnect, plain HTTP (feeds, tickers); both need **connection-affine gateways** (a user's connection lives on one node) + pub/sub (Redis/Kafka) to route messages to whichever node holds the connection.

## 13.6 Blob Storage & Large Files

- Objects (images, video, backups) go to **object storage** (S3/GCS): flat namespace, HTTP API, 11-nines durability via erasure coding, versioning, lifecycle tiering (hot → infrequent → archive).
- **Never stream large uploads through your app servers:** issue **pre-signed URLs** — client uploads/downloads directly to object storage; your API only authorizes and records metadata.
- Serving: object storage as CDN origin; media pipeline = upload → queue → transcode workers → variants in storage → CDN.
- DB stores *metadata + pointer*, never the blob.

## 13.7 Search as a Component

- OLTP DBs are bad at relevance-ranked, typo-tolerant, faceted text search → dedicated engine (Elasticsearch/OpenSearch, Typesense/Meilisearch).
- Keep it a **derived system**: index fed from the source of truth via CDC/outbox (Chapter 11); rebuildable from scratch; eventual consistency between DB and index is expected and must be acceptable (or verified in the UX).
- Internals in Database Types → Search Engines chapter (inverted index, BM25).

## 13.8 Observability & Operational Safety Nets

- **Three pillars:** metrics (Prometheus-style, RED: rate/errors/duration + saturation), logs (structured, centralized), traces (**correlation/trace id propagated** across every hop — the only way to debug a 12-service request).
- **SLI → SLO → error budget:** define what "working" means (p99 latency, availability), alert on *budget burn rate*, not raw spikes.
- Resilience defaults every design should mention: **timeouts everywhere, retries-with-jitter only on idempotent ops, circuit breakers, bulkheads (isolated pools per dependency), graceful degradation** (serve stale/partial rather than 500).
- Deploy safety: **feature flags, canary + progressive rollout, fast rollback** — human faults are the top outage cause (Chapter 1).

## 13.9 Interview Sound Bites

- "Token bucket for limits (bursts allowed), Redis+Lua when it must be global, 429 with Retry-After, and a deliberate fail-open/closed choice."
- "UUIDv7/Snowflake over UUIDv4: time-prefixed ids keep B-tree inserts append-ish instead of splitting random pages."
- "Every queue consumer is idempotent, has a visibility timeout, backoff with jitter, and a DLQ — at-least-once is the contract."
- "Large files go client → pre-signed URL → S3; my API only ever touches metadata."
- "Search, caches, and feeds are all *derived data* — fed by CDC from one source of truth, rebuildable, allowed to lag."
