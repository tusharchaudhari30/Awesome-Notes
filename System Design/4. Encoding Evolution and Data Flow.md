# 4. Encoding, Evolution and Data Flow

> Systems evolve while running. Rolling upgrades mean **old and new code, and old and new data formats, coexist** — permanently (data outlives code). Everything here is about keeping that coexistence safe: encodings, schema evolution, and the three ways data flows between processes (databases, service calls, messages).

## 4.1 Compatibility — The Core Concept

- **Backward compatibility:** *newer code* can read data written by *older code*. Usually easy — you know the old format.
- **Forward compatibility:** *older code* can read data written by *newer code*. Harder — old code must ignore fields it doesn't know about, **without dropping them** on a read-modify-write.
- Rolling upgrades require **both** simultaneously: during deploy, old and new nodes serve traffic side by side.

## 4.2 Encoding Formats

| Format | Schema? | Compact? | Compatibility story |
|---|---|---|---|
| Language-native serialization (Java `Serializable`, pickle) | No | No | **Avoid** — language lock-in, security holes (deserialization RCE), poor versioning |
| JSON / XML | Optional | No | Human-readable, universal; ambiguity around numbers (JS 2^53 precision → send IDs as strings), no binary strings (Base64 +33 %) |
| Thrift / Protocol Buffers | Required | Yes | **Field tags** (numbers) are the contract — names can change, tags never. New fields must be optional/defaulted |
| Avro | Required | Yes (most compact) | No tags — **writer's schema + reader's schema resolved at read time**. Friendliest for dynamically generated schemas and schema registries (Kafka) |

**Schema evolution rules (Protobuf/Thrift):**
- Add fields → new tag numbers, must be optional (forward compat: old code ignores unknown tags; backward compat: new code fills defaults).
- Never reuse or change a tag number; only remove optional fields.
- Changing types is risky (truncation).

**Why schema-based binary formats win for internal services:** compact, schema = guaranteed-current documentation, code generation gives type safety, and a **schema registry** can check compatibility *before* deploy.

## 4.3 Dataflow Through Databases

"Sending a message to your future self." The subtleties:

- Data outlives code: five-year-old rows will be read by next year's code — schema evolution is not optional.
- The **unknown-field preservation trap:** old code reads a row written by new code, updates one field, writes back — and silently drops the new field unless the ORM/code preserves unknowns.
- Migrations: most engines can `ADD COLUMN` with a default cheaply; full rewrites at scale need online-migration tooling (gh-ost, pt-online-schema-change).

## 4.4 Dataflow Through Services: REST and RPC

**Service-oriented / microservices architecture:** decompose by function, expose APIs, make services independently deployable — which *forces* the compatibility discipline above across team boundaries.

### REST vs RPC

| Aspect | REST (HTTP+JSON) | gRPC (Protobuf) |
|---|---|---|
| Philosophy | Resources, verbs, HTTP semantics | Call a remote function |
| Performance | Text, HTTP/1.1 typical | Binary, HTTP/2, multiplexed, streaming |
| Contract | OpenAPI (optional, drifts) | `.proto` (enforced, codegen) |
| Best for | Public APIs, browser clients | Internal service-to-service |

**The fundamental problem with RPC:** a network call is *not* a local call, and abstractions that pretend otherwise leak:
- It can fail, time out, or succeed **without you receiving the response** (was the action performed? → need **idempotence** to retry safely).
- Latency is wildly variable; payloads must be encoded; no pass-by-reference.
- Design consequence: make remote calls explicit, set **timeouts + retries with idempotency keys + circuit breakers**.

**API versioning:** URL/`Accept`-header versions for REST; additive-only evolution for Protobuf. Rule: the server must tolerate old clients indefinitely (you don't control client upgrades).

## 4.5 Dataflow Through Messages (Async)

**Message broker** (Kafka, RabbitMQ, SQS) between sender and recipient:

Advantages over direct RPC:
1. **Buffering** — absorbs recipient overload/unavailability (improves reliability).
2. **Decoupling** — sender doesn't know who consumes; one message can fan out to many consumers; consumers can be added later without touching producers.
3. **Redelivery** — crashed consumers don't lose messages.

Cost: **one-way, asynchronous** — the sender doesn't wait for (or usually get) a response; the reply, if any, arrives on another channel.

```
   Producer ──▶ [ Broker: topic/queue ] ──▶ Consumer A (email)
                        │
                        └──────────────────▶ Consumer B (analytics)
```

- **Queue semantics** (RabbitMQ/SQS): message deleted after ack — each message processed by one consumer (work distribution).
- **Log semantics** (Kafka): append-only log, consumers track offsets — replayable, multiple independent consumer groups (see Chapter 11).
- Messages are bytes → same schema-evolution rules apply; this is where **Avro + schema registry** shines: producers and consumers deploy independently, the registry enforces compatible schema changes.

## 4.6 Choosing the Data Flow

| Need | Use |
|---|---|
| Synchronous answer required (user waiting) | REST/gRPC call |
| Fire-and-forget, spikes, fan-out, retries | Message broker |
| State that outlives processes | Database |
| Cross-team public contract | REST + OpenAPI, additive evolution |
| High-QPS internal mesh | gRPC + Protobuf |

## 4.7 Interview Sound Bites

- "Rolling upgrades make forward *and* backward compatibility mandatory — old and new code run side by side during every deploy."
- "In Protobuf the field *tag* is the contract; rename freely, renumber never."
- "An RPC can succeed without the caller knowing — that's why every retried endpoint needs an idempotency key."
- "A message broker converts a temporal coupling (both up at once) into a durability problem the broker solves for you."
- "Data outlives code — the database will hold every schema version you ever wrote."
