# 5. Replication

> Replication = keeping a copy of the same data on multiple machines. Why: **high availability** (survive node/datacenter loss), **latency** (data near users), and **read throughput** (scale reads). The entire difficulty is one thing: **handling changes** to replicated data.

## 5.1 Three Replication Architectures

| Architecture | Writes go to | Used by | Sweet spot |
|---|---|---|---|
| **Single-leader** | One leader; followers replicate | PostgreSQL, MySQL, MongoDB, Kafka | Default choice; simple conflict-free writes |
| **Multi-leader** | A leader per datacenter/device | Bi-directional MySQL, CouchDB, calendar apps, collaborative editors | Multi-DC write latency, offline clients |
| **Leaderless** | Any replica (quorums) | Cassandra, DynamoDB(-style), Riak | Always-writable, no failover machinery |

## 5.2 Single-Leader (Primary/Replica)

```
             writes                 replication log
  Client ───────────▶ Leader ───────────────────────▶ Follower 1
                        │        (change stream)  └──▶ Follower 2
  Client ◀──── reads ───┴──────── reads can go to leader or followers
```

### Sync vs async replication

- **Synchronous:** leader waits for follower ack → follower guaranteed up-to-date, but one slow/dead follower blocks all writes. Practical form: **semi-synchronous** — exactly one sync follower, rest async.
- **Asynchronous:** leader never waits → fast, always-writable, but **unreplicated writes are lost if the leader dies** (weakened durability).

### Setting up followers & handling failure

- New follower: consistent snapshot + replay the replication log from the snapshot's position.
- **Follower crash:** catch-up recovery from its last logged position.
- **Leader crash → failover:** detect (timeout) → elect new leader (most up-to-date replica) → reroute writes. Failure modes to name in interviews:
  - Lost writes (async replication → new leader missing recent commits; if externally visible, dangerous — e.g., reused auto-increment keys corrupting downstream caches).
  - **Split brain** — two nodes both believe they're leader; need fencing ("shoot the other node in the head").
  - Timeout tuning — too short causes needless failovers during load spikes (which make things worse).

### Replication log implementations

Statement-based (fragile: `NOW()`, `RAND()`), **WAL shipping** (exact but couples versions/storage format), **logical (row-based) log** (decoupled — also the basis of **CDC/change data capture**), trigger-based (flexible, slow).

## 5.3 Replication Lag and Read-Your-Writes

Async followers lag behind → reading from a follower can return stale data. **Eventual consistency:** stop writing, wait, and replicas converge — "eventual" is deliberately vague.

Three anomalies + their guarantees:

| Anomaly | Guarantee needed | Implementation sketch |
|---|---|---|
| User doesn't see their own just-submitted write | **Read-your-writes** | Read own-modified data from leader; or track write timestamp and only read from sufficiently caught-up replicas; harder **cross-device** |
| Data appears, then disappears (reading from different replicas going back in time) | **Monotonic reads** | Pin each user to one replica (hash of user id) |
| Answers observed before questions (causally related writes seen out of order) | **Consistent prefix reads** | Write causally-related data to the same partition; or causality tracking |

**Design stance:** either the application handles these (complex) or you pay for stronger guarantees (transactions/consensus, Chapter 9). "Eventual consistency is fine" is a claim about your *product*, not your database.

## 5.4 Multi-Leader Replication

One leader per datacenter; leaders asynchronously replicate each other's writes.

- **Pros:** local write latency in every DC; DC failure tolerance; offline devices and collaborative editing are secretly multi-leader (every device/client is a leader).
- **The price: write conflicts.** The same record can be modified concurrently on two leaders — both succeed locally, conflict is discovered *later, asynchronously*.

### Conflict resolution

- **Avoidance** (best): route all writes for a given record to one home leader.
- **Last-write-wins (LWW):** pick highest timestamp — simple, convergent, and **silently discards writes** (plus clock-skew hazards).
- **Merge:** keep both versions and merge (application logic, or CRDTs — data structures that merge automatically: counters, sets, collaborative text).
- **On-read resolution:** store siblings, let the application/user resolve on next read.

Replication **topologies** (all-to-all, ring, star): all-to-all is most fault-tolerant but can deliver causally-related writes out of order (needs version vectors).

## 5.5 Leaderless Replication (Dynamo-style)

No leader; client (or coordinator) writes to **all N replicas**, succeeds after **w** acks; reads query **r** replicas and take the newest version.

### Quorums

```
N = replicas (e.g., 3)      w + r > N  ⇒  read & write sets overlap
w = write quorum (e.g., 2)               ⇒ reads see the latest ack'd write
r = read quorum  (e.g., 2)               (usually — see caveats)
```

- Tune for workload: w=N,r=1 → fast reads; w=1,r=N → fast writes; w=r=2,N=3 → balanced.
- **Caveats that break the "guarantee":** sloppy quorums, concurrent writes (need LWW or version vectors), partial write failures (no rollback), edge cases during node recovery. Quorum overlap is *probabilistic staleness reduction*, not linearizability.

### Keeping replicas in sync (anti-entropy)

- **Read repair:** on read, detect stale replica versions and fix them (repairs hot data only).
- **Anti-entropy process:** background comparison (Merkle trees) syncing cold data.
- **Sloppy quorum + hinted handoff:** during partitions, accept writes on stand-in nodes, hand them back later — maximizes write availability, further weakens read guarantees.

### Detecting concurrency: version vectors

"Happens-before" vs concurrent: if B builds on A, B supersedes A; if neither knew of the other, they're **concurrent** → keep both as **siblings** for later merge. Version vectors (one counter per replica per key) capture exactly this.

## 5.6 Choosing a Replication Strategy

| Requirement | Choice |
|---|---|
| Simplicity, transactions, strong-ish consistency | Single-leader (default) |
| Multi-region writes, offline-first, collaboration | Multi-leader + real conflict-resolution design |
| Extreme write availability, latency SLAs over consistency | Leaderless with tuned quorums |
| Read scaling only | Single-leader + read replicas (mind the lag anomalies) |

## 5.7 Interview Sound Bites

- "Async replication buys availability and speed by making 'committed' mean 'committed on the leader' — a failover can lose those writes."
- "The three lag anomalies I always check for: read-your-writes, monotonic reads, consistent prefix."
- "Multi-leader means conflicts are a *feature of the architecture*, not a bug — you must design the merge."
- "LWW is the polite name for 'silently drop concurrent writes.'"
- "w + r > N overlaps read and write sets, but it's not linearizability — sloppy quorums and concurrent writes both puncture it."
