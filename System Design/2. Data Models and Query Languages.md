# 2. Data Models and Query Languages

> The data model is the most consequential decision in a system's design: it shapes how you *think* about the problem, what queries are cheap, and what changes are painful. Most applications are built by layering one data model on top of another (objects → JSON/tables → bytes on disk → magnetic/flash media).

## 2.1 Relational Model

Data organized into **relations (tables)** of **tuples (rows)**. Dominant since the 1980s because it generalizes well and hides implementation detail behind a declarative interface.

- **Strengths:** many-to-one and **many-to-many relationships** via joins; strong schema; ad-hoc queries; decades of query-optimizer engineering.
- **Query optimizer** decides execution order and index usage — you declare *what*, not *how*. Add an index and queries automatically benefit; no application change.
- **Schema-on-write:** structure enforced at insert time (like static typing).

## 2.2 Document Model

Data stored as self-contained **documents** (JSON/BSON), e.g., MongoDB, CouchDB.

- **Strengths:** schema flexibility, **locality** (one read fetches the whole aggregate — e.g., a résumé with all its jobs and education), closer to application objects (kills impedance mismatch).
- **Weaknesses:** weak join support — many-to-many relationships force either denormalization (data duplication → update anomalies) or application-level joins (more code, more round-trips).
- **Schema-on-read:** structure interpreted at read time (like dynamic typing). Great for heterogeneous data or externally-determined structure; schema changes are trivial (just start writing new format + handle old in code) versus `ALTER TABLE`/backfill migrations.
- **Locality caveat:** the database typically rewrites the *entire* document on update — keep documents small and avoid writes that grow them.

**Which to pick?**

| Situation | Better fit |
|---|---|
| Tree of one-to-many, loaded together (self-contained aggregate) | Document |
| Many-to-many everywhere, evolving access patterns, ad-hoc analytics | Relational |
| Highly interconnected data (relationships *are* the data) | Graph |

**Convergence:** the models are stealing each other's features — PostgreSQL has first-class `jsonb` with indexing; MongoDB added `$lookup` (joins) and multi-document transactions. A hybrid ("polyglot persistence" within one engine) is now normal.

## 2.3 Normalization vs Denormalization

- **Normalized:** each fact stored once; relationships by reference (foreign keys / document references). Consistent updates, no duplication — but reads require joins.
- **Denormalized:** duplicate data into the read path so one fetch answers the query. Faster reads — but writes must update every copy, and application bugs can create inconsistencies.
- **System-design rule:** OLTP source-of-truth data should start normalized; denormalize *deliberately* into caches, materialized views, or read-optimized stores when read patterns demand it (see Chapter 12 — derived data).

## 2.4 Graph Model

When **many-to-many relationships are the dominant feature** (social networks, fraud rings, knowledge graphs, dependency graphs), model data as **vertices + edges**.

- **Property graph** (Neo4j, Cypher): vertices and edges each carry key-value properties; edges are typed and directed.
- **Triple store / RDF** (SPARQL): facts as (subject, predicate, object).
- Killer capability: **variable-length traversals** — "friends of friends up to 5 hops" is one Cypher clause (`-[:KNOWS*1..5]->`) but a nightmare of recursive CTEs in SQL, and the optimizer handles direction/indexing for you.
- Graphs favor **evolvability**: adding new vertex/edge types doesn't disturb existing structure.

## 2.5 Declarative vs Imperative Queries

- **Declarative (SQL, Cypher):** specify the result's shape; the optimizer chooses access paths. Concise, parallelizable, keeps the door open for the engine to improve performance without app changes.
- **Imperative (code, MapReduce-ish):** specify the steps. More control, less optimizer leverage.
- Interview line: "Declarative languages decouple *what* from *how*, which is exactly what lets databases add indexes, change storage engines, or parallelize without breaking applications."

## 2.6 Schema Evolution Cheat Sheet

| Change | Relational | Document |
|---|---|---|
| Add optional field | `ALTER TABLE ... ADD COLUMN` (fast in modern engines) | Just write it; readers tolerate absence |
| Rename/restructure | Migration + backfill (needs care at scale, often online-migration tools) | Write new shape; read-path handles both until backfilled |
| Enforce invariant | Constraint in DB — one place | Application code — every writer |

**Rule of thumb:** schema-on-write moves errors to write time (fail fast, one enforcement point); schema-on-read moves flexibility to read time (every reader carries compatibility logic).

## 2.7 Interview Sound Bites

- "I pick the data model from the *relationships*: aggregates → document, many-to-many → relational, traversals → graph."
- "Document locality is a two-edged sword: one read gets everything, but one update rewrites everything."
- "Denormalization is a read optimization paid for at write time — I treat it as derived data that must be rebuildable from the source of truth."
- "Schema-on-read vs schema-on-write is dynamic vs static typing for databases — neither is free."
